[/body/p[@paraId=1A78A695]] 04.05.01 Purpose
[/body/p[@paraId=00E531F4]] Before the three developers implement features in parallel, they need a consistent development environment that can be recreated from the repository and its documentation.
[/body/p[@paraId=0D925C2E]] NEXUS spans several execution environments:
[/body/p[@paraId=7210E5FE]] · Windows 11 for user-facing computer operations.
[/body/p[@paraId=32E2443C]] · Ubuntu on WSL 2 for backend development.
[/body/p[@paraId=4B45CF4E]] · Python and FastAPI for the API and application services.
[/body/p[@paraId=5DD4E048]] · PostgreSQL for durable application state.
[/body/p[@paraId=6C561DF5]] · A native Windows process for the bridge.
[/body/p[@paraId=074FD96D]] · A local AI runtime for planning and context processing.
[/body/p[@paraId=13B782F1]] · Git and automated tests for shared development.
[/body/p[@paraId=3AF6D75C]] These components must not depend on one developer's machine-specific paths, untracked files, manually modified database or undocumented environment variables.
[/body/p[@paraId=088BAE43]] Goal: a new developer should be able to follow the setup instructions, run the backend and test suite, connect a test Windows bridge and understand which optional capabilities require additional setup.
[/body/p[@paraId=58E7B4D5]] This is a setup specification, not a command-by-command installation tutorial. Exact software versions should be selected and pinned after the host and runtime decisions in Sections 04.01–04.03 are resolved.
[/body/p[@paraId=4D14523A]] 04.05.02 Standard development environments
[/body/p[@paraId=27079365]] Use separate environments for Linux-side development and Windows-specific execution.
[/body/p[@paraId=75C7063F]] Ubuntu on WSL 2
[/body/p[@paraId=4F5C103B]] Backend development environment
[/body/p[@paraId=7675C199]] · Python virtual environment and project dependencies.
[/body/p[@paraId=393A9900]] · FastAPI application and application services.
[/body/p[@paraId=264936D2]] · Database migrations and backend tests.
[/body/p[@paraId=6AB20BEB]] · Git operations and development scripts.
[/body/p[@paraId=2D3DA7C3]] PostgreSQL
[/body/p[@paraId=4344DD09]] Application persistence
[/body/p[@paraId=284E898C]] · Local or containerized development database.
[/body/p[@paraId=7E6B2C2A]] · Separate test database.
[/body/p[@paraId=1E7D8890]] · Version-controlled schema migrations.
[/body/p[@paraId=6F05CB1E]] Windows 11
[/body/p[@paraId=249551AB]] Native computer integration
[/body/p[@paraId=7EB67D6A]] · Windows bridge and local tool implementations.
[/body/p[@paraId=46201D38]] · Filesystem security and path handling tests.
[/body/p[@paraId=1074A351]] · Application-launch tests and bridge diagnostics.
[/body/p[@paraId=75411346]] · Windows-side credential storage if selected.
[/body/p[@paraId=2ECE9597]] Optional local AI runtime
[/body/p[@paraId=2C472FEF]] Inference and planning evaluation
[/body/p[@paraId=781A00F5]] · Installed and tested independently.
[/body/p[@paraId=10087088]] · Fixed model/runtime versions for reproducible evaluation.
[/body/p[@paraId=7D73182A]] · Not required for deterministic backend unit tests.
[/body/p[@paraId=009394DB]] Environment rules
[/body/p[@paraId=5DA15640]] 1. Run Windows-specific bridge code in the intended Windows environment rather than assuming Linux path and process semantics are equivalent.
[/body/p[@paraId=2647FB59]] 2. Use a documented Python version and dependency lock or equivalent reproducible dependency specification.
[/body/p[@paraId=0E5065FE]] 3. Keep development and test databases separate.
[/body/p[@paraId=6ED3638D]] 4. Keep the model runtime optional for tests that do not require inference.
[/body/p[@paraId=7441FA29]] 5. Do not expose PostgreSQL to the LAN merely to simplify development.
[/body/p[@paraId=5BBE3A82]] 6. Do not assume that WSL 2 networking, filesystem mounts or GPU access behave identically on every developer's computer.

[/body/p[@paraId=7D16589D]] 04.05.04 Repository bootstrap procedure
[/body/p[@paraId=0C48276B]] The repository should provide a single, documented onboarding sequence.
[/body/p[@paraId=7700FA0C]] 1. Obtain the repository
[/body/p[@paraId=67BD6778]] 2. Clone the shared Git repository into the documented WSL filesystem location. Confirm that the working tree is clean before setup.
[/body/p[@paraId=3C81E4EF]] 3. Create the Python environment
[/body/p[@paraId=0B9245A1]] 4. Use the documented Python version and project dependency configuration. Do not install project packages into Ubuntu's system Python.
[/body/p[@paraId=4C4B9E76]] 5. Load safe configuration
[/body/p[@paraId=171DB51E]] 6. Start from .env.example or the selected configuration template. Supply local secrets through the documented secret mechanism; never copy production credentials from another developer.
[/body/p[@paraId=67FA7179]] 7. Start PostgreSQL
[/body/p[@paraId=0E7E91FD]] 8. Use the approved local or containerized setup. Verify that the backend can connect and that the application and test databases are distinct.
[/body/p[@paraId=54E6C57A]] 9. Apply migrations
[/body/p[@paraId=4F80EA2A]] 10. Run the version-controlled database migrations. Confirm that a clean database reaches the expected schema version without manual SQL changes.
[/body/p[@paraId=20910977]] 11. Run deterministic tests
[/body/p[@paraId=19487AEC]] 12. Execute formatting, static checks, unit tests and contract tests before attempting real model inference or Windows operations.
[/body/p[@paraId=47EDF1FC]] 13. Start the API
[/body/p[@paraId=5CD5BE04]] 14. Start FastAPI using the documented development command. Verify liveness, readiness and authentication behavior.
[/body/p[@paraId=58602586]] 15. Configure the Windows bridge
[/body/p[@paraId=2E111355]] 16. Register a test device, establish its credentials and configure only a dedicated test directory. Verify that the bridge is associated with the correct device identity.
[/body/p[@paraId=0B45BAFA]] 17. Run the first end-to-end test
[/body/p[@paraId=3C193032]] 18. Execute the restricted file-search workflow against the test directory and verify the task record, bridge result and CLI output.
[/body/p[@paraId=20E9D12F]] 19. Configure AI separately
[/body/p[@paraId=22B00D7C]] 20. Install the selected runtime and model only after the basic stack passes. Run the documented inference smoke test and fixed planning evaluation set.
[/body/p[@paraId=249F234D]] The final repository must contain the exact commands, expected outputs and troubleshooting steps for the chosen configuration. The sequence above establishes the required order, not an assertion that the team's final tools have already been selected.
[/body/p[@paraId=57091EA2]] 04.05.05 Configuration and secrets
[/body/p[@paraId=7AE06612]] Configuration must separate application-wide defaults from machine-specific details.
[/body/p[@paraId=636CE59D]] Proposed configuration categories
[/body/tbl[2]] [Table: 8 rows]
[/body/p[@paraId=1B562681]] Required files and rules
[/body/p[@paraId=77414343]] The repository should include:
[/body/p[@paraId=194A87EA]] · .env.example containing placeholders and non-secret defaults.
[/body/p[@paraId=547D3DDB]] · .gitignore rules for local secrets, environment files, generated data and test artifacts.
[/body/p[@paraId=7B96851E]] · A configuration reference documenting each supported setting, its type, default, security implications and whether restart is required.
[/body/p[@paraId=15179075]] · Separate example configuration for backend and Windows bridge where their settings differ.

[/body/p[@paraId=692D6420]] Windows directory paths must be configured on the Windows bridge, mapped to logical directory IDs and validated locally. A Linux path in WSL is not automatically a valid Windows path.
[/body/p[@paraId=220CA547]] 04.05.06 Database setup and test isolation
[/body/p[@paraId=6A3E8B42]] The development environment must make it difficult to accidentally run tests against the wrong database.
[/body/p[@paraId=56BB9C3D]] The proposed setup defines three distinct uses:
[/body/p[@paraId=2C9CC920]] · Developer database: personal, disposable development data.
[/body/p[@paraId=5574E65E]] · Automated test database: isolated and safe to reset as part of the test workflow.
[/body/p[@paraId=027F26F7]] · Shared integration database: controlled data for multi-user and end-to-end tests.
[/body/p[@paraId=2B90FFF9]] The shared integration database must not be used as the default database for destructive automated tests.
[/body/p[@paraId=062EC75F]] Startup checks
[/body/p[@paraId=49F2F6C8]] Before migrations or tests run, the tooling should verify:
[/body/p[@paraId=7160C87D]] 1. The configured database host and database name.
[/body/p[@paraId=61AF1F33]] 2. The intended environment.
[/body/p[@paraId=2E64CE8D]] 3. That the target is not a protected shared or production-like database.
[/body/p[@paraId=408AB51E]] 4. The current schema version.
[/body/p[@paraId=39208CAF]] 5. The availability of the database dependency.
[/body/p[@paraId=4611CD7F]] If the environment cannot be established safely, the operation should fail rather than guess.
[/body/p[@paraId=0D2AD1E4]] Migration acceptance
[/body/p[@paraId=251E05DC]] A developer must be able to:
[/body/p[@paraId=29165902]] · Create an empty database.
[/body/p[@paraId=2299293E]] · Apply all migrations.
[/body/p[@paraId=6BD9A2BB]] · Start the application.
[/body/p[@paraId=27502ADC]] · Run integration tests.
[/body/p[@paraId=0DB93482]] · Upgrade a database from the previously supported schema.
[/body/p[@paraId=66903098]] · Diagnose migration failures without manually editing schema state.
[/body/p[@paraId=5446737E]] PostgreSQL integration tests are especially important for task idempotency, unique constraints, row locking, worker claims and concurrent state transitions. SQLite or an in-memory substitute cannot establish that these behaviors work correctly on PostgreSQL.
[/body/p[@paraId=7723CB8B]] 04.05.07 Windows bridge setup and safety
[/body/p[@paraId=1AA79D73]] Each developer needs a native Windows bridge instance associated with their own registered device.
[/body/p[@paraId=332A39BD]] The setup process should cover:
[/body/p[@paraId=6D745B89]] · Installing the documented Windows-side dependencies.
[/body/p[@paraId=6E6EBC60]] · Loading machine-specific configuration.
[/body/p[@paraId=63313CC0]] · Registering the bridge with the backend.
[/body/p[@paraId=46384F96]] · Provisioning a unique device credential.
[/body/p[@paraId=46018BC6]] · Mapping logical directory IDs to permitted local directories.
[/body/p[@paraId=733509E6]] · Configuring approved application IDs, if application launching is enabled.
[/body/p[@paraId=622377AE]] · Starting the bridge in the intended user context.
[/body/p[@paraId=3F094C5C]] · Verifying connectivity and reported capabilities.
[/body/p[@paraId=7022335A]] · Revoking and replacing the device credential in a controlled test.
[/body/p[@paraId=02BA299B]] Safe initial configuration
[/body/p[@paraId=1B7012D3]] Start with a dedicated test directory containing synthetic files. Do not initially point the bridge at an entire user profile, all drives or shared personal folders.
[/body/p[@paraId=26AF577E]] The bridge must reject:
[/body/p[@paraId=5DE6F2C0]] · Unknown tools and unsupported protocol versions.
[/body/p[@paraId=5B17C440]] · Invalid or revoked device credentials.
[/body/p[@paraId=04C28B04]] · Requests targeting a different device.
[/body/p[@paraId=10F9309E]] · Directory IDs not configured locally.
[/body/p[@paraId=4EF299B5]] · Paths that escape the permitted scope.
[/body/p[@paraId=7E852241]] · File creation that would silently overwrite an existing file.
[/body/p[@paraId=469F7FED]] · Operations exceeding their configured limits.
[/body/p[@paraId=234D3236]] The backend must not treat a successful bridge connection as proof that every tool is available. Tool capabilities and local directory configuration must be validated separately.
[/body/p[@paraId=54677063]] 04.05.08 Deterministic testing without a live model
[/body/p[@paraId=5AA13C0D]] A core goal of this setup is that developers can work on NEXUS without waiting for an AI runtime to load or using real inference for every test.
[/body/p[@paraId=186EC269]] The repository should provide deterministic fixtures for:
[/body/p[@paraId=13EB23A2]] · Valid plans.
[/body/p[@paraId=216A1355]] · Malformed model output.
[/body/p[@paraId=5CCA07DC]] · Unknown tools.
[/body/p[@paraId=67226835]] · Missing or invalid arguments.
[/body/p[@paraId=3EA3920A]] · Clarification requests.
[/body/p[@paraId=2586B2F8]] · Unauthorized device targets.
[/body/p[@paraId=2EC7ED6B]] · Approval-required operations.
[/body/p[@paraId=4E5B858A]] · Model timeouts and unavailability.
[/body/p[@paraId=276CD08F]] · Plans containing malicious or irrelevant document instructions.
[/body/p[@paraId=194809E0]] A mock planner can return a predetermined proposal so the team can test the task state machine, policy engine and bridge protocol independently.
[/body/p[@paraId=4A16B9E8]] However, mock tests do not replace the real-model evaluation. Keep two separate claims:
[/body/p[@paraId=5B0DFC10]] · Deterministic contract tests passed: the application correctly handles known inputs and failures.
[/body/p[@paraId=0E60783E]] · Real-model evaluation passed: the selected runtime and model meet the documented quality and resource criteria.
[/body/p[@paraId=00B117AB]] This distinction prevents a fully mocked test suite from creating a false impression of AI readiness.

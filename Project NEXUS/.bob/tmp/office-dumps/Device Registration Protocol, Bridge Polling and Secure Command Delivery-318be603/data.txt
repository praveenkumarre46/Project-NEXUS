[/body/p[@paraId=24E9476B]] 04.10.01 Purpose
[/body/p[@paraId=1F9682D0]] NEXUS needs a reliable way to deliver an authorized operation from the shared backend to the correct Windows computer, receive its result and recover when the network or either process fails.
[/body/p[@paraId=22562390]] This is not merely an HTTP integration problem. A bridge may disconnect after receiving an operation, a backend may restart before recording a response, or a message may be delivered more than once.
[/body/p[@paraId=43EDBC2C]] The communication protocol must therefore support:
[/body/p[@paraId=403CF443]] · Secure device registration and authentication.
[/body/p[@paraId=45373162]] · Device-specific operation delivery.
[/body/p[@paraId=5AD5CA57]] · Durable operation tracking.
[/body/p[@paraId=56E98D92]] · Duplicate-message handling.
[/body/p[@paraId=235C875E]] · Heartbeats and capability reporting.
[/body/p[@paraId=243990A3]] · Explicit timeouts and acknowledgements.
[/body/p[@paraId=771A51E0]] · Safe reconnect and recovery behavior.
[/body/p[@paraId=4DF0343D]] · Authorization checks at both backend and bridge.
[/body/p[@paraId=6DF8C9AE]] Proposed initial choice: use authenticated outbound polling from each Windows bridge to the backend. This avoids requiring the backend to initiate an inbound connection to each developer's computer. Polling interval, transport authentication and endpoint schemas remain decisions to finalize.
[/body/p[@paraId=0A5F7254]] 04.10.02 Communication architecture
[/body/p[@paraId=4ABDCA5A]] NEXUS backend
[/body/p[@paraId=2C1667D9]] FastAPI · task orchestrator · policy · PostgreSQL
[/body/p[@paraId=25F15886]] Authenticated bridge protocol
[/body/p[@paraId=1375C035]] Operation delivery · acknowledgements · heartbeat · results
[/body/p[@paraId=0B53BB7B]] Developer PC A
[/body/p[@paraId=77B95CDF]] Windows bridge
[/body/p[@paraId=523C9A5D]] Local tools and filesystem scope
[/body/p[@paraId=383D3A3B]] Developer PCs B and C
[/body/p[@paraId=05A08DDF]] Independent bridges
[/body/p[@paraId=7C3B4483]] Separate identities and credentials
[/body/p[@paraId=227343B7]] Each bridge initiates its connection to the backend. The backend decides whether that authenticated device is eligible to receive an operation. The bridge validates each operation before executing it.
[/body/p[@paraId=37561DD2]] The diagram describes the logical flow. It does not imply that the bridge receives unrestricted commands or that every registered tool is enabled on every device.
[/body/p[@paraId=0E912A37]] 04.10.03 Bridge registration and authentication handshake
[/body/p[@paraId=3741C41D]] Registration and routine authentication should be separate operations. Registering a device creates its identity; authenticating proves that the current bridge possesses the corresponding credential.
[/body/p[@paraId=0CA9A86A]] Proposed registration sequence
[/body/p[@paraId=3E22D10B]] 1. Initiate registration
[/body/p[@paraId=7A23BC36]] 2. An authenticated user requests registration of a new Windows bridge. The backend checks whether the user is allowed to enroll another device.
[/body/p[@paraId=361CF626]] 3. Provision a unique device identity
[/body/p[@paraId=708EBF79]] 4. The backend creates or securely enrolls a device record and establishes a per-device authentication credential. The credential must not be a shared team-wide secret.
[/body/p[@paraId=7EEBB670]] 5. Store the credential securely
[/body/p[@paraId=6A3FF6C8]] 6. The bridge stores its credential using the selected protected Windows storage mechanism. The provisioning workflow must not expose the credential in ordinary logs or command history.
[/body/p[@paraId=4A872ABC]] 7. Authenticate to the backend
[/body/p[@paraId=04BD7F48]] 8. The bridge proves possession of its credential over the selected authenticated transport. A submitted device ID by itself is insufficient.
[/body/p[@paraId=4ADC3409]] 9. Validate registration status
[/body/p[@paraId=0E104780]] 10. The backend verifies the device record, ownership, credential validity and revocation status.
[/body/p[@paraId=4FFF4716]] 11. Report capabilities
[/body/p[@paraId=4C7EA91B]] 12. The bridge reports its protocol version, supported tools and relevant local configuration status.
[/body/p[@paraId=715C12E5]] 13. Enable eligible delivery
[/body/p[@paraId=70724F9A]] 14. The backend makes the device eligible for dispatch only after successful authentication and the required readiness checks.
[/body/p[@paraId=7A9FB6F7]] Registration security rules
[/body/p[@paraId=21124257]] · A bridge must not choose its own authoritative owner or privilege level.
[/body/p[@paraId=5A7C59B1]] · Credentials must be unique per device and independently revocable.
[/body/p[@paraId=0E169FEF]] · A revoked device must not become trusted merely by reconnecting.
[/body/p[@paraId=1D6D8592]] · Re-registration after credential loss must follow a controlled authorization process.
[/body/p[@paraId=06CE1E2B]] · Device registration must not automatically grant access to another user's tasks or files.
[/body/p[@paraId=6521EBFD]] The exact credential format and enrollment handshake remain open until the transport and credential-storage choices are finalized.
[/body/p[@paraId=709CCF26]] 04.10.04 Polling protocol and endpoint responsibilities
[/body/p[@paraId=102D470B]] With polling, the bridge periodically asks the backend whether work is available for its registered device. The backend must never return an operation merely because the request includes a matching device ID.
[/body/p[@paraId=1C96EEF8]] The following routes are proposed logical endpoints; exact HTTP methods and payloads must be agreed in the bridge contract.
[/body/tbl[1]] [Table: 8 rows]
[/body/p[@paraId=4E6FE395]] A possible route family is:
[/body/p[@paraId=3B0273E0]] POST /v1/bridge/session
[/body/p[@paraId=198F4DD9]] POST /v1/bridge/heartbeat
[/body/p[@paraId=703351A5]] PUT  /v1/bridge/capabilities
[/body/p[@paraId=0CE87CCA]] POST /v1/bridge/poll
[/body/p[@paraId=4C0CF661]] POST /v1/bridge/operations/{operation_id}/ack
[/body/p[@paraId=07837F8E]] POST /v1/bridge/operations/{operation_id}/result
[/body/p[@paraId=0B263981]] GET  /v1/bridge/operations/{operation_id}
[/body/p[@paraId=23A3105E]] These are proposed routes, not a frozen API specification. For example, a separate session endpoint may be unnecessary if the selected authentication mechanism authenticates every request directly.
[/body/p[@paraId=163FBF7D]] Polling behavior
[/body/p[@paraId=434AE2ED]] 1. The bridge authenticates.
[/body/p[@paraId=671411C4]] 2. It polls using its authenticated device context.
[/body/p[@paraId=57EA28ED]] 3. The backend verifies device status, eligibility and pending work.
[/body/p[@paraId=797FEC93]] 4. The backend atomically claims an eligible operation for that device.
[/body/p[@paraId=1DD6B866]] 5. The bridge validates the operation and acknowledges receipt.
[/body/p[@paraId=37EF3EA6]] 6. The bridge executes only after its local checks pass.
[/body/p[@paraId=298F7307]] 7. The bridge reports progress or the final outcome.
[/body/p[@paraId=68E47AED]] 8. The backend validates the response and persists the result.
[/body/p[@paraId=242327CA]] An empty poll means no eligible operation is available at that moment. It does not imply that the device has no tasks waiting for approval or blocked by another dependency.
[/body/p[@paraId=5FA33226]] Polling interval
[/body/p[@paraId=46FBC77A]] The interval should be configurable and measured during integration testing. A fixed starting interval is an implementation choice, not yet a confirmed requirement.
[/body/p[@paraId=24FBDF7B]] The design should consider:
[/body/p[@paraId=7B63D132]] · Responsiveness for interactive requests.
[/body/p[@paraId=30B90CCF]] · Load from three concurrently polling devices.
[/body/p[@paraId=395C014B]] · Idle CPU and network usage.
[/body/p[@paraId=697B6AC1]] · Backoff when the backend is unavailable.
[/body/p[@paraId=19B14593]] · Jitter to avoid all devices polling simultaneously.
[/body/p[@paraId=5B381E57]] · Prompt detection of credential revocation and changed capabilities.
[/body/p[@paraId=04C8138C]] The backend must enforce the real dispatch deadline and task state regardless of how frequently the bridge polls.
[/body/p[@paraId=10F5489E]] 04.10.05 Operation delivery, acknowledgement and execution
[/body/p[@paraId=495239BA]] The protocol must distinguish delivery from execution.
[/body/tbl[2]] [Table: 7 rows]
[/body/p[@paraId=4C1158DB]] Acknowledgement requirements
[/body/p[@paraId=4244AE5E]] An acknowledgement should correlate to the exact operation_id, attempt_id and target device. The backend must reject mismatched identifiers or stale attempts according to the protocol rules.
[/body/p[@paraId=265F9250]] An acknowledgement should distinguish at least:
[/body/p[@paraId=0C2069D0]] · Accepted for execution.
[/body/p[@paraId=707540B4]] · Rejected before execution.
[/body/p[@paraId=6D812223]] · Already known or duplicate operation.
[/body/p[@paraId=612B46F9]] · Unable to accept because the bridge is busy or incompatible.
[/body/p[@paraId=3A35B86D]] The precise status names belong in the frozen bridge contract.
[/body/p[@paraId=454C913C]] Why an acknowledgement is not enough
[/body/p[@paraId=63362338]] Suppose the bridge receives a file-search operation, executes it and loses network connectivity before returning the result. The backend cannot conclude that the search failed merely because it did not receive a response.
[/body/p[@paraId=534252EA]] For a read-only search, a controlled retry may be acceptable. For a later write operation, retrying could duplicate an external side effect. The bridge and backend must follow the operation's retry and reconciliation policy rather than applying a universal retry rule.
[/body/p[@paraId=662DD2AC]] 04.10.06 Heartbeats, health and capability reporting
[/body/p[@paraId=32D3D20F]] A heartbeat tells the backend that a bridge recently communicated. It does not prove that every tool works, that the desktop session is available or that a file operation can succeed.
[/body/p[@paraId=4EC3DF34]] Proposed device statuses
[/body/tbl[3]] [Table: 6 rows]
[/body/p[@paraId=369A7BC5]] The exact state names and timeout thresholds remain open. REVOKED must take precedence over a heartbeat: a revoked device must never become usable simply by sending another heartbeat.
[/body/p[@paraId=50A367FC]] Heartbeat contents
[/body/p[@paraId=66A49801]] A heartbeat should contain only the information needed for routing and operations, such as:
[/body/p[@paraId=71AB8D8F]] · Device identity established by authentication.
[/body/p[@paraId=4D927CB5]] · Bridge version and protocol version.
[/body/p[@paraId=378D6E17]] · Timestamp or server-validated contact time.
[/body/p[@paraId=0A91C9E1]] · Current bridge health.
[/body/p[@paraId=6E1A39A6]] · Bounded active-operation summaries, if required for recovery.
[/body/p[@paraId=0676EDC5]] · Capability or configuration version.
[/body/p[@paraId=097187C2]] It should not include document contents, passwords, private memory or unrestricted filesystem listings.
[/body/p[@paraId=4021349E]] Capability reporting
[/body/p[@paraId=3335F6F4]] The bridge reports what it implements and what is locally configured. The backend compares that report with its authoritative tool catalogue.
[/body/p[@paraId=68D0C637]] For example, a bridge might implement search_files but lack a configured directory for that tool. In that case, the tool implementation exists, but the capability is not ready for the corresponding operation.
[/body/p[@paraId=37C293D8]] Capability reporting is advisory. The backend must revalidate capability at dispatch, and the bridge must independently validate the actual operation.
[/body/p[@paraId=365B89D2]] 04.10.07 Duplicate delivery and operation deduplication
[/body/p[@paraId=30BB6462]] Polling can return the same logical operation more than once if acknowledgement or result delivery is interrupted. NEXUS must treat duplicate delivery as a normal failure scenario, not an exceptional impossibility.
[/body/p[@paraId=3B48347B]] Required behavior
[/body/p[@paraId=79EAC4E4]] · The same operation_id and same operation fingerprint must map to the same logical operation.
[/body/p[@paraId=3010F6E5]] · A duplicate delivery must not create a new logical task step.
[/body/p[@paraId=4F324A0D]] · Reuse of an operation ID with different arguments, tool version or target device must be rejected.
[/body/p[@paraId=4191637D]] · An active duplicate should return its known status where possible.
[/body/p[@paraId=64197AD5]] · A completed duplicate should return the known outcome when the bridge has sufficient durable evidence.
[/body/p[@paraId=6DE1CD90]] · An operation with an unresolved external effect must be reconciled before a potentially unsafe retry.
[/body/p[@paraId=41BFB090]] · The backend must persist operation intent before dispatch.
[/body/p[@paraId=31CFD73B]] · The bridge should maintain a durable operation journal if the chosen local persistence design supports it.
[/body/p[@paraId=3D16359A]] The operation fingerprint should represent the normalized tool, schema version, arguments and target device. It must not be used as a substitute for authentication or authorization.
[/body/p[@paraId=6BCD84CE]] Important crash window
[/body/p[@paraId=702C204D]] Consider this sequence:
[/body/p[@paraId=7A92A4C2]] 1. The bridge receives an operation.
[/body/p[@paraId=78B5F737]] 2. The bridge creates an external side effect.
[/body/p[@paraId=5025E062]] 3. The bridge crashes before recording the result.
[/body/p[@paraId=536B70F7]] 4. The bridge restarts and receives the same operation again.
[/body/p[@paraId=5739F3A8]] A deduplication table alone cannot prove whether the external action happened if the crash occurred between steps 2 and 3.
[/body/p[@paraId=55E036A3]] The correct response is to reconcile the external state when possible. If the result remains unknowable, retain UNCERTAIN rather than pretending that exactly-once execution has been achieved.
[/body/p[@paraId=34CFCB6C]] 04.10.08 Disconnects, reconnects and recovery
[/body/p[@paraId=35D351A9]] The bridge protocol must support both short network interruptions and longer outages.
[/body/p[@paraId=00533202]] Backend unavailable
[/body/p[@paraId=11D5F948]] When the backend cannot be reached:
[/body/p[@paraId=405A77A3]] · The bridge stops requesting new operations.
[/body/p[@paraId=2827ACA3]] · It uses bounded exponential backoff with jitter rather than polling continuously.
[/body/p[@paraId=6BBAE2F4]] · It preserves any locally recorded operation journal.
[/body/p[@paraId=6C97F25E]] · It does not invent new work or change task ownership.
[/body/p[@paraId=04A0A407]] · It reports unresolved operations after reconnection.
[/body/p[@paraId=05F2C4DB]] The bridge should not queue arbitrary new user instructions locally in the first release. Durable task acceptance and scheduling remain backend responsibilities.
[/body/p[@paraId=355F3468]] Bridge unavailable
[/body/p[@paraId=4201CEE5]] When a target bridge becomes unavailable:
[/body/p[@paraId=5CCF8E57]] · The backend stops new dispatches to that device.
[/body/p[@paraId=673467F3]] · Tasks that have not dispatched remain recoverable according to their state.
[/body/p[@paraId=4287CFF2]] · Operations already dispatched are assessed for possible execution.
[/body/p[@paraId=6561AA81]] · The backend does not silently move the task to another developer's computer.
[/body/p[@paraId=1969067D]] · The user receives a truthful status and a useful next step.
[/body/p[@paraId=6358AD3E]] Reconnection procedure
[/body/p[@paraId=7E6CDC08]] 1. Reauthenticate the bridge.
[/body/p[@paraId=4B9B5E07]] 2. Verify the device is still registered and not revoked.
[/body/p[@paraId=4DE57AAE]] 3. Verify protocol and capability compatibility.
[/body/p[@paraId=5C04D07F]] 4. Exchange bounded information about unresolved operations.
[/body/p[@paraId=35823048]] 5. Compare the bridge's operation journal with backend records.
[/body/p[@paraId=1DA7E5E8]] 6. Reconcile dispatched or uncertain operations.
[/body/p[@paraId=2A5A7B04]] 7. Revalidate current permissions and approvals.
[/body/p[@paraId=56FA4FC2]] 8. Resume only operations that are safe and eligible to continue.
[/body/p[@paraId=0DCB9BE2]] A stale approval must not become valid merely because a device reconnects. Similarly, restoring a backend database backup must not silently reinstate a revoked device.

[/body/p[@paraId=55990D8F]] The protocol must define distinct time limits for different stages.

[/body/p[@paraId=61778794]] These timeouts are related but not interchangeable. For example, an acknowledgement timeout does not establish that execution failed.
[/body/p[@paraId=310DC6A0]] Lease requirements
[/body/p[@paraId=596CDC12]] If the backend uses leases to coordinate workers:
[/body/p[@paraId=188D6CE1]] · Claims must be atomic.
[/body/p[@paraId=6A024CDA]] · Claims should include a worker identity and generation or fencing token.
[/body/p[@paraId=5533AF41]] · A stale worker must not overwrite a newer authoritative task state.
[/body/p[@paraId=74F73E97]] · Lease expiry does not prove that an old bridge operation stopped.
[/body/p[@paraId=54ABFCEA]] · Any external side effect that might have happened must be reconciled before unsafe retry.
[/body/p[@paraId=2A848B15]] · Expired dispatch deadlines must be enforced when the bridge receives or executes the request.
[/body/p[@paraId=2F3845A2]] Actual timeout values should be selected after measuring normal network behavior, tool durations and recovery scenarios.
[/body/p[@paraId=31A68868]] 04.10.10 Security requirements for bridge communication
[/body/p[@paraId=5BF9B88A]] The transport must not be considered trustworthy merely because it runs on a private LAN.
[/body/p[@paraId=7B007A22]] Required controls:
[/body/p[@paraId=51A2AAE2]] · Authenticate each bridge independently.
[/body/p[@paraId=0EAFB648]] · Validate the intended target device on every operation.
[/body/p[@paraId=2D7585E4]] · Authorize the user, task, tool and operation before dispatch.
[/body/p[@paraId=1B168D71]] · Reject revoked credentials and unsupported security-sensitive protocol versions.
[/body/p[@paraId=18D8335D]] · Protect against replay and duplicate side effects.
[/body/p[@paraId=12320523]] · Apply payload-size and request-rate limits.
[/body/p[@paraId=209A2254]] · Keep PostgreSQL and the model endpoint private to their intended consumers.
[/body/p[@paraId=3CAF931C]] · Avoid public internet exposure and port forwarding for the initial deployment.
[/body/p[@paraId=06766E34]] · Use TLS where required by the LAN threat model and selected authentication scheme.
[/body/p[@paraId=7C301F16]] · Ensure that the bridge does not expose an inbound listener unless the architecture explicitly requires one.
[/body/p[@paraId=673FE121]] A polling design can reduce inbound firewall complexity, but it does not eliminate the need for authenticated transport, server-side authorization or local validation.

[/body/p[@paraId=63290724]] 04.10.12 Required integration tests
[/body/p[@paraId=1B98BB1C]] The initial protocol must pass these scenarios:
[/body/p[@paraId=3920B383]] · A registered bridge authenticates and reports its capabilities.
[/body/p[@paraId=12350D61]] · An unregistered bridge cannot poll for work.
[/body/p[@paraId=73A4F6B1]] · A bridge cannot receive another device's operation.
[/body/p[@paraId=3ED2DDBE]] · An offline device does not cause silent rerouting.
[/body/p[@paraId=0600BB96]] · Repeated polling does not create duplicate task steps.
[/body/p[@paraId=64AA9DB8]] · Repeated delivery of the same operation ID does not blindly repeat a side effect.
[/body/p[@paraId=35430DAF]] · Reusing an operation ID with different arguments is rejected.
[/body/p[@paraId=275CD7ED]] · A lost acknowledgement is handled without assuming execution did not occur.
[/body/p[@paraId=2D40ED7E]] · A lost result after execution triggers reconciliation.
[/body/p[@paraId=492ED686]] · A backend restart recovers eligible and uncertain operations correctly.
[/body/p[@paraId=453FB342]] · A revoked bridge remains blocked after reconnecting.
[/body/p[@paraId=2245395C]] · An expired approval cannot authorize dispatch.
[/body/p[@paraId=44DB9447]] · Unsupported protocol or tool versions fail closed.
[/body/p[@paraId=00DE02CC]] · Three bridges can communicate concurrently without mixing task ownership.
[/body/p[@paraId=3B476FFE]] · Heartbeat and diagnostics do not expose secrets or private file contents.
[/body/p[@paraId=5EBCAECA]] These tests must be automated where practical, with real Windows integration tests for bridge behavior and PostgreSQL tests for durable coordination.

[/body/p[@paraId=3732FB48]] · The bridge communication schema is versioned and tested.

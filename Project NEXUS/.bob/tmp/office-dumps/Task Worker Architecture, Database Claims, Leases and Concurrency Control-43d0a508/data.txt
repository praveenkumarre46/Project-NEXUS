[/body/p[@paraId=3D36E228]] 04.11.01 Purpose
[/body/p[@paraId=7F250FB0]] Once NEXUS accepts tasks from multiple developers, it must coordinate their execution without duplicating work, corrupting task state or exhausting shared resources.
[/body/p[@paraId=411B9106]] Consider three users submitting tasks at nearly the same time. A worker might claim a task, the backend might restart, and a second worker might attempt to claim the same task. Meanwhile, the original Windows bridge may still be executing the first operation.
[/body/p[@paraId=7A4D5F88]] NEXUS must prevent a stale worker from changing authoritative state, avoid unsafe duplicate execution and preserve enough information to recover after failures.
[/body/p[@paraId=77233D98]] Recommended initial approach: use PostgreSQL for durable task coordination, atomic worker claims, bounded leases and generation-based fencing. Do not introduce Redis or a separate message broker unless measured requirements justify the additional infrastructure.
[/body/p[@paraId=0A1E1D0E]] 04.11.02 Worker architecture
[/body/p[@paraId=735F481C]] The worker is the backend component responsible for progressing a persisted task through planning, authorization, dispatch, result handling and recovery.
[/body/p[@paraId=362D049E]] FastAPI API
[/body/p[@paraId=50E6782B]] Authenticates requests and persists accepted tasks
[/body/p[@paraId=1D144AF7]] PostgreSQL task store
[/body/p[@paraId=3FED86E4]] Authoritative task state, steps, claims and operation intent
[/body/p[@paraId=14F4E26C]] Worker A
[/body/p[@paraId=5C2080EE]] Claim, execute and record
[/body/p[@paraId=2064A7D1]] Worker B
[/body/p[@paraId=5FCBD047]] Claim independent eligible work
[/body/p[@paraId=2BC487A8]] Operation dispatcher
[/body/p[@paraId=684F8B38]] Checks policy and sends operations to the authenticated target bridge
[/body/p[@paraId=2FF2EED8]] The worker may initially run within the backend application process. Its logical responsibilities should remain separate from HTTP request handlers so it can later move into a separate process if load or reliability measurements require that change.
[/body/p[@paraId=379EB3E0]] A worker is not a security authority. It must load authoritative task and device data and apply the required authorization and policy checks before dispatch.
[/body/p[@paraId=7998F1C3]] 04.11.03 Separate task eligibility from resource availability
[/body/p[@paraId=0CEAE985]] A task should execute only when two independent conditions hold.
[/body/p[@paraId=39992C99]] Task eligibility answers whether the task is allowed and ready to progress:
[/body/p[@paraId=329B9A0F]] · The task is in an eligible state.
[/body/p[@paraId=4C587D8E]] · Required dependencies are complete.
[/body/p[@paraId=195C1FD9]] · The target device is registered and authorized.
[/body/p[@paraId=7BB98D5D]] · Required approvals are valid.
[/body/p[@paraId=7B1FF833]] · The tool and protocol are supported.
[/body/p[@paraId=52969CA4]] · The task has not been cancelled or otherwise invalidated.
[/body/p[@paraId=1B23C865]] Resource availability answers whether execution capacity is available:
[/body/p[@paraId=3B2C97E5]] · A worker slot is available.
[/body/p[@paraId=46C5E8CD]] · The target device can accept work.
[/body/p[@paraId=7B6C4F0D]] · The model runtime has capacity, if needed.
[/body/p[@paraId=493C9BE9]] · Database capacity is available.
[/body/p[@paraId=27614D2A]] · The task remains within configured concurrency and resource limits.
[/body/p[@paraId=5D0BD366]] A task can be eligible but waiting for a resource. Conversely, an available worker must not execute a task that is unauthorized, awaiting approval or dependent on an unresolved operation.
[/body/p[@paraId=0BB930E3]] This distinction is important because queue position alone must never imply permission to execute.
[/body/p[@paraId=603F386D]] 04.11.04 Atomic task claims
[/body/p[@paraId=6D45AC0D]] Two workers must not independently decide that the same task is available based on separate reads.
[/body/p[@paraId=0BA1B70D]] The claim must be established atomically in PostgreSQL. The implementation can use row locking, conditional updates or another verified PostgreSQL coordination pattern.
[/body/p[@paraId=6A603E19]] Required claim behavior
[/body/p[@paraId=79067E31]] 1. Find an eligible task.
[/body/p[@paraId=3B9A9126]] 2. Atomically claim it, ensuring that another worker cannot obtain the same active claim.
[/body/p[@paraId=559B997F]] 3. Record the worker identity, claim generation and lease expiry.
[/body/p[@paraId=5AE79969]] 4. Confirm that the claim succeeded.
[/body/p[@paraId=614FFEDC]] 5. Only then begin the work associated with that claim.
[/body/p[@paraId=71974C94]] 6. Verify claim ownership before committing subsequent authoritative state transitions.
[/body/p[@paraId=0279D225]] If a worker loses the claim, it must stop making authoritative state changes for that task.

[/body/p[@paraId=1C079C22]] Transaction boundaries
[/body/p[@paraId=17365FFC]] The database transaction should cover the claim and its associated state change, not the entire task execution.
[/body/p[@paraId=6A5D91C2]] Do not keep a PostgreSQL transaction open while waiting for:
[/body/p[@paraId=3AED8C8F]] · A model to generate a plan.
[/body/p[@paraId=7A217EE0]] · A Windows bridge to respond.
[/body/p[@paraId=79DA8A66]] · A file operation to complete.
[/body/p[@paraId=65C25BCC]] · A human to approve an operation.
[/body/p[@paraId=48ABA5A9]] Long-running transactions can hold locks, consume connections and delay unrelated users.
[/body/p[@paraId=24A93813]] 04.11.05 Leases and fencing stale workers
[/body/p[@paraId=005602D8]] A lease is a time-bounded claim. It helps NEXUS detect a worker that has stopped making progress, but it does not prove that the worker or its external operation has stopped.
[/body/p[@paraId=1B3BF47F]] For example, a worker may pause temporarily, lose its database connection and continue executing a delayed request to the Windows bridge after its lease expires.
[/body/p[@paraId=61F7F5F5]] A second worker must not assume that the old operation is harmless.
[/body/p[@paraId=40B7ED74]] Fencing rule
[/body/p[@paraId=76A4AEAF]] Each successful new claim should receive a higher claim generation. Authoritative task-state updates must verify that the worker still owns the current generation.
[/body/p[@paraId=530101CA]] Conceptually:
[/body/p[@paraId=4B0F82DD]] · Worker A claims task generation 7.
[/body/p[@paraId=53F85997]] · Worker A stalls and its lease expires.
[/body/p[@paraId=430ABCB7]] · Recovery evaluates the task and assigns generation 8 when a new claim is safe.
[/body/p[@paraId=489555B0]] · Worker A later resumes with generation 7.
[/body/p[@paraId=40BCAB96]] · Its stale state updates are rejected.
[/body/p[@paraId=25EED85B]] A fencing token protects backend state only if every relevant state-changing path checks it. It does not automatically stop an external Windows operation already in progress.
[/body/p[@paraId=7AF2EC3F]] Lease-expiry behavior
[/body/p[@paraId=7C9D3C47]] When a lease expires, NEXUS should:
[/body/p[@paraId=0F206A12]] 1. Mark the claim as stale or eligible for recovery.
[/body/p[@paraId=7731B41C]] 2. Inspect the task and operation records.
[/body/p[@paraId=0CB9BE1B]] 3. Determine whether the worker had dispatched an external operation.
[/body/p[@paraId=7E66100B]] 4. Reconcile any operation that might have executed.
[/body/p[@paraId=70A03E04]] 5. Revalidate authorization, device status and approval.
[/body/p[@paraId=06A23C10]] 6. Reclaim work only when doing so is safe.
[/body/p[@paraId=2B750FBA]] Never treat lease expiry as proof that an external side effect did not occur.
[/body/p[@paraId=6DB43580]] The lease duration, heartbeat interval and renewal policy should be selected using measured task and network durations, with bounded renewal behavior.
[/body/p[@paraId=25F4A9C6]] 04.11.06 Concurrency limits and shared resource protection
[/body/p[@paraId=207F5ED0]] NEXUS shares a backend, PostgreSQL database and initially a designated computer for local AI inference. Each resource needs its own concurrency control.
[/body/tbl[2]] [Table: 8 rows]
[/body/p[@paraId=24B67FDB]] Exact numerical limits remain open. They should be based on host measurements rather than arbitrary claims about how much the machine can handle.
[/body/p[@paraId=0458D47B]] Initial resource policy
[/body/p[@paraId=2BBBE416]] · A single user's burst of tasks must not indefinitely starve other eligible users.
[/body/p[@paraId=059B69B4]] · Device-specific work must remain bound to its intended device.
[/body/p[@paraId=4966B171]] · The model runtime should have a configurable concurrency limit.
[/body/p[@paraId=0D288883]] · Work waiting for a human approval must not occupy an active execution slot indefinitely.
[/body/p[@paraId=2FA316D7]] · A task waiting for an offline device should not consume a worker slot while it waits.
[/body/p[@paraId=18E71074]] · If the durable queue reaches its configured capacity, new submissions must receive a clear response rather than disappearing.
[/body/p[@paraId=66CCE4A3]] · A task must not be reported as durably accepted if PostgreSQL is unavailable and the task has not been persisted.
[/body/p[@paraId=4F454F62]] A fair scheduler, such as round-robin selection among eligible users, is a reasonable starting proposal. The exact fairness policy should be kept simple until the team has measured real contention.
[/body/p[@paraId=12302677]] 04.11.07 Task dispatch and worker responsibilities
[/body/p[@paraId=77977455]] A worker should process one bounded unit of work at a time and persist meaningful progress between stages.
[/body/p[@paraId=013DD7C9]] The recommended sequence is:
[/body/p[@paraId=295AD4BF]] 1. Claim an eligible task or step.
[/body/p[@paraId=6DB47898]] 2. Load its authoritative owner, target device and current state.
[/body/p[@paraId=1A82D3FF]] 3. Verify that required dependencies have completed.
[/body/p[@paraId=7DDE9115]] 4. Obtain a structured plan or the next deterministic operation.
[/body/p[@paraId=11E000ED]] 5. Validate the operation against the registry and schema.
[/body/p[@paraId=4FBAEF47]] 6. Recheck authorization and policy.
[/body/p[@paraId=62E68979]] 7. Verify approval if required.
[/body/p[@paraId=501942FA]] 8. Persist operation intent.
[/body/p[@paraId=210F3327]] 9. Dispatch to the intended bridge.
[/body/p[@paraId=67256B2C]] 10. Record acknowledgement and subsequent execution evidence.
[/body/p[@paraId=40EE989C]] 11. Verify the outcome and persist the result.
[/body/p[@paraId=4A9CA5B4]] 12. Release the claim or progress to the next eligible step.
[/body/p[@paraId=73CEC4F3]] Each stage needs defined error and recovery behavior. A generic exception handler that marks every error as FAILED is not sufficient.

[/body/p[@paraId=71340F3B]] 04.11.08 Cancellation and worker shutdown
[/body/p[@paraId=107CAF55]] Cancellation is a request to stop further work, not proof that all activity has stopped.
[/body/p[@paraId=128B2BE7]] When cancellation is requested, NEXUS should:
[/body/p[@paraId=6173F6C7]] · Persist the cancellation request.
[/body/p[@paraId=00826233]] · Prevent new steps from being dispatched.
[/body/p[@paraId=0BE2DBE6]] · Signal an active worker where practical.
[/body/p[@paraId=05FC231D]] · Apply the tool's cancellation behavior if supported.
[/body/p[@paraId=128B3F39]] · Reconcile any operation that may already have executed.
[/body/p[@paraId=0110092C]] · Preserve completed side effects and report partial results.
[/body/p[@paraId=472916A9]] · Mark the task CANCELLED only when the cancellation conditions are satisfied.
[/body/p[@paraId=144A0BA4]] If the operation cannot be interrupted safely, the task may remain in a cancellation-pending or recovery state until its outcome is established. Whether cancellation-pending is represented as a separate persisted state or an explicit cancellation flag remains a design decision.
[/body/p[@paraId=2E474DFA]] Graceful shutdown
[/body/p[@paraId=1D81684F]] When the backend is stopping:
[/body/p[@paraId=118A4744]] 1. Stop accepting new worker claims.
[/body/p[@paraId=03AE3862]] 2. Stop dispatching new operations.
[/body/p[@paraId=256B550B]] 3. Allow a bounded period for active work to finish.
[/body/p[@paraId=0D260757]] 4. Persist known outcomes and outstanding recovery information.
[/body/p[@paraId=42B072A7]] 5. Leave unresolved external operations recoverable.
[/body/p[@paraId=647C08A1]] 6. Close database connections cleanly.
[/body/p[@paraId=1032226D]] A forced process termination can still occur. Startup recovery must not assume that graceful shutdown completed.
[/body/p[@paraId=269422A5]] 04.11.09 Backpressure, admission control and fairness
[/body/p[@paraId=26844A20]] The system needs two separate limits:
[/body/p[@paraId=14A4E329]] · Admission control: determines whether a new task can be durably accepted.
[/body/p[@paraId=13B2093B]] · Execution scheduling: determines when an accepted task can run.
[/body/p[@paraId=4FFC568D]] A task may be accepted and queued while execution capacity is temporarily unavailable, provided queue capacity and persistence are healthy.
[/body/p[@paraId=29D325EB]] If the queue is full, NEXUS should return a stable capacity error. It must not create an in-memory-only task and report it as durable.
[/body/p[@paraId=76C3C421]] Fair scheduling proposal
[/body/p[@paraId=49A5792D]] For the initial three-user deployment:
[/body/p[@paraId=4A0E95EA]] 1. Exclude tasks that are blocked, cancelled, unauthorized or waiting for approval.
[/body/p[@paraId=6207A7CC]] 2. Group eligible work by user.
[/body/p[@paraId=07D4B057]] 3. Select users fairly, initially using round-robin scheduling.
[/body/p[@paraId=7E799637]] 4. Apply per-user and per-device concurrency limits.
[/body/p[@paraId=5DBE8748]] 5. Select an eligible task for the chosen user.
[/body/p[@paraId=23B99400]] 6. Revalidate eligibility before dispatch.
[/body/p[@paraId=5AF70749]] This avoids a user who submits many tasks monopolizing the shared model or worker pool.
[/body/p[@paraId=3FD24E8D]] Priority classes and priority aging can be added later if real workloads demonstrate starvation. User-provided urgency must not bypass security checks, capacity limits or approval requirements.
[/body/p[@paraId=2CEDEE93]] 04.11.10 Worker observability
[/body/p[@paraId=28284276]] Each worker should emit structured events that allow the team to reconstruct what happened without logging sensitive content.

[/body/p[@paraId=0E5506CC]] · worker_id and claim generation

[/body/p[@paraId=41EA3B3C]] · Dispatch, acknowledgement and result timestamps
[/body/p[@paraId=6E2A2E7A]] · Retry and recovery classification
[/body/p[@paraId=5F7DD0E1]] · Stable error code
[/body/p[@paraId=6AFFC5B7]] · Execution duration
[/body/p[@paraId=6858EDBB]] Useful metrics include:
[/body/p[@paraId=1070E425]] · Active workers and active claims.
[/body/p[@paraId=118DEDD3]] · Queue length and queue wait time.
[/body/p[@paraId=506D62A3]] · Claim conflicts and expired leases.

[/body/p[@paraId=65F14908]] Do not use task IDs, user IDs or filesystem paths as unrestricted metric labels. Keep high-cardinality details in appropriately protected logs or persisted task records.

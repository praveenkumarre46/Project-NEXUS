[/body/p[@paraId=6BADAF3D]] 04.07.01 Purpose
[/body/p[@paraId=35DE9B84]] Section 04.06 defined the first end-to-end workflow. This section converts it into concrete work items that three developers can implement in parallel without inventing incompatible interfaces.
[/body/p[@paraId=6F3B8462]] The milestone is still limited to authenticated task submission, durable task tracking and scoped Windows file search. The objective is to prove the shared architecture before introducing live AI planning or additional computer-control capabilities.
[/body/p[@paraId=2E6DFEE9]] Planning rules
[/body/p[@paraId=1C7D7CBA]] 1. Freeze shared contracts before parallel implementation.
[/body/p[@paraId=0C5A0775]] 2. Assign one primary owner to each work item.
[/body/p[@paraId=3944E63F]] 3. Keep database migrations and API changes reviewable.
[/body/p[@paraId=171A8744]] 4. Require tests with each feature, not after integration.
[/body/p[@paraId=12F6F579]] 5. Integrate working code continuously instead of waiting for all branches to finish.
[/body/p[@paraId=09F1A218]] 6. Do not mark a task complete because its code exists; its acceptance tests must pass.

[/body/p[@paraId=06D1B140]] 04.07.05 WP-03 — Windows bridge and scoped file search
[/body/p[@paraId=668D5D31]] Owner: Developer 2
[/body/p[@paraId=053CFBCA]] Deliverables
[/body/tbl[3]] [Table: 9 rows]
[/body/p[@paraId=740C102F]] Implementation boundaries
[/body/p[@paraId=070A0803]] The bridge owns local filesystem access. It must not trust a path simply because the backend or AI supplied it.
[/body/p[@paraId=040C68EE]] The bridge should accept a logical directory ID such as nexus_test_documents, resolve it through local configuration and validate the operation before accessing the filesystem.
[/body/p[@paraId=198B7035]] It must not provide a generic shell or PowerShell execution endpoint.
[/body/p[@paraId=403067BB]] Required failure tests
[/body/p[@paraId=14A1CF9A]] · A request targets an unknown directory ID.
[/body/p[@paraId=271EE5E7]] · A relative path attempts to escape the configured directory.
[/body/p[@paraId=6FE356B8]] · A link or junction points outside the permitted scope.
[/body/p[@paraId=20A5F1D0]] · The bridge receives an unsupported protocol version.
[/body/p[@paraId=373845F0]] · A request arrives after device revocation.
[/body/p[@paraId=2A646C7B]] · A duplicate operation arrives after a prior successful search.
[/body/p[@paraId=6C3EBFE2]] · The bridge restarts with an operation whose outcome was not recorded.
[/body/p[@paraId=391C87FE]] Exit gate: the Windows bridge can authenticate, execute a bounded search and return a structured result without allowing access outside its configured scope.
[/body/p[@paraId=55F8CD01]] 04.07.06 WP-04 — Deterministic planner and tool proposals
[/body/p[@paraId=024BE3DD]] Owner: Developer 3
[/body/p[@paraId=201EF8EF]] This work package prepares the boundary between natural-language understanding and tool execution without making the first vertical slice depend on an AI model.
[/body/p[@paraId=67FC3B8B]] Deliverables
[/body/tbl[4]] [Table: 7 rows]
[/body/p[@paraId=028DED36]] Implementation boundaries
[/body/p[@paraId=238479ED]] Developer 3 does not own authorization or task state. The planner may propose a search operation, but the backend must independently validate the tool, arguments, target device, resource scope and policy.
[/body/p[@paraId=062E0C4E]] For the initial milestone, use explicit supported request forms or a small deterministic parser. Do not label arbitrary text matching as general natural-language understanding.
[/body/p[@paraId=31399929]] The live model adapter, model benchmark and hybrid memory retrieval remain separate deliverables.
[/body/p[@paraId=7A1B3B9A]] Exit gate: the backend receives a valid, structured search proposal—or a clear unsupported/clarification result—and never needs to trust the planner as an authority.
[/body/p[@paraId=71CCEC75]] 04.07.07 WP-05 — Orchestration, integration and recovery
[/body/p[@paraId=56AB57BA]] Primary owner: Developer 1. Supporting owners: Developers 2 and 3.
[/body/p[@paraId=26C2F603]] This package joins the components into the actual vertical workflow.
[/body/p[@paraId=2F983DBF]] Deliverables
[/body/p[@paraId=2632FC5E]] 1. Persist the task before confirming acceptance.
[/body/p[@paraId=69EC8432]] 2. Claim eligible work using the agreed concurrency-control mechanism.
[/body/p[@paraId=75D74895]] 3. Obtain a validated search proposal.
[/body/p[@paraId=38FC9949]] 4. Validate authorization and policy before dispatch.
[/body/p[@paraId=2021BFDA]] 5. Persist operation intent before contacting the bridge.
[/body/p[@paraId=16877B1C]] 6. Dispatch the operation to the specified registered device.
[/body/p[@paraId=68B185BC]] 7. Validate response identity and correlate it with the operation.
[/body/p[@paraId=3D301A86]] 8. Persist the result and update task state through legal transitions.
[/body/p[@paraId=3059CACB]] 9. Expose task progress and results through the API.
[/body/p[@paraId=7B87BEED]] 10. Reconcile uncertain operations rather than blindly replaying them.
[/body/p[@paraId=293ACCC5]] Integration checkpoints
[/body/p[@paraId=3F2E28DB]] 11. Checkpoint A — API to database
[/body/p[@paraId=22B80A69]] 12. Submit and retrieve a task without executing a Windows operation.
[/body/p[@paraId=51EDEF98]] 13. Checkpoint B — Bridge contract
[/body/p[@paraId=17BA1CC9]] 14. Send a test operation to the correct bridge and reject an unauthorized target.
[/body/p[@paraId=63708F4A]] 15. Checkpoint C — Complete search
[/body/p[@paraId=759CD802]] 16. Submit a request from the CLI and obtain persisted search results from Windows.
[/body/p[@paraId=1696A100]] 17. Checkpoint D — Failure recovery
[/body/p[@paraId=1290F8E3]] 18. Interrupt dispatch or result delivery and demonstrate safe reconciliation.
[/body/p[@paraId=5060B8A8]] 19. Checkpoint E — Multi-user isolation
[/body/p[@paraId=33336CE3]] 20. Execute concurrent tasks for different users and devices without mixing ownership, context or results.
[/body/p[@paraId=5494556F]] Required tests
[/body/p[@paraId=77E42F20]] · Backend restart before dispatch.
[/body/p[@paraId=2CF70784]] · Bridge disconnect after dispatch.
[/body/p[@paraId=662C01A7]] · Lost response after a successful operation.
[/body/p[@paraId=1B9DF5A2]] · Duplicate submission during concurrent requests.
[/body/p[@paraId=104501DB]] · Two workers competing for the same task.
[/body/p[@paraId=11E7A834]] · Device revocation while a task is queued.
[/body/p[@paraId=1E7B083F]] · Database failure while recording the result.
[/body/p[@paraId=7D42C6E5]] · Cancellation racing with dispatch.
[/body/p[@paraId=00EB31C7]] Exit gate: the end-to-end workflow passes both successful and failure scenarios, with no false completion claims.
[/body/p[@paraId=0E81FDE6]] 04.07.08 WP-06 — CLI, multi-user validation and release evidence
[/body/p[@paraId=6ECC83C1]] Owner: shared; Developer 1 coordinates integration.
[/body/p[@paraId=6722E40E]] Deliverables
[/body/p[@paraId=11AC9D30]] · Task submission command with explicit device targeting.

[/body/p[@paraId=17E01053]] · Result display and stable error messages.

[/body/p[@paraId=4790C290]] · JSON output suitable for scripts.
[/body/p[@paraId=2B0082E9]] · End-to-end test instructions and recorded results.

[/body/p[@paraId=0BED20AD]] Illustrative CLI usage:

[/body/p[@paraId=7616586F]] The CLI must distinguish between a task being accepted, running, waiting for a device, succeeding, failing and having an uncertain outcome. Stopping --watch must not cancel the underlying task.

[/body/p[@paraId=4A0D5CF5]] Each work item should be small enough to review independently.

[/body/p[@paraId=1AFBA173]] · Compatibility considerations for other developers.

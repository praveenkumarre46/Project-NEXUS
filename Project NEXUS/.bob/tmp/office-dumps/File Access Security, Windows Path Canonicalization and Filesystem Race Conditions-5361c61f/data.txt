[/body/p[@paraId=1E814BF4]] 03.32.1 Purpose
[/body/p[@paraId=38F9AFEF]] NEXUS must be able to search files, read documents and create files on each developer's Windows 11 computer without giving the AI unrestricted access to the filesystem.
[/body/p[@paraId=661D6A80]] This is more complicated than checking whether a path starts with an approved directory. Windows supports drive-letter paths, UNC network paths, case-insensitive path comparisons in common configurations, symbolic links, junctions, reparse points, alternate path representations and files that can change between validation and use.
[/body/p[@paraId=37CE20D2]] A path that appears to be inside an approved workspace may resolve somewhere else. A file that was safe to access during validation may be replaced before the operation executes.
[/body/p[@paraId=67991C6C]] Core design rule: the Windows bridge owns filesystem access and enforces the configured local boundaries. The backend and AI planner must not be trusted to supply safe absolute paths.
[/body/p[@paraId=4778682E]] This section builds on the existing NEXUS decisions:
[/body/p[@paraId=7B49EBB7]] · Filesystem tools run in the native Windows bridge.
[/body/p[@paraId=1583C79E]] · Tools accept logical directory IDs instead of unrestricted absolute paths.
[/body/p[@paraId=389EE919]] · The AI cannot grant itself permissions or expand a directory's scope.
[/body/p[@paraId=2AB8590F]] · File creation is create-only by default.
[/body/p[@paraId=394A1856]] · Uncertain file operations require reconciliation before retry.
[/body/p[@paraId=31F06844]] · Each developer's device remains an independent execution target.
[/body/p[@paraId=07A8A01E]] 03.32.02 Security objectives
[/body/p[@paraId=279B6E23]] The filesystem layer must:
[/body/p[@paraId=61621982]] 1. Restrict every operation to configured directory scopes.
[/body/p[@paraId=1384AF3B]] 2. Prevent traversal outside the permitted scope.
[/body/p[@paraId=3855F989]] 3. Handle Windows path representations consistently.
[/body/p[@paraId=21853014]] 4. Account for links, junctions and other reparse-point behavior.
[/body/p[@paraId=7485BBDA]] 5. Avoid validation-to-use race conditions where practical.
[/body/p[@paraId=48EEC73B]] 6. Reject unauthorized UNC/network paths unless explicitly supported.
[/body/p[@paraId=00DE5379]] 7. Enforce file size, search depth, result count and execution-time limits.
[/body/p[@paraId=7274FB74]] 8. Prevent silent overwrite during file creation.
[/body/p[@paraId=3DE52D9E]] 9. Avoid leaking private paths or file contents into logs.
[/body/p[@paraId=5C19A827]] 10. Return a clear, auditable outcome when safety cannot be established.
[/body/p[@paraId=3D8039B8]] The security boundary must remain effective even when a request contains malicious text, a document attempts prompt injection, the model invents a path, or a bridge receives a malformed operation.
[/body/p[@paraId=3A5DA4B7]] 03.32.03 Filesystem trust boundaries
[/body/p[@paraId=5BFFD0B8]] AI planner
[/body/p[@paraId=52520F67]] Proposes a logical directory ID and operation
[/body/p[@paraId=26D1905E]] Backend validation and policy
[/body/p[@paraId=1472CBC1]] Validates the registered tool, user, device, scope and approval
[/body/p[@paraId=76418C89]] Windows bridge security boundary
[/body/p[@paraId=7456F42C]] Resolves local configuration, canonicalizes paths and revalidates the operation
[/body/p[@paraId=7CA507FD]] Windows filesystem
[/body/p[@paraId=40274E91]] Actual file and directory operations under the bridge process's OS permissions
[/body/p[@paraId=429EFEFC]] The operating system's permissions remain an important final boundary. NEXUS should run the bridge as the normal logged-in user, not as an administrator, unless a separately justified requirement exists.
[/body/p[@paraId=37FD366A]] Application-level authorization does not replace Windows access controls, and Windows access controls do not replace NEXUS's own user and device authorization.

[/body/p[@paraId=1166EF2E]] 03.32.05 Windows path canonicalization
[/body/p[@paraId=3487F6F0]] Canonicalization means converting a path into a consistent representation suitable for comparison and further validation. It does not, by itself, prove that accessing the path is safe.
[/body/p[@paraId=5789C9E4]] Windows paths can have different textual representations that refer to the same location or behave differently under the filesystem's rules. For example:
[/body/p[@paraId=63F32501]] · C:\NexusWorkspace\Reports
[/body/p[@paraId=25F60323]] · C:\NexusWorkspace\Reports\..\Reports
[/body/p[@paraId=6546D146]] · c:\nexusworkspace\reports
[/body/p[@paraId=0648008D]] A naive string comparison can produce incorrect authorization decisions.
[/body/p[@paraId=1CF8D5FF]] Required validation sequence
[/body/p[@paraId=6391C6F2]] For each filesystem operation, the bridge should:
[/body/p[@paraId=4D955F65]] 1. Validate the tool's arguments and the logical directory ID.
[/body/p[@paraId=2AED4A65]] 2. Resolve the directory ID using trusted local configuration.
[/body/p[@paraId=5FFF6241]] 3. Reject disallowed path forms and unsupported namespaces.
[/body/p[@paraId=0FC256F5]] 4. Normalize and resolve the requested relative path using Windows-aware filesystem APIs.
[/body/p[@paraId=44FBC629]] 5. Confirm that the resolved target remains inside the permitted scope.
[/body/p[@paraId=5B9BC721]] 6. Inspect relevant filesystem attributes and link behavior.
[/body/p[@paraId=171BF510]] 7. Perform the operation using the safest available filesystem primitive.
[/body/p[@paraId=5B71362F]] 8. Verify the result and record its outcome.
[/body/p[@paraId=45041512]] The sequence is a security design, not a guarantee that ordinary path-string checks prevent every attack. Steps involving the actual filesystem must account for changes between validation and use.
[/body/p[@paraId=23C6717B]] Why string-prefix checks are insufficient
[/body/p[@paraId=5C9A3C74]] Consider an approved directory:
[/body/p[@paraId=32FB6E9B]] C:\NexusWorkspace
[/body/p[@paraId=38CE03AD]] A prefix check could mistakenly treat this path as inside the workspace:
[/body/p[@paraId=4EC25A89]] C:\NexusWorkspace-Private
[/body/p[@paraId=0ED679F1]] The second path begins with the same characters but is a different directory.
[/body/p[@paraId=7BD8B977]] Comparing path components is better than checking raw string prefixes, but even component-aware comparisons are insufficient if symbolic links, junctions or other filesystem indirections can redirect access.
[/body/p[@paraId=6A110B3E]] Required rule: do not authorize filesystem access solely because a normalized path string starts with an approved root.
[/body/p[@paraId=01C17520]] 03.32.06 Symbolic links, junctions and reparse points
[/body/p[@paraId=42BC2652]] Windows supports filesystem features that can redirect a path to another location. These include symbolic links, junctions and other reparse-point types.
[/body/p[@paraId=4E6FEB1A]] Suppose NEXUS is authorized to read:
[/body/p[@paraId=517D8EBB]] C:\NexusWorkspace
[/body/p[@paraId=4B5600A8]] Inside that directory, an entry named External points to a location outside the workspace. Searching recursively through External could expose files the user never intended to include in the approved scope.
[/body/p[@paraId=0C69A12C]] Proposed MVP policy
[/body/p[@paraId=050F3084]] · Do not follow directory links or junctions during recursive search by default.
[/body/p[@paraId=241B5B4D]] · Inspect relevant filesystem attributes before traversing entries.
[/body/p[@paraId=350B902D]] · Do not assume that a link's displayed path determines the location it ultimately accesses.
[/body/p[@paraId=51E53081]] · Reject or safely skip entries whose target cannot be validated.
[/body/p[@paraId=5CC48297]] · Apply equivalent restrictions to file reads and file creation.
[/body/p[@paraId=75AB85F0]] · Treat unsupported reparse-point types as unsafe until their behavior is explicitly handled and tested.
[/body/p[@paraId=1A9BAA67]] A simple policy of not following links is easier to reason about than attempting to support every Windows filesystem redirection feature during the first release.
[/body/p[@paraId=0F85A2C1]] However, merely checking a path's attributes and then reopening it by name can still leave a race window. Stronger protection requires safer operating-system APIs and handle-based checks where practical.
[/body/p[@paraId=516F3788]] The precise implementation should be selected and tested against the actual Windows environment rather than assumed from a generic path-normalization example.

[/body/p[@paraId=7E75E02D]] 03.32.08 The time-of-check-to-time-of-use problem
[/body/p[@paraId=072561D2]] A time-of-check-to-time-use (TOCTOU) race occurs when a resource changes after validation but before an operation uses it.
[/body/p[@paraId=124432D6]] Example:
[/body/p[@paraId=77ECA6C5]] 1. The bridge validates that C:\NexusWorkspace\report.txt is inside an approved directory.
[/body/p[@paraId=5F75C8C3]] 2. Another process replaces an intermediate directory or changes a link.
[/body/p[@paraId=598C759F]] 3. The bridge opens the path by name.
[/body/p[@paraId=1227FA29]] 4. The actual operation reaches a different location than the one validated.
[/body/p[@paraId=236A42D1]] The same class of issue can affect file creation if an attacker changes a directory entry after validation.
[/body/p[@paraId=25115128]] Required engineering response
[/body/p[@paraId=3C9D5875]] · Keep path resolution and access as closely coupled as practical.
[/body/p[@paraId=0CDD3A1B]] · Prefer safe handle-based operations when available.
[/body/p[@paraId=527E68C6]] · Revalidate security-relevant attributes at the point of access.
[/body/p[@paraId=4D9A7626]] · Avoid following untrusted links or reparse points.
[/body/p[@paraId=291D104F]] · Use restrictive directory permissions to reduce the ability of other processes to manipulate the workspace.
[/body/p[@paraId=64C7FB63]] · For writes, use an operation that fails if the destination already exists rather than a separate existence check followed by an ordinary write.
[/body/p[@paraId=52A00E3E]] · If the bridge cannot establish that the operation stayed within scope, reject it or report an uncertain outcome.
[/body/p[@paraId=15311846]] No portable path-validation helper should be treated as a complete defense against filesystem races. The team must verify the guarantees of the actual Windows APIs and libraries selected.
[/body/p[@paraId=45C38604]] 03.32.09 Safe file creation
[/body/p[@paraId=231A89E7]] The initial create_file tool must be designed to avoid accidental data loss and unauthorized writes.
[/body/p[@paraId=70E1C02C]] Required behavior
[/body/p[@paraId=324351C3]] 1. Accept an approved logical directory ID and a relative destination name.
[/body/p[@paraId=313400D1]] 2. Validate path components and reject unsupported path syntax.
[/body/p[@paraId=1DF8668E]] 3. Resolve and verify the destination against the configured workspace.
[/body/p[@paraId=6D074D83]] 4. Enforce content size and encoding constraints.
[/body/p[@paraId=47912D6E]] 5. Create the destination only if it does not already exist.
[/body/p[@paraId=183C7665]] 6. Avoid overwriting existing files, following an unsafe link or creating files outside the approved root.
[/body/p[@paraId=5D79B105]] 7. Verify the resulting file and report its outcome.
[/body/p[@paraId=03BCA08D]] 8. Record enough operation metadata to support recovery without logging the entire document content.
[/body/p[@paraId=257FD0F7]] Existing destination
[/body/p[@paraId=4F5B76D3]] If the destination already exists, return a clear conflict result. Do not silently append to, truncate or replace it.
[/body/p[@paraId=40AE4F55]] A future version could offer an explicitly approved replacement operation, but it should be a separate, reviewed capability or operation mode with its own risk classification and approval semantics.
[/body/p[@paraId=12136D3B]] Atomicity considerations
[/body/p[@paraId=07BF24AA]] A create-if-absent filesystem operation is preferable to this unsafe pattern:
[/body/p[@paraId=5C0FC293]] # Illustrative unsafe pattern.if not destination.exists():    destination.write_text(content)
[/body/p[@paraId=68F06866]] Another process can create or replace the destination between the check and the write.
[/body/p[@paraId=5826FBD9]] The implementation should use an appropriate create-new/exclusive-create primitive and verify its semantics on the target filesystem. Temporary-file-and-rename strategies also require care: replacement semantics and atomicity depend on the specific API and filesystem.
[/body/p[@paraId=5F198CDF]] Lost response after a successful write
[/body/p[@paraId=6DC1EAD5]] If a file was created but the bridge crashed before reporting success, NEXUS must not blindly retry.
[/body/p[@paraId=27A9042A]] The backend should reconcile the operation using its stable operation ID, the bridge's operation journal and available filesystem evidence. If it cannot reliably establish whether the intended operation completed, the result remains uncertain and the user is informed.
[/body/p[@paraId=3DB23EEF]] File existence alone may not prove that a particular operation created the file, especially if another process could have created it independently.
[/body/p[@paraId=5E4B8F88]] 03.32.10 Safe file search
[/body/p[@paraId=70975726]] The search_files tool must have explicit limits so that a single request cannot trigger an unbounded scan of a user's computer.
[/body/p[@paraId=53AFFDFA]] Proposed limits include:
[/body/p[@paraId=11423464]] · Permitted directory IDs only.
[/body/p[@paraId=17FB03D3]] · Maximum traversal depth.
[/body/p[@paraId=12DD28D4]] · Maximum number of returned results.
[/body/p[@paraId=2ACE7F5F]] · Maximum execution duration.
[/body/p[@paraId=7D16878A]] · Explicit rules for hidden and system files.
[/body/p[@paraId=145E1887]] · No recursive traversal through links or junctions by default.
[/body/p[@paraId=6A654406]] · Bounded query length and supported matching behavior.
[/body/p[@paraId=335A069A]] · Cancellation checks during long-running searches.
[/body/p[@paraId=132EEF94]] · Restricted error reporting that does not expose unrelated local paths.
[/body/p[@paraId=18714470]] The numeric limits should be established through performance testing on the team's actual hardware.
[/body/p[@paraId=3F1C6968]] Search result contract
[/body/p[@paraId=790421BC]] A result should include enough information to identify and later reference a permitted file without exposing unnecessary local information.
[/body/p[@paraId=72CD8E69]] Proposed fields:
[/body/p[@paraId=0168E215]] · A stable result identifier for the current operation.
[/body/p[@paraId=09308FF5]] · A display name.
[/body/p[@paraId=738999F7]] · A path relative to the configured logical directory.
[/body/p[@paraId=3E1CEA89]] · Relevant metadata, such as size and modification time.
[/body/p[@paraId=39529FE9]] · A status for inaccessible, skipped or unsupported entries when appropriate.
[/body/p[@paraId=7484D4E7]] Absolute paths should not be sent to the AI unless there is a specific, reviewed reason. A relative path is generally sufficient for planning a follow-up read.
[/body/p[@paraId=4420A113]] Search consistency
[/body/p[@paraId=60133AA1]] A filesystem can change during a search. A returned entry may be renamed or removed before the next operation.
[/body/p[@paraId=410499CA]] Therefore, a search result is not a permanent authorization grant. Before reading a selected file, the bridge must resolve and validate it again under the current permissions and filesystem state.
[/body/p[@paraId=7567D3A8]] 03.32.11 Safe document reading
[/body/p[@paraId=628E49AD]] The read_document tool needs protections against oversized files, malformed documents and hostile content.
[/body/p[@paraId=1E40DB13]] Input checks
[/body/p[@paraId=73C21B1E]] · The file must be inside the authorized scope.
[/body/p[@paraId=253BBC91]] · The file must be of an explicitly supported format.
[/body/p[@paraId=7A12F059]] · File size and extraction time must be bounded.
[/body/p[@paraId=5893530F]] · Unsupported or malformed documents must produce controlled errors.
[/body/p[@paraId=7EDA9CB8]] · Extraction must not execute macros, scripts or embedded active content.
[/body/p[@paraId=464272C0]] · Extracted content must be treated as untrusted data by the planner.
[/body/p[@paraId=510C7DD3]] · Output length must be bounded before sending content to the model.
[/body/p[@paraId=262AC865]] Plain text, PDF and DOCX were previously identified as candidate formats. The exact MVP format list is still open; the team should not promise support until the corresponding extraction libraries and security tests are selected.
[/body/p[@paraId=66994368]] Content and privacy
[/body/p[@paraId=51514023]] The bridge should not log full document content by default. Diagnostics can record the operation ID, logical directory ID, safe file reference, duration, extraction outcome and bounded error code.
[/body/p[@paraId=65BD82A4]] Document content must not be allowed to:
[/body/p[@paraId=57B123C6]] · Grant access to another directory.
[/body/p[@paraId=06062968]] · Change the tool registry.
[/body/p[@paraId=65045069]] · Approve a pending operation.
[/body/p[@paraId=0DC80FDD]] · Change the target device.
[/body/p[@paraId=73C2AB36]] · Override the application's policy.
[/body/p[@paraId=336FF59A]] · Cause NEXUS to execute arbitrary commands.
[/body/p[@paraId=679A5B4E]] These restrictions are enforced by the application and bridge, not by relying on the model to ignore malicious instructions.

[/body/p[@paraId=6D973D60]] 03.32.13 Testing strategy
[/body/p[@paraId=21CF971B]] The team should use isolated temporary directories and dedicated test fixtures. Tests must never rely on modifying a developer's real documents.
[/body/p[@paraId=16B988B5]] Required test groups
[/body/p[@paraId=5F516AD0]] Path authorization
[/body/p[@paraId=7191E870]] Test path traversal, sibling-directory prefix confusion, case differences, relative paths, alternate path forms, unknown directory IDs and unauthorized roots.
[/body/p[@paraId=4EA257C0]] Links and filesystem redirection
[/body/p[@paraId=72BF009B]] Test symbolic links, junctions, reparse points and links introduced after initial validation. Verify that unsupported or unsafe targets are not accessed.
[/body/p[@paraId=7123D99A]] Safe writes
[/body/p[@paraId=32FAA762]] Test existing destinations, simultaneous create attempts, invalid names, oversized content, interrupted writes and a successful write with a lost response.
[/body/p[@paraId=08BBEA96]] Search and document extraction
[/body/p[@paraId=367CDA18]] Test depth and result limits, inaccessible entries, unsupported formats, oversized documents, malformed files and prompt injection inside document contents.
[/body/p[@paraId=5D9473C6]] Recovery and concurrency
[/body/p[@paraId=13DE4BF0]] Test files changed after search, bridge restarts, duplicate operation delivery, concurrent writers, timeouts and reconciliation after an uncertain result.
[/body/p[@paraId=7D635066]] Important acceptance scenarios
[/body/p[@paraId=236E639B]] · A traversal attempt cannot read or write outside the approved directory.
[/body/p[@paraId=64C2E475]] · A sibling directory with a similar name cannot bypass scope validation.
[/body/p[@paraId=5A04873B]] · A prohibited link cannot expose files outside the workspace.
[/body/p[@paraId=60C0F9BC]] · An existing file is never overwritten by create_file.
[/body/p[@paraId=2E926D28]] · Two concurrent create requests cannot both claim successful creation of the same new destination.
[/body/p[@paraId=312A58FE]] · A file changed after search is revalidated before reading.
[/body/p[@paraId=18A51D0E]] · Search limits are enforced even when the model requests a larger result set.
[/body/p[@paraId=7CDFF2AA]] · Malicious document text cannot alter permissions or enable tools.
[/body/p[@paraId=1808CEF8]] · A timeout after a possible write does not trigger an unsafe blind retry.
[/body/p[@paraId=1E5460F5]] · Diagnostics do not leak document contents, credentials or unauthorized absolute paths.
[/body/p[@paraId=4152558E]] Run these tests on Windows itself, because filesystem behavior and APIs must be validated on the actual execution platform. WSL2-only Linux tests are not a substitute for Windows bridge integration tests.

[/body/p[@paraId=547AFFF8]] 03.32.16 Definition of done
[/body/p[@paraId=76AE07EF]] · Filesystem tools accept logical directory IDs rather than arbitrary model-provided absolute paths.
[/body/p[@paraId=6023C29F]] · Directory mappings and permitted operations are configured locally and enforced by the bridge.
[/body/p[@paraId=44AF88FB]] · Canonicalization, scope validation and link handling are documented and tested.
[/body/p[@paraId=7C0561B1]] · Search and extraction have enforceable resource limits.
[/body/p[@paraId=759C149A]] · File creation does not overwrite an existing destination by default.
[/body/p[@paraId=655FDDD9]] · Race conditions and uncertain outcomes have explicit handling.
[/body/p[@paraId=76AA31CC]] · Windows-specific security tests pass.
[/body/p[@paraId=4CB48BBE]] · The bridge does not require administrator privileges for ordinary MVP operations.
[/body/p[@paraId=3E963B09]] · Private content and sensitive local paths are not unnecessarily exposed in logs or model context.
[/body/p[@paraId=3D825E9F]] · Unsafe or ambiguous filesystem operations fail closed.
[/body/p[@paraId=2FB6E059]] Recommended engineering decision: keep filesystem access deliberately narrow for the first release. Use locally configured logical directory IDs, bounded search and reading, and create-only writes. Treat path resolution as a security-sensitive operation rather than a string-processing task.

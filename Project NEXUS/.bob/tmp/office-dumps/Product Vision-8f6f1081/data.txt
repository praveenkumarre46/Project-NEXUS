[/body/p[@paraId=6358BEB5]] Product vision
[/body/p[@paraId=5E99244E]] NEXUS is a personal AI computer companion that combines two equally important capabilities:
[/body/p[@paraId=3412BC86]] • Computer automation: Understand requests and safely execute useful, multi-step tasks on a user's Windows 11 computer.
[/body/p[@paraId=4DD721A4]] • Context awareness: Maintain useful knowledge of the user's projects, preferences, ongoing tasks, and prior interactions to provide relevant assistance.
[/body/p[@paraId=51327CEC]] NEXUS should progress beyond a chatbot. It should plan, act through explicitly permitted tools, observe outcomes, recover from supported failures, and explain what happened.

[/body/p[@paraId=0AC2E1D8]] 1.3 Updated system concept
[/body/p[@paraId=715ED41D]] The proposed system has three main layers.
[/body/p[@paraId=5DFC42A9]] Per-user Windows computer
[/body/p[@paraId=31963D6A]] Terminal client · Windows bridge · Restricted local tools
[/body/p[@paraId=6BBED430]] NEXUS backend
[/body/p[@paraId=12DF169F]] Authentication · Permissions · Planning · Task execution · API
[/body/p[@paraId=13739BDE]] Shared services
[/body/p[@paraId=552F5FC6]] PostgreSQL · Task history · User memory · Model adapter · Audit records
[/body/p[@paraId=157A1DC0]] Conceptual architecture only. The physical placement of services is not yet finalized.
[/body/p[@paraId=08D41B08]] Why this separation matters
[/body/p[@paraId=4C1DB1EF]] If a user asks NEXUS to summarize a document on their own laptop, the backend must not accidentally read a similarly named document on another teammate's machine.
[/body/p[@paraId=2A400839]] We therefore need to distinguish:
[/body/p[@paraId=758849D8]] • User identity: Who issued the request?
[/body/p[@paraId=0885ED31]] • Device identity: Which registered computer is the intended target?
[/body/p[@paraId=14E91EE2]] • Authorization: Which actions may that user perform on that device?
[/body/p[@paraId=4E5292C7]] • Task ownership: Who can view, cancel, or inspect the resulting task?
[/body/p[@paraId=50D5AB7E]] • Execution location: Which computer actually performs the operation?
[/body/p[@paraId=3020DA64]] These must be enforced by the backend and Windows bridge, not left to the AI model's judgment.

[/body/p[@paraId=35E8E206]] 1.6 Architectural implications
[/body/p[@paraId=4233CCC2]] The new decisions introduce several requirements that were less important in the original single-host proposal.
[/body/p[@paraId=5842FA61]] A. Device registration and trust
[/body/p[@paraId=1C8C3528]] Every Windows bridge needs a way to register, authenticate, identify its device, and establish which user is allowed to invoke it. A device must not trust arbitrary requests simply because they originate on the local network.
[/body/p[@paraId=49DFF1CF]] B. Distributed task execution
[/body/p[@paraId=2F4C6778]] The backend and a user's Windows computer can become disconnected independently. Tasks need explicit states for pending, running, waiting for approval, succeeded, failed and cancelled, plus carefully defined recovery behavior.
[/body/p[@paraId=212A3532]] C. Multi-tenant data isolation
[/body/p[@paraId=6B478765]] Conversations, memories, tasks, approvals and device records must be scoped to the right user. Database constraints and authorization checks should reinforce one another.
[/body/p[@paraId=32220B6E]] D. Network and deployment topology
[/body/p[@paraId=5F1D376D]] A local-network deployment needs authenticated communication, firewall rules, appropriate transport security, and a strategy for clients reconnecting after a laptop sleeps or changes networks.
[/body/p[@paraId=7EE440D6]] E. AI and computer capabilities must be decoupled
[/body/p[@paraId=159855B2]] The model proposes plans and tool arguments; backend policy checks authorize them; the bridge executes only supported operations. We should be able to replace the model without rewriting the computer integration.

[/body/p[@paraId=038CE995]] 04.08.01 Purpose
[/body/p[@paraId=4E37C6D0]] The three developers will implement different parts of NEXUS, but those parts must agree on the exact shape and meaning of the data they exchange.
[/body/p[@paraId=0784D5BE]] For example, the backend cannot safely interpret a bridge response if one developer uses success, another uses completed, and a third treats a timeout as a failure that can always be retried.
[/body/p[@paraId=35BC101D]] This section establishes the rules for freezing shared contracts before implementation expands.
[/body/p[@paraId=30A7E005]] Objective: every component must agree on identifiers, required fields, valid states, error meanings, authorization boundaries, version compatibility and failure behavior.
[/body/p[@paraId=48126F9A]] The contract freeze applies to the first vertical slice. It does not mean that every future NEXUS API or tool must be designed now.
[/body/p[@paraId=5ACE2244]] 04.08.02 Contract ownership
[/body/tbl[1]] [Table: 6 rows]
[/body/p[@paraId=6689AD8E]] The accountable owner maintains the contract, examples and tests. Other developers must approve changes that affect their consumers.
[/body/p[@paraId=7A43FFF3]] A contract must not be changed unilaterally after another component has implemented against it.
[/body/p[@paraId=74AFF1D0]] 04.08.03 Contract layers
[/body/p[@paraId=3AA74068]] NEXUS should maintain distinct contracts for distinct boundaries.
[/body/p[@paraId=3D7C76E6]] 1. Public API
[/body/p[@paraId=72DCC9EA]] CLI ↔ FastAPI
[/body/p[@paraId=4FC06500]] Authentication, requests, task status, approvals, results and errors.
[/body/p[@paraId=0D63A260]] 2. Internal application
[/body/p[@paraId=40D3BB04]] Services ↔ orchestrator and policy
[/body/p[@paraId=29B66EC8]] Validated domain objects, state transitions and authorization decisions.
[/body/p[@paraId=1CCE35EB]] 3. Planner
[/body/p[@paraId=477FE4E4]] AI or deterministic planner → backend
[/body/p[@paraId=4C40082F]] Structured proposals and clarification results; never authoritative permission decisions.
[/body/p[@paraId=01A96015]] 4. Bridge protocol
[/body/p[@paraId=320D6CFF]] Backend ↔ Windows bridge
[/body/p[@paraId=5E1956DB]] Device identity, operation envelope, deadlines, responses and protocol compatibility.
[/body/p[@paraId=54074170]] 5. Tool contract
[/body/p[@paraId=2C27D04C]] Registry ↔ tool implementation
[/body/p[@paraId=50241150]] Arguments, results, resource limits, risk metadata, retries and verification.
[/body/p[@paraId=095881EA]] These layers may share schema definitions where appropriate, but they should not collapse into one giant schema. In particular, a planner proposal is not a bridge command, and a bridge response is not itself proof that the overall task succeeded.

[/body/p[@paraId=79A1B479]] The initial contract should define these identifiers consistently:
[/body/tbl[2]] [Table: 11 rows]
[/body/p[@paraId=4099E70C]] Rules:
[/body/p[@paraId=474E063A]] · Identifiers are opaque to consumers; they must not encode permissions.
[/body/p[@paraId=631F45DE]] · The authenticated identity determines task ownership.
[/body/p[@paraId=0881F641]] · A client-generated request ID is not an authentication credential.
[/body/p[@paraId=51E70674]] · An operation ID is not proof of authorization.
[/body/p[@paraId=37D7CCDD]] · Timestamps use UTC in ISO 8601 format.
[/body/p[@paraId=461D3F40]] · Missing, null, empty and default values must have documented, distinct meanings where relevant.
[/body/p[@paraId=43886064]] · IDs used for correlation must remain consistent across retries of the same logical operation.
[/body/p[@paraId=565D43A7]] The exact ID format—UUID or another suitable opaque identifier—is still an implementation decision.
[/body/p[@paraId=0D4FB331]] 04.08.05 Public task API schemas
[/body/p[@paraId=4B402820]] The following examples establish the intended contract semantics. They are proposed examples, not final Pydantic models or a generated OpenAPI specification.
[/body/p[@paraId=494C5B1E]] A. Task submission request
[/body/p[@paraId=68C6A5D5]] {
[/body/p[@paraId=1E83CB7E]]   "client_request_id": "client-generated-unique-id",
[/body/p[@paraId=098775FF]]   "target_device_id": "registered-device-id",
[/body/p[@paraId=64371EE6]]   "request": "Find files containing the word design"
[/body/p[@paraId=38C20BAA]] }
[/body/p[@paraId=2177C9FB]] Required fields:
[/body/p[@paraId=6450F3FB]] · client_request_id: enables duplicate-submission detection.
[/body/p[@paraId=3C83A3F3]] · target_device_id: explicit destination device.
[/body/p[@paraId=271EB7AE]] · request: user-requested task description.
[/body/p[@paraId=260D76E6]] The backend must derive user_id from the authenticated session. It must not accept a client-supplied owner as authoritative.
[/body/p[@paraId=1E51FE3E]] B. Task acceptance response
[/body/p[@paraId=5C3DEAC8]] {
[/body/p[@paraId=088F3495]]   "task_id": "task-id",
[/body/p[@paraId=6CD4EC70]]   "status": "QUEUED",
[/body/p[@paraId=2DEE1293]]   "request_id": "request-correlation-id",
[/body/p[@paraId=7FA0697D]]   "created_at": "2026-10-22T12:00:00Z"
[/body/p[@paraId=493EAD36]] }
[/body/p[@paraId=5462CFC5]] The response means the task has been durably accepted. It does not mean execution has started or completed.
[/body/p[@paraId=4A4A40AE]] If persistence fails before the task can be accepted, the API must not return a successful acceptance response.
[/body/p[@paraId=1C096F04]] C. Task status response
[/body/p[@paraId=2A2C89F8]] {
[/body/p[@paraId=5C56FFD4]]   "task_id": "task-id",
[/body/p[@paraId=7F7ADC12]]   "target_device_id": "registered-device-id",
[/body/p[@paraId=379AE129]]   "status": "RUNNING",
[/body/p[@paraId=04D55698]]   "created_at": "2026-10-22T12:00:00Z",
[/body/p[@paraId=75D5958D]]   "updated_at": "2026-10-22T12:00:02Z",
[/body/p[@paraId=513F5F40]]   "steps": [
[/body/p[@paraId=32B2872C]]     {
[/body/p[@paraId=20976386]]       "step_id": "step-id",
[/body/p[@paraId=3C95F85D]]       "tool_name": "search_files",
[/body/p[@paraId=36C4C855]]       "status": "RUNNING"
[/body/p[@paraId=17CEE73B]]     }
[/body/p[@paraId=35591F28]]   ],
[/body/p[@paraId=25E3A50E]]   "error": null
[/body/p[@paraId=6A15BEF5]] }
[/body/p[@paraId=02684D9B]] The final schema should distinguish required and optional fields, and define whether embedded steps are complete or only a summary. A dedicated steps endpoint can return detailed step history without making every task-status response excessively large.
[/body/p[@paraId=09BBA7C3]] D. Error response
[/body/p[@paraId=560CAEBB]] {
[/body/p[@paraId=66D9B772]]   "error": {
[/body/p[@paraId=2646012D]]     "code": "DEVICE_UNAVAILABLE",
[/body/p[@paraId=536CC927]]     "message": "The selected device is currently unavailable.",
[/body/p[@paraId=0A249EFE]]     "request_id": "request-correlation-id",
[/body/p[@paraId=415DC430]]     "retryable": true
[/body/p[@paraId=7BE70461]]   }
[/body/p[@paraId=03B03572]] }
[/body/p[@paraId=1A985EC5]] The retryable field is informational. It must not authorize an unsafe retry of an external operation. The client must follow the operation-specific recovery policy.
[/body/p[@paraId=0E949E2F]] 04.08.06 Canonical task and step states
[/body/p[@paraId=1A47401C]] Use one canonical set of state names across persistence, application services and API responses. Any different naming required by a transport must be translated at that boundary.
[/body/p[@paraId=551AD083]] Task states

[/body/p[@paraId=514967CA]] The last three are terminal states. A terminal task must not silently return to an active state.
[/body/p[@paraId=30F1E6A3]] Step states
[/body/tbl[4]] [Table: 11 rows]
[/body/p[@paraId=7E250E69]] DISPATCHED is not equivalent to RUNNING, and UNCERTAIN is not equivalent to FAILED.
[/body/p[@paraId=30626A99]] Contract freeze rules
[/body/p[@paraId=3B3A56EA]] · The orchestrator owns authoritative state transitions.
[/body/p[@paraId=536E63B0]] · The AI planner cannot set execution status.
[/body/p[@paraId=568F9B7D]] · The bridge reports evidence and outcomes, but cannot directly change the backend's task state.
[/body/p[@paraId=1A9B433E]] · The API cannot bypass transition validation.
[/body/p[@paraId=38976EE9]] · State changes must be persisted before they are reported as authoritative.
[/body/p[@paraId=02304740]] · Invalid transitions return a stable error and leave the persisted state unchanged.
[/body/p[@paraId=7237E191]] The exact handling of an interrupted task and approval expiry must be documented in the state-machine contract before those paths are implemented.
[/body/p[@paraId=68A79C0B]] 04.08.07 Planner proposal contract
[/body/p[@paraId=449B68C2]] The planner returns a proposal that the application must validate. It does not return an executable authorization decision.
[/body/p[@paraId=32F86D3D]] Proposed successful response:
[/body/p[@paraId=785B491C]] {
[/body/p[@paraId=274A43DB]]   "proposal_version": "1",
[/body/p[@paraId=3C7BC9C6]]   "outcome": "PROPOSED",
[/body/p[@paraId=13B9F211]]   "objective": "Find files matching the requested term",
[/body/p[@paraId=5D9987E4]]   "target_device_id": "registered-device-id",
[/body/p[@paraId=26B988D1]]   "steps": [
[/body/p[@paraId=5CFAD14F]]     {
[/body/p[@paraId=4BC3E563]]       "step_id": "proposal-step-1",
[/body/p[@paraId=4F5D81B0]]       "tool_name": "search_files",
[/body/p[@paraId=4101028B]]       "tool_schema_version": "1",
[/body/p[@paraId=15BB3F37]]       "arguments": {
[/body/p[@paraId=4C08D631]]         "directory_id": "nexus_test_documents",
[/body/p[@paraId=2621D6FF]]         "query": "design"
[/body/p[@paraId=755A693E]]       },
[/body/p[@paraId=20A304E7]]       "depends_on": []
[/body/p[@paraId=035AAAAD]]     }
[/body/p[@paraId=0A897852]]   ]
[/body/p[@paraId=2D3A9E49]] }
[/body/p[@paraId=4B9513D8]] The example demonstrates structure only. The application should assign authoritative execution IDs and validate the requested target against the persisted task and authenticated user's permissions.
[/body/p[@paraId=13AE4FEA]] The planner contract must define three outcomes:
[/body/p[@paraId=5714EC1E]] · PROPOSED: a structurally valid proposal is available for further validation.
[/body/p[@paraId=41F61E0A]] · CLARIFICATION_REQUIRED: the request cannot be safely or correctly planned without additional information.
[/body/p[@paraId=31DCAC4E]] · UNSUPPORTED: the requested capability is unavailable or outside the supported scope.
[/body/p[@paraId=662B0A2C]] The planner must not be able to declare an operation approved, remove an approval requirement, assign itself additional permissions, or assert that an external side effect succeeded.
[/body/p[@paraId=127CD98B]] A proposal with an unknown tool, invalid schema or unauthorized target is rejected even if the model claims that it is safe.

[/body/p[@paraId=00E57F31]] The bridge protocol is a security boundary and requires stricter compatibility rules than ordinary internal data structures.

[/body/p[@paraId=720A68A8]]   "task_id": "task-id",
[/body/p[@paraId=1F3FEE7F]]   "step_id": "step-id",
[/body/p[@paraId=5800CF6A]]   "target_device_id": "registered-device-id",
[/body/p[@paraId=06E6EA83]]   "tool_name": "search_files",

[/body/p[@paraId=6E058D72]] Proposed response envelope
[/body/p[@paraId=4E0619BA]] {
[/body/p[@paraId=6A308694]]   "protocol_version": "1",
[/body/p[@paraId=08E14E59]]   "operation_id": "stable-operation-id",
[/body/p[@paraId=2D50309F]]   "attempt_id": "attempt-id",
[/body/p[@paraId=287B2D1B]]   "device_id": "registered-device-id",
[/body/p[@paraId=32B3FC6F]]   "status": "SUCCEEDED",
[/body/p[@paraId=679806FA]]   "result": {
[/body/p[@paraId=48EBE73B]]     "matches": []
[/body/p[@paraId=43C53DD9]]   },
[/body/p[@paraId=12A89D33]]   "error": null
[/body/p[@paraId=49528C30]] }
[/body/p[@paraId=76EFD85A]] The actual result schema belongs to the search_files tool contract. The empty array here is illustrative, not evidence that a search occurred.
[/body/p[@paraId=2CE77A26]] Required response semantics
[/body/p[@paraId=254EE1FE]] · SUCCEEDED: the tool completed and produced a result.
[/body/p[@paraId=355A9D79]] · FAILED: the tool's contract establishes that the operation failed.
[/body/p[@paraId=6FD96BFF]] · REJECTED: validation, authorization or local policy blocked the operation.
[/body/p[@paraId=291B1472]] · RUNNING: the operation remains in progress.
[/body/p[@paraId=55A84D4D]] · UNCERTAIN: the bridge cannot establish the final outcome.
[/body/p[@paraId=40948C78]] Every response must be correlated to the requested operation and attempt. Mismatched IDs, target device or unsupported protocol versions must not be accepted as successful execution.
[/body/p[@paraId=5313698C]] If the bridge executes a side effect but fails to record its result, recovery must reconcile the operation. The protocol cannot promise exactly-once execution for arbitrary Windows operations.
[/body/p[@paraId=748F00CE]] 04.08.09 Canonical error catalogue
[/body/p[@paraId=20B7F80E]] Error codes should describe stable categories of failure, not implementation-specific exception names.
[/body/tbl[5]] [Table: 16 rows]
[/body/p[@paraId=5A25683C]] The catalogue should define which component can emit each code, whether it is terminal, whether a retry is meaningful, and what recovery procedure applies.
[/body/p[@paraId=445C49EB]] Avoid exposing stack traces, SQL details, secrets or sensitive local paths in public error responses.
[/body/p[@paraId=1604A810]] 04.08.10 Schema validation and compatibility rules
[/body/p[@paraId=63D91463]] NEXUS needs a consistent schema-validation approach across the API, planner, bridge and tools. Pydantic is a proposed choice for Python-side validation; the team should confirm it when selecting the dependency baseline.
[/body/p[@paraId=65109721]] Rules for the first release
[/body/p[@paraId=124E1829]] 1. Validate incoming data at each trust boundary.
[/body/p[@paraId=172A972F]] 2. Reject missing required fields and invalid types.
[/body/p[@paraId=25CC2E40]] 3. Apply explicit length, count and payload-size limits.
[/body/p[@paraId=11BBDC46]] 4. Reject unknown tool names and unsupported security-sensitive fields.
[/body/p[@paraId=429604ED]] 5. Do not silently reinterpret an unknown enum value or protocol version.
[/body/p[@paraId=6866EA76]] 6. Keep optional fields and their defaults documented.
[/body/p[@paraId=14A2277C]] 7. Return stable error codes instead of leaking framework-specific validation output.
[/body/p[@paraId=6AEAAB2C]] 8. Keep the same example payloads in the contract documentation and automated tests.
[/body/p[@paraId=4A97B969]] Not every future additive field must require a new major version. However, any change that alters authorization, operation identity, result meaning, retry safety or state transitions requires explicit compatibility review.
[/body/p[@paraId=0D95755B]] 04.08.11 Versioning policy
[/body/p[@paraId=4BC75019]] NEXUS has several independently versioned boundaries.
[/body/tbl[6]] [Table: 7 rows]
[/body/p[@paraId=2DD8D048]] Version numbers are not interchangeable. For example, a bridge protocol update does not automatically mean that every tool schema must change.
[/body/p[@paraId=58A9D9EE]] Compatibility requirements
[/body/p[@paraId=49987B79]] · Components must advertise or establish the versions they support.
[/body/p[@paraId=0C08ECAF]] · Unsupported security-sensitive versions fail closed.
[/body/p[@paraId=3E26E640]] · A tool schema change must consider queued and in-flight tasks created under the previous schema.
[/body/p[@paraId=29560D36]] · Rolling back application code must not reinterpret an already-dispatched operation using different arguments.
[/body/p[@paraId=34C3E147]] · Contract changes require updated fixtures and compatibility tests.
[/body/p[@paraId=2D556C61]] · Version removal requires a documented migration or deprecation plan.
[/body/p[@paraId=5CA0128A]] For the first vertical slice, avoid elaborate version-negotiation machinery. Explicit versions and a clear fail-closed rule are sufficient until a real compatibility need emerges.

[/body/p[@paraId=0F4D932C]] 04.08.13 Contract freeze procedure
[/body/p[@paraId=70CE11B0]] The initial contracts are considered frozen when the following steps are complete:
[/body/p[@paraId=1E23A5C3]] 1. Draft: each owner publishes schemas, examples, error behavior and unresolved decisions.
[/body/p[@paraId=56C9A1E5]] 2. Consumer review: the developers implementing dependent components verify that the contract is sufficient.
[/body/p[@paraId=20ACCF98]] 3. Test fixtures: valid, invalid and failure-case examples are committed.
[/body/p[@paraId=552F5B46]] 4. Security review: ownership, device targeting, operation identity, approval and retry semantics are checked.
[/body/p[@paraId=2D71FAC0]] 5. Baseline approval: the team records the accepted contract version in the repository.
[/body/p[@paraId=56EB7BEE]] 6. Controlled changes: later modifications include migration impact, affected consumers, tests and backward-compatibility notes.
[/body/p[@paraId=7E18620B]] Freeze means that the team has a reliable starting contract, not that future changes are forbidden.
[/body/p[@paraId=67F03E9E]] Open decisions before implementation
[/body/p[@paraId=26E4EC7E]] · Exact identifier format.
[/body/p[@paraId=157AA9ED]] · Pydantic model organization and strictness settings.
[/body/p[@paraId=333D95C6]] · Bridge transport and authentication mechanism.
[/body/p[@paraId=448F7CC5]] · Exact tool-result and error payload schemas.
[/body/p[@paraId=59B8B05C]] · Approval-expiry and interruption semantics.
[/body/p[@paraId=38C4204B]] · Unknown-field behavior for each boundary.
[/body/p[@paraId=20540D82]] · API payload limits and pagination defaults.
[/body/p[@paraId=1B020507]] · How long older bridge and tool schemas must remain supported.
[/body/p[@paraId=29215624]] These decisions should be resolved by the responsible developer with evidence from the architecture, security and integration requirements—not guessed independently.
[/body/p[@paraId=0DFFC17F]] 04.08.14 Definition of done
[/body/p[@paraId=7438B8A1]] · API, planner, bridge and tool contracts are documented separately.
[/body/p[@paraId=140364DB]] · Canonical identifiers and task/step states are agreed.
[/body/p[@paraId=7C798C38]] · Request, response and error examples are committed.
[/body/p[@paraId=307F5CB0]] · Ownership and authorization rules are reflected in the contracts.
[/body/p[@paraId=282B94C8]] · Operation timeouts and uncertain outcomes have explicit semantics.
[/body/p[@paraId=608D4AF1]] · Version compatibility and rejection behavior are documented.
[/body/p[@paraId=7F1DA36F]] · Shared fixtures and contract tests run in CI.
[/body/p[@paraId=69C6D7EC]] · All three developers have reviewed the interfaces they consume.
[/body/p[@paraId=5894389C]] · Unresolved decisions have an owner and closure plan.
[/body/p[@paraId=54047DCA]] Section exit criterion: the team can implement the first vertical slice without inventing incompatible schemas or relying on implicit behavior between components.

[/body/p[@paraId=06425A56]] 03.29.1 Purpose
[/body/p[@paraId=4431074D]] NEXUS must represent task progress precisely enough that the CLI, API, scheduler, AI planner, Windows bridge and recovery logic all agree on what has happened.
[/body/p[@paraId=1262E0A0]] Consider this scenario:
[/body/p[@paraId=64230064]] 1. A user asks NEXUS to create a file.
[/body/p[@paraId=3B8774DC]] 2. The backend records the task and sends the operation to the Windows bridge.
[/body/p[@paraId=732BDEF2]] 3. Windows creates the file successfully.
[/body/p[@paraId=257395DB]] 4. The bridge's response is lost before the backend records the result.
[/body/p[@paraId=0521F1A6]] 5. The backend restarts.
[/body/p[@paraId=2DDD9D1B]] At this point, the file may exist even though the database does not record success. Marking the task as failed and repeating the operation could create a duplicate or overwrite data.
[/body/p[@paraId=6BF64986]] The task state machine must preserve the distinction between what NEXUS knows, what it has requested and what may have happened externally.
[/body/p[@paraId=46BA8A01]] This section defines:
[/body/p[@paraId=61ADC499]] · Legal task and step states.
[/body/p[@paraId=2A3055BA]] · Allowed state transitions.
[/body/p[@paraId=04BA9370]] · Which component is permitted to make each transition.
[/body/p[@paraId=138C5A7A]] · Required persistence and validation.
[/body/p[@paraId=4EE074B3]] · Handling for cancellation, approval, timeouts, retries and recovery.
[/body/p[@paraId=4E486826]] · Invariants that automated tests must enforce.
[/body/p[@paraId=16C9B32C]] The state machine is a proposed formalization of the earlier architecture sections. Exact enum names and schema representations can change during implementation, but the behavioral invariants must remain intact.
[/body/p[@paraId=7B811546]] 03.29.02 State-machine design principles
[/body/p[@paraId=37F7CBB5]] 1. Persist before dispatch. Record execution intent before sending an operation that may cause an external side effect.
[/body/p[@paraId=71C6F99C]] 2. Never infer success from submission. Dispatching an operation does not prove it executed.
[/body/p[@paraId=44C57B7A]] 3. Unknown is a valid outcome. When evidence is insufficient, preserve uncertainty rather than inventing success or failure.
[/body/p[@paraId=1A4E715E]] 4. Enforce transitions centrally. Application services validate state changes; API handlers, AI output and bridge messages must not update arbitrary states directly.
[/body/p[@paraId=43C0643A]] 5. Use transactions for state changes. Concurrent updates must not silently overwrite one another.
[/body/p[@paraId=010839B1]] 6. Separate task state from step state. A task may contain several operations with different outcomes.
[/body/p[@paraId=696C4157]] 7. Make recovery explicit. Restarting a process must not automatically replay every unfinished operation.
[/body/p[@paraId=100C4AF0]] 8. Keep policy independent. A legal state transition does not itself authorize an operation.
[/body/p[@paraId=6C93012B]] 03.29.03 Task lifecycle

[/body/p[@paraId=621E2653]] 03.29.06 Which component may change task state?
[/body/p[@paraId=2554374F]] State ownership must be explicit. Otherwise, individual modules will gradually implement conflicting lifecycle rules.
[/body/tbl[4]] [Table: 9 rows]
[/body/p[@paraId=19811F8C]] The task service and orchestrator should own lifecycle transitions. Other components communicate events or return typed results to that workflow.
[/body/p[@paraId=6AC255E1]] A bridge response is evidence about a local operation. The backend must validate the response's operation ID, task ID, device identity and protocol version before using it to update state.
[/body/p[@paraId=409AB467]] 03.29.07 Transition invariants
[/body/p[@paraId=79325EA6]] An invariant is a rule that must remain true regardless of concurrency, failures or restart.
[/body/p[@paraId=6AF85AA6]] Identity and ownership
[/body/p[@paraId=635C3FE1]] · Every task has exactly one owner and one explicit target device.
[/body/p[@paraId=55D55BB8]] · The task's owner is derived from authenticated identity, not from an untrusted request body.
[/body/p[@paraId=083B167D]] · Only authorized callers may read task status, steps, results or approvals.
[/body/p[@paraId=152DD691]] · A task cannot silently change target devices.
[/body/p[@paraId=72A9F0DF]] · A revoked user or device cannot perform new unauthorized operations.
[/body/p[@paraId=233E8C89]] State correctness
[/body/p[@paraId=2C2F0FFB]] · Only documented transitions are permitted.
[/body/p[@paraId=1A5C532A]] · Every accepted transition is persisted before it is reported as durable.
[/body/p[@paraId=62ECF2A9]] · Terminal states cannot return to active states.
[/body/p[@paraId=13E351D6]] · A task cannot succeed while required steps remain unresolved.
[/body/p[@paraId=3E83379F]] · A task cannot be cancelled while an external effect remains unresolved.
[/body/p[@paraId=447F03D2]] · Partial results remain available even if the overall task fails.
[/body/p[@paraId=269A3EB8]] Execution correctness
[/body/p[@paraId=60A74304]] · Each logical step has a stable operation ID.
[/body/p[@paraId=211EA0CE]] · Every dispatch has a recorded execution intent.
[/body/p[@paraId=3A3A69F7]] · Duplicate delivery cannot create a new logical operation accidentally.
[/body/p[@paraId=39EB3445]] · An expired worker claim does not establish that its operation stopped.
[/body/p[@paraId=649E7DCE]] · Retries follow the tool's retry policy and the known operation outcome.
[/body/p[@paraId=2E03F3E6]] · A timeout never automatically implies failure or permission to repeat a side effect.
[/body/p[@paraId=5CF13B2C]] Approval and authorization
[/body/p[@paraId=4FC4337A]] · Approval applies only to the exact operation, target, scope and parameters that were approved.
[/body/p[@paraId=6838A2F6]] · Expired, rejected or invalidated approval cannot authorize dispatch.
[/body/p[@paraId=4449E5C7]] · Authorization is rechecked immediately before execution.
[/body/p[@paraId=325B6F3C]] · A task's priority cannot override policy.
[/body/p[@paraId=715B7A0E]] · AI-generated output cannot grant permissions or directly mutate lifecycle state.
[/body/p[@paraId=4BE0B64F]] These invariants should be enforced in application code and, where suitable, reinforced with PostgreSQL constraints and conditional updates.
[/body/p[@paraId=059373D6]] 03.29.08 Atomicity and concurrent transitions
[/body/p[@paraId=5703BA32]] Two workers may attempt to claim the same task. A user may cancel a task just as an approval arrives. A bridge result may arrive while recovery is processing an expired claim.
[/body/p[@paraId=058B8CAE]] The state machine must define which operation wins and prevent invalid intermediate states.
[/body/p[@paraId=0586ACAE]] Recommended transaction pattern
[/body/p[@paraId=060D630C]] 1. Start a short database transaction.
[/body/p[@paraId=68A6CC17]] 2. Read or conditionally update the relevant task and step records.
[/body/p[@paraId=510601B9]] 3. Verify the expected current state and claim generation.
[/body/p[@paraId=3550D619]] 4. Verify that the requested transition is legal.
[/body/p[@paraId=7AADD13D]] 5. Update state, timestamps and required event records atomically.
[/body/p[@paraId=4FA79000]] 6. Commit.
[/body/p[@paraId=2BA9073D]] 7. Perform external work only after the required intent has been committed.
[/body/p[@paraId=3FB3E5B7]] A conditional update can enforce the expected state:
[/body/p[@paraId=0345A22E]] UPDATE tasks
[/body/p[@paraId=38A71708]] SET status = 'running',
[/body/p[@paraId=3DAEF00C]]     updated_at = CURRENT_TIMESTAMP
[/body/p[@paraId=2DDA4E51]] WHERE task_id = :task_id
[/body/p[@paraId=40C31FA1]]   AND status = 'queued';
[/body/p[@paraId=35E81DB1]] This is an illustrative fragment, not a complete claim implementation. A production claim also needs appropriate worker ownership, lease or fencing data, concurrency control and verification that exactly one eligible row was claimed.
[/body/p[@paraId=7F164A14]] The application must not assume that a successful SQL statement means it won the claim unless it checks the affected-row count and all required claim conditions.
[/body/p[@paraId=054BC29F]] Cancellation versus approval race
[/body/p[@paraId=71DC2617]] If approval and cancellation happen concurrently, NEXUS must use an atomic state check so only a valid transition wins.
[/body/p[@paraId=70D10E08]] · If cancellation is committed first, the approval cannot restart the task.
[/body/p[@paraId=0273F68C]] · If approval is committed first, cancellation must still prevent subsequent dispatch if it is committed before dispatch authorization.
[/body/p[@paraId=5B0C63DB]] · If the operation has already been dispatched, cancellation must follow the in-flight operation and reconciliation rules.
[/body/p[@paraId=18DFD683]] · If the result is unknown, preserve uncertainty until the operation can be reconciled.
[/body/p[@paraId=000CC987]] The exact serialization mechanism can be finalized during implementation, but these outcomes must remain true.
[/body/p[@paraId=2E33A36D]] 03.29.09 Cancellation is a lifecycle protocol
[/body/p[@paraId=227B5318]] A user pressing Ctrl+C in the CLI may only stop waiting for output. It must not automatically be interpreted as a cancellation request unless the CLI explicitly sends one.
[/body/p[@paraId=43A6D49F]] NEXUS should distinguish these events:
[/body/p[@paraId=2C19B79B]] · WATCH_STOPPED: the client stopped displaying progress.
[/body/p[@paraId=672CB411]] · CANCEL_REQUESTED: a user requested cancellation.
[/body/p[@paraId=25AB1ADD]] · CANCEL_ACCEPTED: the backend accepted the request and is processing it.
[/body/p[@paraId=70509965]] · CANCELLED: the task has reached a confirmed terminal cancellation state.
[/body/p[@paraId=4EB84E36]] Only the last represents a completed cancellation.
[/body/p[@paraId=19FAFD4E]] Cancellation procedure
[/body/p[@paraId=04CFE2A7]] 1. Authenticate the caller and authorize access to the task.
[/body/p[@paraId=4C57FC2E]] 2. Persist the cancellation request or equivalent durable cancellation intent.
[/body/p[@paraId=1478C10F]] 3. Prevent dispatch of new steps.
[/body/p[@paraId=4A6DCA24]] 4. Signal cooperative cancellation to workers and the bridge where supported.
[/body/p[@paraId=3A2B88C8]] 5. Wait for or reconcile in-flight operations.
[/body/p[@paraId=47E90C6F]] 6. Preserve completed effects and partial results.
[/body/p[@paraId=4EB81C66]] 7. Mark the task CANCELLED only when the task is no longer executing and unresolved side effects have been addressed.
[/body/p[@paraId=08346302]] If an operation cannot be stopped and its outcome cannot be determined, the task must remain interrupted or otherwise explicitly unresolved. It must not be marked cancelled merely to satisfy a user-interface expectation.
[/body/p[@paraId=35A3C1E6]] 03.29.10 Approval lifecycle and expiry
[/body/p[@paraId=5D846EC0]] An approval record should have its own lifecycle, separate from the task and step states.
[/body/p[@paraId=59FED163]] Proposed approval decisions:
[/body/p[@paraId=01229D0A]] · PENDING
[/body/p[@paraId=242F1868]] · APPROVED
[/body/p[@paraId=696341B8]] · REJECTED
[/body/p[@paraId=70DB827B]] · EXPIRED
[/body/p[@paraId=2607D17F]] · INVALIDATED
[/body/p[@paraId=2CC131F4]] Approval is not a reusable permission token. It is a decision bound to a specific operation.
[/body/p[@paraId=65546CDF]] The approval record should include:
[/body/p[@paraId=373802FD]] · Approval ID and the task/step it applies to.
[/body/p[@paraId=5FF87B1B]] · Requesting user and authorized decision-maker.
[/body/p[@paraId=3765A9BF]] · Target device and tool identity.
[/body/p[@paraId=6FD73A0E]] · Normalized operation arguments or a securely computed fingerprint.
[/body/p[@paraId=08E7DCA0]] · Relevant resource scope and policy version.
[/body/p[@paraId=639D1409]] · Creation, expiry and decision timestamps.
[/body/p[@paraId=75DDD363]] · Decision and audit correlation ID.
[/body/p[@paraId=297AF392]] Expiry rules
[/body/p[@paraId=3A8152CC]] · Expiry must be checked at decision time and immediately before dispatch.
[/body/p[@paraId=264F376B]] · A late approval must not revive a cancelled task.
[/body/p[@paraId=7B85BCCE]] · A change to the tool, arguments, target, resource scope or relevant policy must invalidate the previous approval when it changes what is being authorized.
[/body/p[@paraId=131B859D]] · Approval must not override a hard prohibition.
[/body/p[@paraId=55E34C7A]] · A new approval request must receive a new identity or clearly versioned approval record.
[/body/p[@paraId=5835493D]] The default approval duration remains an open configuration decision. It must be defined before production use.
[/body/p[@paraId=7260A6FF]] 03.29.11 Recovery after a backend restart
[/body/p[@paraId=52F41DF1]] The backend must not treat every nonterminal task as immediately runnable when it restarts.
[/body/p[@paraId=7B5EFEB7]] Recovery procedure
[/body/p[@paraId=5E5EF1EF]] 1. Load durable state. Find tasks and steps that are nonterminal, dispatched, running or associated with expired claims.
[/body/p[@paraId=6D33C48A]] 2. Classify the interruption. Determine whether work was merely queued, was waiting for approval, was dispatched, or may have produced an external side effect.
[/body/p[@paraId=30CC0D57]] 3. Reconcile external operations. Use the operation ID, bridge's recorded outcome and available local evidence to establish what happened.
[/body/p[@paraId=532E801D]] 4. Revalidate eligibility. Check current user/device status, permissions, approval expiry, policy and task cancellation state.
[/body/p[@paraId=29AD8F94]] 5. Choose a safe next state. Requeue work that is safe to retry, resume confirmed incomplete work, fail unrecoverable work, or preserve uncertainty.
[/body/p[@paraId=2F316FAB]] 6. Persist the recovery result. Record the transition and recovery evidence before continuing execution.

[/body/p[@paraId=330D8882]] 03.29.13 Implementation design
[/body/p[@paraId=01D65DC5]] The recommended implementation is a central transition service with explicit transition rules.
[/body/p[@paraId=19F03656]] Illustrative Python pseudocode:
[/body/p[@paraId=4EC9F8AD]] def transition_task(task, event, context):    # Illustrative pseudocode, not production-ready code.    if task.is_terminal:        raise InvalidTransitionError()    next_state = transition_rules.resolve(        current_state=task.status,        event=event,    )    validate_transition_invariants(        task=task,        next_state=next_state,        context=context,    )    return next_state
[/body/p[@paraId=5562A204]] Production implementation must additionally perform the transition within an appropriate transaction, verify expected database state and worker generation, persist the transition event, and handle concurrent updates.

[/body/p[@paraId=5AF6E53C]] · domain/state_machine.py: state definitions, legal transitions and pure transition rules.
[/body/p[@paraId=65B07E86]] · services/task_service.py: authenticated task operations and lifecycle coordination.
[/body/p[@paraId=1A6DF407]] · execution/orchestrator.py: plans and sequences work, invoking the transition service.
[/body/p[@paraId=6ECFDF22]] · execution/recovery.py: identifies unresolved work and coordinates safe reconciliation.
[/body/p[@paraId=770EDF07]] · execution/claims.py: worker ownership, leases and fencing.
[/body/p[@paraId=07388D3D]] · services/approval_service.py: approval creation, decisions, expiry and invalidation.

[/body/p[@paraId=15A35A6C]] 03.29.14 Required automated tests
[/body/p[@paraId=572285E7]] State-machine unit tests
[/body/p[@paraId=2F10D2D8]] · Every documented transition is accepted under its required conditions.
[/body/p[@paraId=74124318]] · Every forbidden transition is rejected.
[/body/p[@paraId=7353CF50]] · Terminal states cannot return to active states.
[/body/p[@paraId=1EEA1833]] · A task cannot succeed while required steps are unresolved.
[/body/p[@paraId=40DF205A]] · An uncertain step cannot be treated as a confirmed failure without evidence.
[/body/p[@paraId=182A3D8C]] · A denied operation cannot be dispatched.

[/body/p[@paraId=5C040697]] · Two workers cannot successfully claim the same eligible task concurrently.
[/body/p[@paraId=44316A2F]] · A stale worker cannot overwrite a newer transition.
[/body/p[@paraId=461594BC]] · Task state and transition history are committed atomically.
[/body/p[@paraId=79A327F7]] · Concurrent cancellation and approval cannot violate the state machine.
[/body/p[@paraId=69FCC7AC]] · Duplicate client request IDs do not create duplicate tasks.
[/body/p[@paraId=2D0D187A]] · A transaction rollback leaves no partially committed lifecycle transition.
[/body/p[@paraId=3B216CFF]] Recovery and fault-injection tests
[/body/p[@paraId=0E095430]] · Backend crash immediately before dispatch.
[/body/p[@paraId=2EDB2437]] · Backend crash after dispatch but before result persistence.
[/body/p[@paraId=157EF06B]] · Bridge response lost after successful file creation.

[/body/p[@paraId=06FFC32D]] · Recovery itself crashes before committing its result.
[/body/p[@paraId=35CCA3E0]] For every scenario, tests must assert both the final state and the external side effects. A test that merely expects 200 OK is insufficient.

[/body/p[@paraId=38286775]] 03.29.17 Definition of done
[/body/p[@paraId=45B27CE2]] Section 03.29 is ready for implementation when:
[/body/p[@paraId=6877742B]] · The task and step state definitions are agreed.
[/body/p[@paraId=020BC65F]] · Every supported state transition has a documented trigger and validation rule.
[/body/p[@paraId=7D736C2E]] · Forbidden transitions are rejected.
[/body/p[@paraId=07067FF0]] · Only the designated application workflow can commit lifecycle transitions.

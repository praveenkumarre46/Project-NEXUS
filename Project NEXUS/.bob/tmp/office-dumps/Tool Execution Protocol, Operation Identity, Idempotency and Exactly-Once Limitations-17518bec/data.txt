[/body/p[@paraId=076AF7EC]] 03.30.1 Purpose
[/body/p[@paraId=610E9A54]] NEXUS coordinates work across several independent components: the FastAPI backend, PostgreSQL, the AI runtime and a native Windows bridge on each user's computer. These components can fail independently, and network messages can be delayed, duplicated or lost.
[/body/p[@paraId=76F5E421]] This creates a fundamental reliability problem.
[/body/p[@paraId=56DE9B82]] Suppose NEXUS asks a Windows bridge to create a file:
[/body/p[@paraId=62894085]] 1. The backend sends the operation.
[/body/p[@paraId=3B1230D5]] 2. The bridge creates the file successfully.
[/body/p[@paraId=437FFA96]] 3. The bridge sends a success response.
[/body/p[@paraId=34DF0E99]] 4. The response never reaches the backend.
[/body/p[@paraId=75810104]] 5. The backend times out.
[/body/p[@paraId=299A32D1]] The backend knows the operation was dispatched, but it does not know whether the file was created.
[/body/p[@paraId=484F3C28]] If it retries blindly, it may duplicate a side effect. If it marks the operation failed, it may report an incorrect result.
[/body/p[@paraId=143625EB]] NEXUS must treat operation delivery, execution and outcome recording as separate events. This section defines the protocol that makes that distinction explicit.
[/body/p[@paraId=3CDBFFC1]] 03.30.02 Core concepts and identifiers
[/body/p[@paraId=6BE57686]] NEXUS needs multiple identifiers because a task, a logical operation and an individual attempt are not the same thing.
[/body/tbl[1]] [Table: 8 rows]
[/body/p[@paraId=4B810A4B]] The identifiers must be opaque and unguessable where they cross trust boundaries. An ID is a correlation mechanism, not proof of authorization.
[/body/p[@paraId=1C2CB561]] Example
[/body/p[@paraId=33952506]] A user submits one task to create a report and open an approved application afterward.
[/body/p[@paraId=42314FDB]] · One task_id represents the overall request.
[/body/p[@paraId=648E2BA9]] · The file creation has one step_id and one stable operation_id.
[/body/p[@paraId=1CFDB114]] · If a retry is allowed, it reuses that logical operation identity while receiving a new attempt_id.
[/body/p[@paraId=1CC255C9]] · Opening the application is a separate logical operation with its own operation identity.
[/body/p[@paraId=51B4FAA3]] The exact schema and identifier format remain implementation decisions. The separation of identities is a behavioral requirement.
[/body/p[@paraId=3C548AE2]] 03.30.03 The execution protocol
[/body/p[@paraId=74C66D32]] Each operation should follow a durable protocol.
[/body/p[@paraId=131307B7]] 1. Prepare
[/body/p[@paraId=027A4CCB]] Validate the step, tool contract, arguments and dependencies.
[/body/p[@paraId=7C2669DA]] 2. Authorize
[/body/p[@paraId=2659A8B0]] Check identity, device scope, policy and any required approval.
[/body/p[@paraId=20B09EF5]] 3. Persist intent
[/body/p[@paraId=4984289E]] Commit the operation identity, arguments reference or snapshot, attempt and dispatch intent.
[/body/p[@paraId=7EA4D82F]] 4. Dispatch
[/body/p[@paraId=5BD9B0D9]] Send the authenticated, device-targeted operation to the bridge.
[/body/p[@paraId=455E9AC0]] 5. Execute and report
[/body/p[@paraId=41A2D7BE]] The bridge validates locally, executes the registered tool and returns a structured outcome.
[/body/p[@paraId=5EB883B4]] 6. Record and verify
[/body/p[@paraId=5CB85187]] Validate the response, persist the result and verify the required postcondition.
[/body/p[@paraId=54851EAD]] The intent must be durably committed before dispatch. Otherwise, the bridge could perform a side effect that the backend has no record of requesting.
[/body/p[@paraId=04232F18]] The backend must not hold a PostgreSQL transaction open throughout network communication or tool execution. Persist intent in a short transaction, commit it, and then perform the external operation.
[/body/p[@paraId=7CE82458]] A timeout, process crash or lost response between these stages can leave the operation uncertain. Recovery must be designed around that possibility.
[/body/p[@paraId=275AA4BF]] 03.30.04 Operation contract
[/body/p[@paraId=7566525D]] Every bridge operation must use a versioned, validated contract. The following is an illustrative envelope, not the final API schema.
[/body/p[@paraId=4777892A]] {
[/body/p[@paraId=1715894A]]   "protocol_version": "1",
[/body/p[@paraId=009999A1]]   "operation_id": "stable-logical-operation-id",
[/body/p[@paraId=5922119D]]   "attempt_id": "unique-attempt-id",
[/body/p[@paraId=6F5DA86D]]   "task_id": "parent-task-id",
[/body/p[@paraId=590364DE]]   "step_id": "logical-step-id",
[/body/p[@paraId=31345B0E]]   "target_device_id": "registered-device-id",
[/body/p[@paraId=14E67BF9]]   "tool_name": "create_file",
[/body/p[@paraId=3048072B]]   "tool_schema_version": "1",
[/body/p[@paraId=37BD8126]]   "arguments": {
[/body/p[@paraId=74A651E6]]     "directory_id": "approved-workspace",
[/body/p[@paraId=36F694EB]]     "relative_path": "report.txt",
[/body/p[@paraId=5D670D3E]]     "content": "Example report content"
[/body/p[@paraId=38888BA6]]   },
[/body/p[@paraId=129573EE]]   "deadline": "2026-10-22T14:00:00Z"
[/body/p[@paraId=66933399]] }
[/body/p[@paraId=6B68963E]] The actual operation arguments must follow the registered tool's input schema. Unknown fields, unsupported protocol versions and invalid arguments must be handled according to a documented contract policy; security-sensitive unknown fields must fail closed.
[/body/p[@paraId=131F1B3D]] The envelope is not trusted simply because it comes from the backend. The bridge must authenticate the caller and validate the target device, tool, arguments, permissions and local filesystem or application restrictions.
[/body/p[@paraId=53858157]] Contract requirements
[/body/p[@paraId=2575C6CB]] · The operation_id remains stable across attempts for the same logical operation.
[/body/p[@paraId=0A12B3F9]] · A new attempt_id identifies each distinct attempt.
[/body/p[@paraId=52D4E7FB]] · The target device must match the authenticated bridge registration.
[/body/p[@paraId=1AEFFB84]] · The tool name and schema version must be supported.
[/body/p[@paraId=108718B1]] · Arguments must be validated against the registered tool contract.
[/body/p[@paraId=3AE82F61]] · The deadline must be enforced using a defined clock and timeout policy.
[/body/p[@paraId=4E1A34C8]] · Credentials, passwords and unrelated private context must not be embedded in operation arguments.
[/body/p[@paraId=108A00C8]] · Retries must not silently change the logical operation's parameters.
[/body/p[@paraId=67B43772]] If a planned operation changes materially—for example, creating a different file or using a different target directory—it is a new logical operation and requires fresh authorization and, when applicable, approval.
[/body/p[@paraId=1EA840D3]] 03.30.05 Idempotency and deduplication
[/body/p[@paraId=11A2E9D1]] An operation is idempotent when repeating it has the same intended effect as performing it once. Not all NEXUS tools have this property.
[/body/tbl[2]] [Table: 6 rows]
[/body/p[@paraId=2373C971]] Even a read-only operation can be expensive, observe changed data or expose new information, so retries still require authorization and resource limits.
[/body/p[@paraId=38CF0FEC]] Bridge-side deduplication
[/body/p[@paraId=275A7079]] The bridge should maintain a durable record of operations it has accepted and their known outcomes. For a repeated operation ID:
[/body/p[@paraId=6C988EE6]] 1. Verify that the incoming operation matches the original logical operation.
[/body/p[@paraId=7C44DCE4]] 2. If a completed outcome is recorded, return the known outcome rather than executing it again.
[/body/p[@paraId=6919A0EF]] 3. If the operation is still in progress, report that status rather than starting a duplicate.
[/body/p[@paraId=0FE84B35]] 4. If the previous attempt has an uncertain outcome, initiate reconciliation where supported.
[/body/p[@paraId=7AAAA138]] 5. If the same operation ID arrives with different parameters or a different target, reject it.
[/body/p[@paraId=61B9A429]] The deduplication record should include the operation identity, a securely computed fingerprint of the relevant request, status and available outcome evidence. It should not need to retain complete private document content indefinitely.
[/body/p[@paraId=0D81992D]] Important limitation: deduplication prevents known duplicate executions. It does not by itself solve the crash window between performing an external side effect and durably recording its result.
[/body/p[@paraId=0EC493C5]] 03.30.06 Exactly-once execution: what NEXUS can and cannot promise
[/body/p[@paraId=0F1E8A18]] NEXUS must not promise exactly-once execution for arbitrary Windows operations across backend crashes, bridge crashes and network failures.
[/body/p[@paraId=0AAA9D16]] The backend database and an external Windows filesystem operation do not participate in one shared atomic transaction. A PostgreSQL commit cannot roll back a file that Windows has already created.
[/body/p[@paraId=4B74369D]] Instead, NEXUS should combine:
[/body/p[@paraId=7B4C3775]] · Durable operation identity.
[/body/p[@paraId=004C386C]] · At-least-once delivery where retry is appropriate.
[/body/p[@paraId=360D23F6]] · Deduplication of known duplicate requests.
[/body/p[@paraId=3AFFE019]] · Tool-specific idempotency.
[/body/p[@paraId=712CF0FB]] · Reconciliation of uncertain outcomes.
[/body/p[@paraId=4B1ABB01]] · Explicit uncertainty when reliable evidence is unavailable.
[/body/p[@paraId=254E0E3E]] These mechanisms can provide strong practical reliability, but they cannot guarantee that every arbitrary external side effect happens exactly once.
[/body/p[@paraId=607D9A1C]] Example: file creation
[/body/p[@paraId=3B0BADFC]] Case A — The bridge never received the operation
[/body/p[@paraId=2C65F9EE]] The backend has reliable evidence that dispatch did not reach the execution boundary.
[/body/p[@paraId=74EBBBC7]] Retry may be allowed under the operation's retry policy.
[/body/p[@paraId=44150239]] Case B — The file was created, but the response was lost
[/body/p[@paraId=43E625E6]] The backend cannot infer failure from the timeout.
[/body/p[@paraId=05190505]] Reconcile the operation record and destination before considering another attempt.
[/body/p[@paraId=4E9B6110]] Case C — The bridge also crashed before recording the outcome
[/body/p[@paraId=012F5795]] The operation record may not settle whether the side effect happened.
[/body/p[@paraId=18BE58AE]] Inspect available evidence. If the result remains ambiguous, preserve UNCERTAIN and do not retry blindly.
[/body/p[@paraId=000AE233]] Can atomic file creation help?
[/body/p[@paraId=2CE0BB68]] Yes, within limits. For create_file, the bridge should use a safe create-if-absent approach where the platform and filesystem support it. The operation must not silently overwrite an existing file.
[/body/p[@paraId=31878D52]] A unique operation-specific temporary file followed by an atomic rename may be useful for some workflows, but the precise behavior depends on the filesystem, target path and rename semantics. It must be designed and tested rather than assumed to be universally atomic.
[/body/p[@paraId=61FBC2AE]] The destination must be revalidated at execution time, and path checks must account for Windows path normalization and filesystem race conditions.
[/body/p[@paraId=385FEAD0]] 03.30.07 Operation fingerprints and immutable requests
[/body/p[@paraId=6396F374]] For safe deduplication, the bridge and backend need to identify whether two deliveries represent the same logical operation.
[/body/p[@paraId=3133C6D5]] A proposed fingerprint can cover:
[/body/p[@paraId=039396A2]] · Tool name and schema version.
[/body/p[@paraId=487382F5]] · Canonicalized arguments.
[/body/p[@paraId=447A2D1F]] · Target device.
[/body/p[@paraId=656FC4D2]] · Resource scope.
[/body/p[@paraId=4B56A7D4]] · Relevant execution options.
[/body/p[@paraId=146ED974]] The fingerprint should be calculated from a deterministic representation. Secret values should not be exposed through diagnostic logs merely because they contribute to the fingerprint.
[/body/p[@paraId=189FB78F]] If the operation is already registered under the same operation_id, a fingerprint mismatch must be rejected. It must not silently replace the original operation.
[/body/p[@paraId=6DB4B4C2]] An approval fingerprint and an execution fingerprint serve related but distinct purposes:
[/body/p[@paraId=46F8E567]] · Approval fingerprint: proves that the operation being executed matches the operation that was approved.
[/body/p[@paraId=47CF54D9]] · Execution fingerprint: supports request consistency and deduplication across delivery attempts.
[/body/p[@paraId=702812E2]] Both must be checked against trusted, validated data—not a fingerprint supplied by the AI model.
[/body/p[@paraId=6AAA99BA]] 03.30.08 Deadlines, timeouts and retries
[/body/p[@paraId=2579727F]] A deadline limits how long NEXUS is willing to wait for a stage or operation. It does not prove that the external operation stopped when the deadline passed.
[/body/p[@paraId=491D1B0D]] Each tool contract must define:
[/body/p[@paraId=0B8203CF]] · Maximum execution duration.
[/body/p[@paraId=128C91A0]] · Dispatch timeout.
[/body/p[@paraId=3C9A034B]] · Result-wait timeout.
[/body/p[@paraId=5052C3FC]] · Retry eligibility.
[/body/p[@paraId=075DC4D7]] · Maximum attempts and total retry budget.
[/body/p[@paraId=75648344]] · Backoff behavior for transient failures.
[/body/p[@paraId=24EB97AD]] · Reconciliation strategy.
[/body/p[@paraId=393401D1]] · Final handling if the result remains uncertain.
[/body/p[@paraId=14A06312]] Retry rules
[/body/p[@paraId=2112BD19]] 1. Retry only if the operation contract permits it.
[/body/p[@paraId=62296C9B]] 2. Recheck task cancellation, device status, authorization and approval before dispatch.
[/body/p[@paraId=0B78CACF]] 3. Preserve the same logical operation ID when retrying the same operation.
[/body/p[@paraId=4ED9624F]] 4. Assign a new attempt ID for the new attempt.
[/body/p[@paraId=5337092D]] 5. Apply bounded backoff and retry budgets.
[/body/p[@paraId=0C6FD723]] 6. Reconcile uncertain side effects before another potentially consequential attempt.
[/body/p[@paraId=2231D2FA]] 7. Record each attempt's outcome independently from the overall logical operation.

[/body/p[@paraId=74A4A657]] The bridge should return a structured outcome that distinguishes execution status from certainty.
[/body/p[@paraId=6C3E9E3A]] Proposed outcome fields:

[/body/p[@paraId=504CE0E3]] This is a proposed contract, not a finalized wire schema.
[/body/p[@paraId=092DC0FC]] A response must be authenticated and correlated with the operation before it changes task state. A validly authenticated bridge can still return an error, an incomplete result or an outcome that needs reconciliation.
[/body/p[@paraId=700C0A52]] Outcome semantics
[/body/p[@paraId=2703E2BC]] · SUCCEEDED: the tool reports success, and the backend's required verification conditions are satisfied.
[/body/p[@paraId=7C7C9D61]] · FAILED: failure is established, with no unresolved external side effect that could make a retry unsafe.
[/body/p[@paraId=5BD45B98]] · REJECTED: validation or policy blocked the operation before execution.
[/body/p[@paraId=3AFB043A]] · RUNNING: the bridge knows execution is in progress.
[/body/p[@paraId=70AFA823]] · UNCERTAIN: the available evidence cannot establish whether the operation succeeded or failed.
[/body/p[@paraId=2A65E1C0]] If a tool reports success but required verification cannot be completed, the backend must not automatically mark the overall task successful. It may need to keep the step unresolved or classify it as uncertain, according to the tool contract.
[/body/p[@paraId=76679C59]] The backend must also distinguish the bridge's reported result from the backend's durable recording of that result. If persistence fails after receiving a response, recovery must use the operation identity and available evidence to reconcile the discrepancy.

[/body/p[@paraId=2312A144]] Verification is tool-specific. There is no universal check that proves every external operation completed correctly.
[/body/tbl[5]] [Table: 5 rows]
[/body/p[@paraId=0C4B4263]] These are examples of verification approaches, not guarantees. Files can change after verification, processes can exit immediately after launch, and some effects may not expose reliable operation metadata.
[/body/p[@paraId=044DCFB7]] Reconciliation protocol
[/body/p[@paraId=724AF5F4]] When the outcome is uncertain:
[/body/p[@paraId=3D01C996]] 1. Locate the operation using its stable identity.
[/body/p[@paraId=4D021C5A]] 2. Check the bridge's durable operation record.
[/body/p[@paraId=7B8394D7]] 3. Check whether the bridge reports the operation as running.
[/body/p[@paraId=55B178C6]] 4. Apply tool-specific external verification where supported.
[/body/p[@paraId=51D794FF]] 5. Determine whether the operation is confirmed successful, confirmed failed, still running or unresolved.
[/body/p[@paraId=6E0AD7D4]] 6. Persist the reconciliation result and supporting evidence.
[/body/p[@paraId=6A25A7AB]] 7. Retry only if the evidence and retry contract make that safe.
[/body/p[@paraId=4B79589E]] If no reliable evidence can resolve the result, NEXUS must preserve uncertainty and surface it to the user. A human recovery step may be necessary.
[/body/p[@paraId=1E77377E]] 03.30.11 Bridge persistence and restart behavior
[/body/p[@paraId=03C341AD]] The Windows bridge needs enough local persistence to recognize duplicate operation deliveries and report known outcomes after a process restart.
[/body/p[@paraId=2AEE4E6E]] The initial design should consider a local durable operation journal containing:
[/body/p[@paraId=5266BFF6]] · Operation ID and request fingerprint.
[/body/p[@paraId=1617B49E]] · Task and step correlation IDs.
[/body/p[@paraId=25766870]] · Target tool and schema version.
[/body/p[@paraId=34A4280F]] · Accepted, running and terminal status.
[/body/p[@paraId=5F83A69C]] · Attempt metadata.
[/body/p[@paraId=443F015E]] · Known result or bounded result reference.
[/body/p[@paraId=06DA153A]] · Timestamps and reconciliation state.
[/body/p[@paraId=4FB3BF1A]] The exact storage technology is open. A small local database is one candidate, but the team must validate durability, locking, permissions, cleanup and recovery behavior before choosing it.
[/body/p[@paraId=1F2025AC]] Bridge startup protocol
[/body/p[@paraId=70FB2140]] After restart, the bridge should:
[/body/p[@paraId=101320FF]] 1. Load and validate its local configuration.
[/body/p[@paraId=0F0076AA]] 2. Re-establish its authenticated device identity.
[/body/p[@paraId=28AC28DB]] 3. Report its capabilities and protocol version.
[/body/p[@paraId=0897E45E]] 4. Load unresolved local operation records.
[/body/p[@paraId=5A1F3DF4]] 5. Report known outcomes and still-running or uncertain operations.
[/body/p[@paraId=3303E1C3]] 6. Reconcile with the backend before accepting duplicate or conflicting work.
[/body/p[@paraId=2842C982]] 7. Accept new operations only when its security and readiness checks pass.
[/body/p[@paraId=01A87E35]] The bridge must not assume that the backend's view is more current than its local evidence. Conversely, local records must not be trusted as authorization to execute new work.
[/body/p[@paraId=55E0CEF8]] Retention of deduplication records
[/body/p[@paraId=6D998A73]] Deduplication records cannot be discarded while a task or retry may still refer to them. The retention policy should consider maximum task lifetime, retry window, recovery window and backup/restore behavior.
[/body/p[@paraId=587EF7C0]] Once an operation is safely terminal and outside all retry or recovery windows, its detailed result may be eligible for cleanup under the retention policy. Minimal tombstones or operation identity records may need to remain longer to prevent a delayed duplicate delivery from being executed again.
[/body/p[@paraId=474B13E5]] The retention periods remain open until task lifetime and transport retry limits are finalized.
[/body/p[@paraId=47D9F9B1]] 03.30.12 Security and authorization at the execution boundary
[/body/p[@paraId=5F92F8BE]] The operation protocol is also a security boundary. Correct deduplication does not make an unauthorized operation safe.
[/body/p[@paraId=6CE5D5E9]] Before execution, the backend and bridge must independently enforce the controls applicable to their roles.
[/body/p[@paraId=4ABEF1F3]] Backend checks
[/body/p[@paraId=6C9AF595]] · The user owns the task or otherwise has explicit access.
[/body/p[@paraId=532217B5]] · The target device is registered, active and authorized.
[/body/p[@paraId=74CAAE85]] · The tool is registered and enabled.
[/body/p[@paraId=7F37CDB1]] · Arguments satisfy the approved tool schema.
[/body/p[@paraId=65E3B2DC]] · The current policy permits execution.
[/body/p[@paraId=50C6B094]] · Required approval is valid, unexpired and bound to the exact operation.
[/body/p[@paraId=4E26ABF6]] · The task is in a state that allows dispatch.
[/body/p[@paraId=5849388D]] · Cancellation has not prevented the operation from starting.
[/body/p[@paraId=38BE7E5D]] Bridge checks
[/body/p[@paraId=3AC91AB4]] · The request came through the configured authenticated transport.
[/body/p[@paraId=53A233A3]] · The request targets this registered device.
[/body/p[@paraId=7D2BCC28]] · The protocol and tool schema are supported.
[/body/p[@paraId=6249EA99]] · The operation ID has not been reused with conflicting parameters.
[/body/p[@paraId=41C389BD]] · The tool is locally enabled.
[/body/p[@paraId=17AA1568]] · Filesystem and application restrictions permit the requested operation.
[/body/p[@paraId=7AAE8359]] · Deadlines and resource limits are respected.
[/body/p[@paraId=2A95C08F]] The bridge must not expose a generic command-execution endpoint to compensate for a missing tool. New tools require an explicit contract, risk classification, permissions, retry policy, verification strategy and tests.
[/body/p[@paraId=4455B728]] A valid operation ID is not authorization. A valid approval is not permission to bypass a local restriction. A high-priority task is not entitled to bypass any of these checks.
[/body/p[@paraId=494C214F]] 03.30.13 Required fault-injection tests
[/body/p[@paraId=6A794B92]] These tests should be automated wherever practical and run against isolated test directories and test devices.

[/body/p[@paraId=005C27E5]] Tests must verify the actual filesystem or application side effect, not just the backend status code. A test that returns an error while creating a duplicate file is still a failure.

[/body/p[@paraId=655DBDF2]] 03.30.16 Definition of done
[/body/p[@paraId=2056FD2D]] Section 03.30 is ready for implementation when:
[/body/p[@paraId=0D3D5F90]] · Task, step, operation and attempt identities are distinct.
[/body/p[@paraId=3289993F]] · Every operation has a defined input contract and execution policy.
[/body/p[@paraId=533B6CD9]] · Execution intent is durably recorded before dispatch.
[/body/p[@paraId=1D3BB2F9]] · Duplicate deliveries and conflicting reuse of operation IDs are handled safely.
[/body/p[@paraId=28EF04CD]] · Tool retry rules distinguish safe retries from uncertain side effects.
[/body/p[@paraId=1F1E7B55]] · Backend and bridge restart behavior is documented and tested.
[/body/p[@paraId=77321881]] · Required verification and reconciliation are defined for every MVP tool.
[/body/p[@paraId=469DC05D]] · The bridge persists enough evidence to recognize known duplicate operations.
[/body/p[@paraId=5F68DDDD]] · Authorization is revalidated at execution boundaries.
[/body/p[@paraId=77DF53DC]] · The team explicitly documents that exactly-once execution cannot be guaranteed for arbitrary external side effects.
[/body/p[@paraId=61EA7692]] · Fault-injection tests verify both durable state and real side effects.
[/body/p[@paraId=6F0B5DF2]] Recommended engineering decision: use stable operation IDs, distinct attempt IDs, durable intent, bridge-side deduplication, tool-specific verification and explicit uncertainty. Do not claim exactly-once execution; make retries safe where possible and make unresolved outcomes visible everywhere else.

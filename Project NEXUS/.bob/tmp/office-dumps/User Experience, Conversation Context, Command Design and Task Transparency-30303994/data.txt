[/body/p[@paraId=6B37FD0E]] 03.38.1 Purpose
[/body/p[@paraId=5AACC3BE]] NEXUS is a terminal-first computer companion. Its interface must make it easy to express a goal, understand what the system intends to do, monitor progress, respond to approval requests and inspect the outcome.
[/body/p[@paraId=6D2483B2]] The interface must not hide important uncertainty behind conversational confidence. A friendly response is useful, but the persisted task state and verified execution evidence are the source of truth.
[/body/p[@paraId=43AE72B4]] This section defines the user-facing interaction model across the CLI, backend task lifecycle, approvals, context and errors.
[/body/p[@paraId=32CA8138]] The design should support two complementary interaction styles:
[/body/p[@paraId=1E43A2DE]] · Natural-language requests: users describe the outcome they want.
[/body/p[@paraId=2A396D39]] · Explicit commands: users inspect devices, tasks, approvals, history, memory and diagnostics.
[/body/p[@paraId=2F1DD55B]] Natural language is the entry point for computer assistance, not a replacement for precise administrative controls.
[/body/p[@paraId=01B9DB09]] 03.38.2 Core UX principles
[/body/p[@paraId=6F42D483]] 1. Make the next action obvious. The user should know whether NEXUS is working, waiting, blocked or finished.
[/body/p[@paraId=4E7380B4]] 2. Distinguish acceptance from completion. Receiving a task ID means the request was recorded, not that the work is finished.
[/body/p[@paraId=6DEE35B1]] 3. Expose consequential actions before execution. Approval requests show the exact operation and target.
[/body/p[@paraId=496AE7D5]] 4. Be honest about uncertainty. An unknown outcome must not be presented as success or failure without evidence.
[/body/p[@paraId=0EB28054]] 5. Keep user control available. Users can inspect tasks, cancel work, review memory and understand permissions.
[/body/p[@paraId=06CC0C82]] 6. Prefer useful details over noisy logs. Show the current step, important events and actionable errors; provide detailed diagnostics separately.
[/body/p[@paraId=6432BBD8]] 7. Keep terminal automation scriptable. Machine-readable output must be stable and free of decorative output on standard output.
[/body/p[@paraId=24F5ED8C]] 8. Do not make security depend on interface wording. Approval prompts and displayed task details support—not replace—backend and bridge enforcement.
[/body/p[@paraId=1269DCA5]] 03.38.3 Primary interaction flow
[/body/p[@paraId=247F0025]] A typical task should follow a predictable sequence.
[/body/p[@paraId=4770CFE2]] 1. Request
[/body/p[@paraId=138A99E1]] The user describes the desired result and target computer.
[/body/p[@paraId=4CA95630]] 2. Acceptance
[/body/p[@paraId=0211D3BA]] NEXUS validates the request and persists it, returning a task ID.
[/body/p[@paraId=1D27B4A7]] 3. Plan or clarification
[/body/p[@paraId=7D371BC4]] NEXUS builds a bounded plan, validates it, or asks a focused question.
[/body/p[@paraId=6F8D4C1F]] 4. Execute or wait
[/body/p[@paraId=340AB84D]] Authorized steps run; consequential actions wait for required approval.
[/body/p[@paraId=5E525C0B]] 5. Verified result
[/body/p[@paraId=15736EFE]] NEXUS reports completion, failure, cancellation, partial success or uncertainty.
[/body/p[@paraId=1B8F50A1]] A clarification request may occur before a valid plan exists. An approval request may occur after a plan has been validated. These are different conditions and should not be displayed as if they were the same task state.

[/body/p[@paraId=2DDB1200]] Command-line behavior rules
[/body/p[@paraId=4C894059]] · Commands that operate on a task must verify ownership and authorization.
[/body/p[@paraId=6CB23069]] · A user's default device may be supported as a convenience, but NEXUS must display the resolved target and must never silently switch devices.
[/body/p[@paraId=0B1F2CE6]] · --watch controls the local display only; stopping it does not cancel the task.
[/body/p[@paraId=31C820AC]] · cancel requests cancellation. The user must inspect the task state to establish whether cancellation actually completed.
[/body/p[@paraId=476E84FB]] · Approval commands must reference the specific pending approval and remain subject to backend validation.
[/body/p[@paraId=069D58E0]] · Memory inspection and deletion must apply the same ownership rules as memory retrieval.
[/body/p[@paraId=4037BD03]] · Unknown commands and invalid arguments should produce a useful error and usage guidance.
[/body/p[@paraId=0D2B1E97]] · Standard output should contain the requested result; progress and diagnostics should go to standard error where appropriate.
[/body/p[@paraId=7061B97A]] 03.38.5 Natural-language request handling
[/body/p[@paraId=6875D72A]] The run command should support natural-language goals without making users learn the internal tool registry.
[/body/p[@paraId=4534BABA]] An illustrative command:
[/body/p[@paraId=69FFBA89]] nexus run "Find the latest design document and summarize it" \
[/body/p[@paraId=1208237D]]   --device my-windows-pc
[/body/p[@paraId=607ADE37]] The CLI submits the request and receives a durable task identifier if acceptance succeeds.
[/body/p[@paraId=5A1F0A50]] Example response:
[/body/p[@paraId=4D2F44EE]] Request accepted
[/body/p[@paraId=2CB76B77]] Task ID: task_abc123
[/body/p[@paraId=491F0E51]] Target: my-windows-pc
[/body/p[@paraId=5FD87174]] Status: QUEUED
[/body/p[@paraId=408ED9AC]] 
[/body/p[@paraId=74B0A7D7]] Track progress:
[/body/p[@paraId=00D28C01]]   nexus task task_abc123 --watch
[/body/p[@paraId=0E307B51]] The identifiers and formatting are illustrative only.
[/body/p[@paraId=40A8C09C]] Request-handling rules
[/body/p[@paraId=7D083567]] · Do not claim a task was accepted until the backend confirms durable acceptance.
[/body/p[@paraId=559279D0]] · If the backend is unavailable, report that acceptance could not be confirmed.
[/body/p[@paraId=3EFBDF2C]] · If the request is ambiguous, ask a focused question before taking a consequential action.
[/body/p[@paraId=47E6AC59]] · If the requested capability is unsupported, explain the limitation honestly.
[/body/p[@paraId=733AD014]] · Do not make the user repeat context that is already available and authorized.
[/body/p[@paraId=2FD05B36]] · Do not silently convert a vague request into a broader or more consequential operation.
[/body/p[@paraId=347213D1]] · If the request exceeds configured planning or execution limits, explain the limit and offer a narrower supported approach.
[/body/p[@paraId=0BE34A20]] The user should be able to distinguish three outcomes: request not accepted, request accepted but not completed, and task completed with verified results.
[/body/p[@paraId=3240581B]] 03.38.6 Plan visibility and informed approval
[/body/p[@paraId=1417E55B]] For straightforward, low-risk operations already covered by the user's permissions, NEXUS should avoid unnecessary interruptions. For consequential operations, the interface must expose enough detail for an informed decision.
[/body/p[@paraId=5D533CF6]] A proposed approval display:
[/body/p[@paraId=15E26DB9]] Approval required
[/body/p[@paraId=423FFE15]] Illustrative terminal preview
[/body/p[@paraId=08AD80BE]] Task
[/body/p[@paraId=5BC12822]] Create a report in the approved workspace.
[/body/p[@paraId=42BAA023]] Target device
[/body/p[@paraId=2B28A164]] my-windows-pc
[/body/p[@paraId=59340461]] Proposed operation
[/body/p[@paraId=156147CE]] Create a new file named report.txt containing the generated report.
[/body/p[@paraId=746E8770]] Destination
[/body/p[@paraId=085B50D2]] The resolved approved workspace, with the destination shown clearly enough to identify it.
[/body/p[@paraId=68E6AF29]] Existing-file behavior
[/body/p[@paraId=11441BE3]] Do not overwrite an existing file.
[/body/p[@paraId=53F41E54]] Approval details
[/body/p[@paraId=23E853C2]] The precise operation, relevant parameters, consequences and expiry must be visible.
[/body/p[@paraId=329C3A85]] Decision
[/body/p[@paraId=773B6ACC]] Approve or reject through the supported CLI.
[/body/p[@paraId=4388320C]] The real interface must show the actual resolved destination and the exact operation being approved, not generic placeholder wording. It should identify any meaningful irreversible consequences and the approval's expiry.
[/body/p[@paraId=3FDBED16]] The approval must be bound to the validated operation, target device, arguments, resource scope and policy requirements. If any material detail changes, NEXUS must revalidate the operation and obtain a new approval when required.
[/body/p[@paraId=383FBC88]] The UI cannot authorize an action merely by displaying an approval prompt. The backend and Windows bridge must independently enforce the relevant rules.
[/body/p[@paraId=2E18CF53]] 03.38.7 Progress and task transparency
[/body/p[@paraId=373E9942]] Users should not have to inspect server logs to understand the progress of ordinary tasks.
[/body/p[@paraId=63FD56F5]] The CLI should show the current task state, current step, completed steps, blocked steps, any required user action and the most recent meaningful event.
[/body/p[@paraId=74189941]] Illustrative progress display:
[/body/p[@paraId=3C51F157]] Task: task_abc123
[/body/p[@paraId=3FCEB4EF]] Status: RUNNING
[/body/p[@paraId=18C20136]] Target: my-windows-pc
[/body/p[@paraId=783345BE]] 
[/body/p[@paraId=42D0C144]] Steps:
[/body/p[@paraId=3D43310F]]   [done]   Find matching document
[/body/p[@paraId=14139FD7]]   [done]   Read document
[/body/p[@paraId=3EE16C2F]]   [active] Generate summary
[/body/p[@paraId=7E27A6A9]]   [pending] Create summary file
[/body/p[@paraId=2F4F7EDF]] 
[/body/p[@paraId=7F50F95C]] Last event:
[/body/p[@paraId=285349F0]]   Summary generation started
[/body/p[@paraId=52DE5C0B]] The status of a step must come from persisted task records, not from a model-generated progress message.
[/body/p[@paraId=693D6027]] Progress display requirements
[/body/p[@paraId=6FE6B3A8]] · Show only progress that the backend can substantiate.
[/body/p[@paraId=0F1DA213]] · Do not invent percentage completion when no defensible estimate exists.
[/body/p[@paraId=5BDE0476]] · Distinguish waiting for approval from waiting for a device or dependency.
[/body/p[@paraId=688E1F78]] · Distinguish a running operation from a dispatched operation whose execution is not confirmed.
[/body/p[@paraId=7C3FD09E]] · Show partial success when some steps succeeded and others failed.
[/body/p[@paraId=5C9E1E90]] · Preserve the ability to inspect individual steps and structured errors.
[/body/p[@paraId=49EB46D2]] · Avoid flooding the terminal with repeated polling output.
[/body/p[@paraId=1F734B14]] · Ensure that a terminal disconnect or interrupted --watch command does not change task state.
[/body/p[@paraId=2D556DF7]] Polling is the proposed initial approach. Server-sent events or WebSockets can be introduced later if measured latency or usability justifies their complexity.
[/body/p[@paraId=395D3E16]] 03.38.8 Results, partial success and uncertainty
[/body/p[@paraId=29FA4E7B]] The final response must accurately describe what happened, including when only part of the requested task was completed.
[/body/tbl[2]] [Table: 7 rows]
[/body/p[@paraId=5F3F1660]] For example, if NEXUS reads a document and generates a summary but cannot establish whether the output file was created, it must not report the entire task as successful. It should report the completed work and clearly mark file creation as uncertain.
[/body/p[@paraId=26890C5A]] Results should include, when applicable:
[/body/p[@paraId=78CEC302]] · Task ID and final state.
[/body/p[@paraId=0FA38EA3]] · Target device.
[/body/p[@paraId=0C5A81F6]] · Completed, failed, skipped and uncertain steps.
[/body/p[@paraId=0D54A51D]] · Output references or approved destination details.
[/body/p[@paraId=33A0FF65]] · Stable error code and human-readable explanation.
[/body/p[@paraId=58EF21CC]] · Any remaining user action.
[/body/p[@paraId=1B113EE0]] · Relevant timestamps and verification evidence.
[/body/p[@paraId=74345D6F]] Large outputs should be bounded and retrievable through a dedicated result command. NEXUS should avoid placing entire document contents into terminal history or logs unnecessarily.
[/body/p[@paraId=193A69EC]] 03.38.9 Conversation context and task continuity
[/body/p[@paraId=1133D9F8]] NEXUS needs enough context to support follow-up requests without confusing previous work with the current task.
[/body/p[@paraId=1886AC21]] Consider this interaction:
[/body/p[@paraId=1574AE39]] 1. User: “Find the latest design document.”
[/body/p[@paraId=75681CC1]] 2. NEXUS: Returns two matching candidates.
[/body/p[@paraId=2B5833BD]] 3. User: “Use the second one and summarize it.”
[/body/p[@paraId=58AB700D]] 4. NEXUS: Resolves “the second one” against the previous authorized result and continues, if the reference remains valid.
[/body/p[@paraId=52C10142]] The system must not assume that every short follow-up refers to the most recent task. If multiple plausible references exist, it should ask for clarification.
[/body/p[@paraId=593A8CA6]] Proposed context-resolution order
[/body/p[@paraId=4524919D]] 5. Current explicit user instruction.
[/body/p[@paraId=01C2A13B]] 6. Explicit references to a task, device, document or other resource.
[/body/p[@paraId=44399001]] 7. Relevant state from the active interaction.
[/body/p[@paraId=1F9E24B4]] 8. Authorized, relevant task history.
[/body/p[@paraId=54D9381E]] 9. Relevant personal or project memory.
[/body/p[@paraId=59AD8725]] 10. Clarification if ambiguity remains material.
[/body/p[@paraId=64233BD2]] This is a proposed resolution order, not an authorization hierarchy. No context source overrides access controls, hard prohibitions or current policy.
[/body/p[@paraId=1E3FBB47]] Additional requirements:
[/body/p[@paraId=061CBEF8]] · Task state is read from the backend's persisted records.
[/body/p[@paraId=51BDBD35]] · A document reference must be revalidated before a new read or write operation.
[/body/p[@paraId=361E3B55]] · Memory is used only when relevant and authorized.
[/body/p[@paraId=2EA0F392]] · Old approvals are not inherited by a new or materially changed operation.
[/body/p[@paraId=5E73DF8D]] · A follow-up request does not automatically authorize repeating a consequential action.
[/body/p[@paraId=05A162EA]] · The user must be able to explicitly name a task when continuity is ambiguous.
[/body/p[@paraId=13A23A90]] 03.38.10 Error messages and recovery guidance
[/body/p[@paraId=2646D760]] Errors should explain the immediate problem without leaking secrets, private data or internal stack traces.
[/body/p[@paraId=2619C127]] A useful error message has three parts:
[/body/p[@paraId=38C361C5]] 1. What happened: a concise, accurate description.
[/body/p[@paraId=407C8FAC]] 2. What it means: whether the task is blocked, failed or uncertain.
[/body/p[@paraId=7A15DE29]] 3. What the user can do: a safe, specific next step where one exists.
[/body/p[@paraId=2E959729]] Illustrative examples:
[/body/p[@paraId=00B28BA8]] DEVICE_UNAVAILABLE
[/body/p[@paraId=39B24D2F]] The target computer is offline.
[/body/p[@paraId=7D823789]] The task has not been redirected to another device. Check the Windows bridge and reconnect the original computer before retrying.
[/body/p[@paraId=4ADADD1D]] APPROVAL_REQUIRED
[/body/p[@paraId=3E2A4812]] This operation is waiting for your approval.
[/body/p[@paraId=162444C5]] Inspect the proposed operation and approve or reject it using the associated task and approval identifiers.
[/body/p[@paraId=755477BA]] OPERATION_OUTCOME_UNCERTAIN
[/body/p[@paraId=41DE3645]] The operation may have completed, but NEXUS could not verify the result.
[/body/p[@paraId=2BED243E]] The system will reconcile the operation before attempting an unsafe retry. Do not assume that the requested change did not occur.
[/body/p[@paraId=034B12D2]] The examples illustrate the desired tone and structure; the precise wording and recovery instructions must match the implemented behavior.
[/body/p[@paraId=36FF2D3C]] Machine-readable error codes should remain stable even if human-readable messages change. Detailed diagnostics may be available through an authorized command, but ordinary error output should not reveal database credentials, authentication tokens, private prompts, unrestricted paths or internal exception details.
[/body/p[@paraId=4FDE34F4]] 03.38.11 Interactive and machine-readable output
[/body/p[@paraId=50A76753]] NEXUS should support both interactive human use and scripts that consume its results.
[/body/p[@paraId=788320CF]] Human-readable mode
[/body/p[@paraId=1ACC6565]] The default mode should display concise status information, helpful explanations, approval prompts and readable results. Color and terminal formatting may improve readability, but the CLI must still function in terminals that do not support them.
[/body/p[@paraId=1AE890F1]] Machine-readable mode
[/body/p[@paraId=07445D0E]] A proposed option is --output json for commands that return structured data.
[/body/p[@paraId=30F2CE5A]] Requirements:
[/body/p[@paraId=0934DC7D]] · Standard output contains valid JSON without banners, progress bars or unrelated text.
[/body/p[@paraId=14D40F31]] · Diagnostics and progress go to standard error where appropriate.
[/body/p[@paraId=01C5C720]] · Output schemas are documented and versioned.
[/body/p[@paraId=410441A8]] · Timestamps use a consistent UTC representation.
[/body/p[@paraId=7E51EE7D]] · IDs and status enums remain stable within the documented contract.
[/body/p[@paraId=3E4E5E02]] · Sensitive fields are omitted or redacted according to authorization and output policy.
[/body/p[@paraId=01812A83]] · Exit codes distinguish successful retrieval, validation errors, authorization failures and operational failures where practical.
[/body/p[@paraId=307B8B1F]] Example result shape:
[/body/p[@paraId=46BA81EE]] {
[/body/p[@paraId=5EAE9150]]   "task_id": "task_abc123",
[/body/p[@paraId=1A757604]]   "status": "SUCCEEDED",
[/body/p[@paraId=68E02E58]]   "outcome": "success",
[/body/p[@paraId=72B9AE00]]   "target_device_id": "registered-device-id",
[/body/p[@paraId=73170ED2]]   "result": {
[/body/p[@paraId=154ACB29]]     "summary_file_created": true
[/body/p[@paraId=761F7320]]   },
[/body/p[@paraId=3BE36EB1]]   "error": null
[/body/p[@paraId=4856E40B]] }
[/body/p[@paraId=62790B23]] This is illustrative, not the final API schema. A real result must be generated from persisted, verified execution records. The CLI must not synthesize success based on the AI's narrative.
[/body/p[@paraId=73A8F5B3]] 03.38.12 Accessibility, usability and operational safety
[/body/p[@paraId=1E9A0E1E]] Although NEXUS is terminal-first, the interface must be practical for different terminals, shell environments and user preferences.
[/body/p[@paraId=0913FFC8]] Proposed requirements:
[/body/p[@paraId=3E308353]] · Support ordinary keyboard-driven workflows.
[/body/p[@paraId=6D75F5B4]] · Do not require color to distinguish success, failure, approval or uncertainty.
[/body/p[@paraId=0BE595B1]] · Use concise default output and provide detailed inspection commands.
[/body/p[@paraId=42F16248]] · Avoid requiring users to remember opaque identifiers when a safe task-listing command can help them select the correct item.
[/body/p[@paraId=46A91C1F]] · Clearly distinguish a task ID from an approval ID, device ID or memory ID.
[/body/p[@paraId=0CF37311]] · Do not echo secrets or sensitive input into terminal history unnecessarily.
[/body/p[@paraId=7A67AC60]] · Require explicit confirmation for destructive local CLI actions where applicable.
[/body/p[@paraId=033D39EB]] · Never interpret terminal display text as a substitute for server-side authorization.
[/body/p[@paraId=71BE7C11]] · Keep help text, examples and error messages aligned with actual implemented behavior.
[/body/p[@paraId=71A41A06]] A command that changes permissions, revokes a device or deletes memory should explain the effect and apply the defined authorization and confirmation rules. For non-interactive scripts, confirmation requirements must have explicit behavior rather than silently defaulting to approval.
[/body/p[@paraId=3381DF67]] 03.38.13 Testing and acceptance criteria
[/body/p[@paraId=16E817A9]] CLI tests
[/body/p[@paraId=54F705E3]] · Valid and invalid command arguments.
[/body/p[@paraId=0172A386]] · Authentication expiry and denied access.
[/body/p[@paraId=64D73662]] · Correct exit codes and stable error responses.
[/body/p[@paraId=6AD2601E]] · Valid JSON output with no terminal decorations on standard output.
[/body/p[@paraId=495FF18E]] · Interrupted watch session without task cancellation.
[/body/p[@paraId=797848B5]] · Cancellation request followed by status verification.
[/body/p[@paraId=2714263D]] · Approval for an incorrect or expired operation is rejected.
[/body/p[@paraId=4B23368C]] User-experience tests
[/body/p[@paraId=56FC4E75]] · A newly accepted task returns an identifier and clear status.
[/body/p[@paraId=31AD2158]] · A clarification request identifies the missing information.
[/body/p[@paraId=5BF96579]] · An approval displays the exact operation and target.
[/body/p[@paraId=5C847C6D]] · Progress matches persisted backend state.
[/body/p[@paraId=749486E7]] · Partial success is reported accurately.
[/body/p[@paraId=7CEA08A9]] · Uncertain outcomes are never presented as confirmed success.
[/body/p[@paraId=4CDAE289]] · Unsupported operations receive honest explanations.
[/body/p[@paraId=1BEBA257]] · Follow-up references resolve correctly or trigger clarification.
[/body/p[@paraId=0D8F77B5]] Multi-user tests
[/body/p[@paraId=28D1487D]] · Task, memory and device results respect authorization.
[/body/p[@paraId=1F1C5574]] · A user cannot act on another user's task through CLI commands.
[/body/p[@paraId=4E3B50F3]] · Context from concurrent requests remains isolated.
[/body/p[@paraId=32D9E0C7]] · Machine-readable results do not expose unauthorized fields.
[/body/p[@paraId=01957BFA]] Proposed usability evaluation
[/body/p[@paraId=0E74337A]] Use a small, repeatable set of real tasks with all three developers. Observe whether users can:
[/body/p[@paraId=4825D98F]] · Submit a task and find its current status.
[/body/p[@paraId=413D260E]] · Understand why a task is blocked.
[/body/p[@paraId=51E029B1]] · Make an informed approval decision.
[/body/p[@paraId=71E64EC2]] · Identify a partial or uncertain result.
[/body/p[@paraId=3368F626]] · Recover from a common failure without needing to inspect server logs.
[/body/p[@paraId=360E2CE9]] The team should record observed confusion and errors rather than assuming that technically correct output is automatically usable.

[/body/p[@paraId=57D0C754]] 04.06.01 Purpose
[/body/p[@paraId=7FFA436C]] The first vertical slice is the smallest complete workflow that proves the core NEXUS architecture works across the CLI, backend, database and a real Windows computer.
[/body/p[@paraId=7AFB74A5]] Instead of building all backend modules, AI planning, memory and automation tools independently, the team will deliver one end-to-end capability:
[/body/p[@paraId=754719E0]] A user submits a file-search request in the terminal, NEXUS persists a task, routes it to the explicitly selected Windows device, searches only an approved directory, records the result and displays it to the user.
[/body/p[@paraId=1B9A2028]] This milestone uses a deterministic plan. It does not require a live AI model, document summarization, unrestricted shell commands or graphical desktop automation.
[/body/p[@paraId=24E44494]] Success criteria
[/body/p[@paraId=791CB18C]] · The task has a durable ID and persisted status.
[/body/p[@paraId=15FFAF94]] · The authenticated user owns the task.
[/body/p[@paraId=751AEC8C]] · The selected device is authenticated and authorized.
[/body/p[@paraId=534CD867]] · The backend and bridge validate the operation independently.
[/body/p[@paraId=6354838A]] · File access remains inside a configured directory scope.
[/body/p[@paraId=73196A86]] · Duplicate requests do not create duplicate tasks.
[/body/p[@paraId=75B604CB]] · Failures and disconnections are represented honestly.
[/body/p[@paraId=697760DF]] · The CLI displays the recorded outcome rather than assuming success.
[/body/p[@paraId=65343DF3]] 04.06.02 Scope boundary
[/body/p[@paraId=789B03E9]] Included in this slice
[/body/p[@paraId=16776B17]] Authentication, device selection, task creation, PostgreSQL persistence, deterministic planning, policy validation, bridge communication, scoped file search, task history and basic recovery tests.
[/body/p[@paraId=27B01A92]] Excluded from this slice
[/body/p[@paraId=28F82732]] Live AI planning, semantic memory retrieval, document summarization, file creation, application launching, GUI automation, broad multi-step plans and unrestricted command execution.
[/body/p[@paraId=16AE3E33]] The first slice is not the entire MVP. It is the integration foundation on which the remaining features will depend.

[/body/p[@paraId=3B218786]] 04.06.04 Request and operation contracts
[/body/p[@paraId=42E41EC4]] The first slice needs only a small number of contracts, but each must be explicit before the three developers work in parallel.
[/body/p[@paraId=32A65D96]] A. Task submission
[/body/p[@paraId=25015CAA]] Illustrative request:
[/body/p[@paraId=033C4729]] {
[/body/p[@paraId=380D8D3C]]   "client_request_id": "client-generated-unique-id",
[/body/p[@paraId=7DC8468D]]   "target_device_id": "registered-device-id",
[/body/p[@paraId=5E6A2E37]]   "request": "Find files containing the word design"
[/body/p[@paraId=411235C5]] }
[/body/p[@paraId=5330CE98]] The authenticated user identity must come from the authentication context, not from a client-supplied user_id.
[/body/p[@paraId=60CAABE5]] The backend must validate:
[/body/p[@paraId=619584A4]] · client_request_id is present and conforms to the agreed format.
[/body/p[@paraId=63CBB76E]] · target_device_id refers to a registered device the user is permitted to target.
[/body/p[@paraId=1DCACA23]] · request is non-empty and within the documented length limit.
[/body/p[@paraId=4D214166]] · The requested operation maps to a supported capability.
[/body/p[@paraId=7522724B]] · The request cannot override security policy through natural-language instructions.
[/body/p[@paraId=07F4377F]] The request above is an example, not the final API schema.
[/body/p[@paraId=7EA6EC18]] B. Deterministic planner output
[/body/p[@paraId=6AD0C627]] For the first slice, a simple deterministic request handler can map an explicitly supported file-search request to a search_files operation. It should not pretend to understand arbitrary natural-language requests.
[/body/p[@paraId=6D5806F2]] The resulting operation must contain:
[/body/p[@paraId=2D0FCE55]] · Registered tool name and schema version.
[/body/p[@paraId=47E75B0F]] · Target device ID.
[/body/p[@paraId=46D9BA58]] · Logical directory ID.
[/body/p[@paraId=0770090C]] · Search query.
[/body/p[@paraId=61BD8840]] · Result and execution limits.
[/body/p[@paraId=31F234AE]] · Expected result structure.
[/body/p[@paraId=6EAD7E7D]] The backend—not the planner—assigns authoritative task, step and operation identifiers and determines the required permissions.
[/body/p[@paraId=690A376C]] C. Bridge operation
[/body/p[@paraId=41BD028C]] The bridge request must identify the intended operation and device, carry validated arguments, and include a deadline or timeout policy.
[/body/p[@paraId=12387975]] The bridge must reject unknown tools, invalid arguments, unsupported protocol versions and out-of-scope directories. It returns a structured result or a typed error. It must not accept a generic command string to execute.
[/body/p[@paraId=6B87C270]] 04.06.05 Task persistence and idempotency
[/body/p[@paraId=753ACF19]] The first implementation must persist a task before reporting successful acceptance.
[/body/p[@paraId=7D4289C7]] Proposed minimum records:
[/body/tbl[1]] [Table: 5 rows]
[/body/p[@paraId=3DD64331]] The exact schema remains governed by the database design and migrations.
[/body/p[@paraId=46B9915A]] Duplicate submission behavior
[/body/p[@paraId=77630918]] 1. The CLI submits a request with a client-generated request ID.
[/body/p[@paraId=3C39C31B]] 2. The backend checks the unique key scoped to the authenticated user.
[/body/p[@paraId=211BCEB7]] 3. If the same ID and same normalized request are submitted again, return the existing task.
[/body/p[@paraId=507D5D9A]] 4. If the same ID is reused with a different request or target device, return a stable conflict error.
[/body/p[@paraId=70D27103]] 5. Concurrent duplicate submissions must be handled by database constraints and transactions, not just an application-level check.
[/body/p[@paraId=1505826B]] A timeout from the API does not prove that the request was rejected. The CLI should be able to retry with the same request ID or retrieve the existing task.
[/body/p[@paraId=4B8C745C]] Completion behavior
[/body/p[@paraId=278204F2]] The task may be marked SUCCEEDED only after the search operation has a valid, correlated result and the backend has successfully persisted the outcome. If the bridge might have executed the operation but the result cannot be established, the system must preserve uncertainty and invoke the recovery rules from Section 03.30.
[/body/p[@paraId=5B96C66F]] 04.06.06 Windows file-search boundaries
[/body/p[@paraId=43C4197F]] The bridge must use a logical directory identifier rather than trusting a path supplied by the model or client.
[/body/p[@paraId=3692F75D]] Example configuration:
[/body/p[@paraId=0E4CEAF6]] Logical directory: nexus_test_documents
[/body/p[@paraId=17E8BF5E]] Local directory:   configured by the Windows device owner
[/body/p[@paraId=43AF91B4]] Allowed operation: search_files
[/body/p[@paraId=388A36D9]] The actual local path is intentionally unspecified here; each developer configures their own test directory.
[/body/p[@paraId=27C59AB9]] The initial search tool should:
[/body/p[@paraId=38A7914F]] · Search only the configured directory.
[/body/p[@paraId=5693A32D]] · Enforce maximum depth, result count and execution duration.
[/body/p[@paraId=3B27F32A]] · Avoid following directory links or junctions by default.
[/body/p[@paraId=6A169915]] · Return bounded metadata, not entire file contents.
[/body/p[@paraId=1A04E7FE]] · Use stable, documented error codes.
[/body/p[@paraId=5EDAFB5D]] · Avoid returning sensitive absolute paths unless the result contract requires them.
[/body/p[@paraId=3AA55EFC]] · Support cancellation where practical, while reporting if an operation has already completed.
[/body/p[@paraId=0C2E45D0]] Search results are not permanent permissions. If a later feature reads a returned file, the bridge must revalidate that file against the active scope.
[/body/p[@paraId=22DCE828]] Required negative tests
[/body/p[@paraId=5523B7F7]] · Search using an unregistered directory ID.
[/body/p[@paraId=2281B2AA]] · Attempt directory traversal.
[/body/p[@paraId=77D9B200]] · Attempt to escape through a link or junction.
[/body/p[@paraId=0C0588B2]] · Target another device.
[/body/p[@paraId=202207B7]] · Send an unknown tool name.
[/body/p[@paraId=3882F429]] · Send malformed or excessive arguments.
[/body/p[@paraId=4CDDFCA8]] · Revoke the bridge credential and retry.
[/body/p[@paraId=687F4438]] · Disconnect the bridge while the task is pending.
[/body/p[@paraId=0270C94D]] · Lose the bridge response after dispatch and verify that NEXUS does not report fabricated success.
[/body/p[@paraId=0A84E0C1]] 04.06.07 Implementation order and team dependencies
[/body/p[@paraId=68B237C0]] Implement the slice in the following order. Do not have all three developers independently invent their own interfaces.
[/body/p[@paraId=5560626E]] 1. Freeze the minimum contracts
[/body/p[@paraId=4F10449D]] 2. Agree on the task request/response, task and step states, search_files arguments and result, error codes, device identity and operation envelope.
[/body/p[@paraId=524DC293]] 3. Gate: backend and bridge developers approve the same contract examples and tests.
[/body/p[@paraId=0A7A302E]] 4. Implement persistence and task acceptance
[/body/p[@paraId=529A8715]] 5. Create the migration, enforce request idempotency, add task lookup and implement legal state transitions.
[/body/p[@paraId=783A7D41]] 6. Gate: duplicate requests, conflicting IDs and concurrent submissions behave correctly against PostgreSQL.
[/body/p[@paraId=66809998]] 7. Implement the deterministic operation path
[/body/p[@paraId=37EB0752]] 8. Map the supported search request to a registered tool proposal. Validate its schema, device and permissions before dispatch.
[/body/p[@paraId=77C3904D]] 9. Gate: unsupported requests and invalid operations are rejected without contacting the bridge.
[/body/p[@paraId=78D40271]] 10. Implement the Windows bridge search tool
[/body/p[@paraId=7A66E4EA]] 11. Add device authentication, local directory configuration, argument validation, bounded search and structured responses.
[/body/p[@paraId=2A454851]] 12. Gate: Windows-specific path and authorization tests pass.
[/body/p[@paraId=6D82937B]] 13. Integrate orchestration and recovery
[/body/p[@paraId=604DE64F]] 14. Persist intent before dispatch, correlate the response with the operation, record the outcome and handle timeouts and disconnections.
[/body/p[@paraId=545F3CB3]] 15. Gate: interrupted operations are not blindly replayed and uncertain outcomes remain visible.
[/body/p[@paraId=759C0683]] 16. Complete CLI and end-to-end tests
[/body/p[@paraId=3FAAD03C]] 17. Display task IDs, progress, results and errors. Test the workflow with at least two developers' Windows computers, then run the three-user integration scenario.
[/body/p[@paraId=3A4577E0]] 18. Gate: the full workflow passes from a clean setup with documented results.

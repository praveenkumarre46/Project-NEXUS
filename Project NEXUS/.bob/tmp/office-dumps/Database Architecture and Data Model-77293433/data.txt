[/body/p[@paraId=606C2FAD]] 03.10.1 — Database design principles
[/body/p[@paraId=332AC709]] NEXUS should start with a relational PostgreSQL schema, explicit foreign keys, transactions and carefully chosen uniqueness constraints.
[/body/p[@paraId=040E06AE]] The design follows these principles:
[/body/p[@paraId=239CE229]] 1. Ownership is explicit. Every user-owned task and memory record has an identifiable owner.
[/body/p[@paraId=7DBC98DF]] 2. Device targeting is explicit. A task cannot accidentally migrate to another teammate's computer.
[/body/p[@paraId=57359536]] 3. History is durable. Task and step outcomes survive backend restarts.
[/body/p[@paraId=3D8E942E]] 4. Authorization is not delegated to the model. The database stores permissions and approvals, but application code enforces them.
[/body/p[@paraId=789FDE24]] 5. Concurrent operations are expected. Constraints and transactions protect against races; Python checks alone are insufficient.
[/body/p[@paraId=0BF6D29D]] 6. Sensitive data is minimized. NEXUS should not persist entire documents or raw conversations when a smaller record is sufficient.
[/body/p[@paraId=129174C3]] 7. Schema changes are versioned. Database migrations are reviewed and tested instead of being applied through ad hoc production changes.

[/body/p[@paraId=05B2CE88]] 03.10.3 — Core tables
[/body/p[@paraId=7E74826A]] A. users
[/body/p[@paraId=122EFED3]] Represents a NEXUS account.
[/body/tbl[1]] [Table: 7 rows]
[/body/p[@paraId=4DC36018]] 
[/body/p[@paraId=56FDB3B4]] Design rules:
[/body/p[@paraId=5998CF66]] · Store password hashes, never plaintext passwords.
[/body/p[@paraId=04DE78B8]] · Do not assume a password column is required if the team chooses another authentication method.
[/body/p[@paraId=5FA937B4]] · Disabling a user must prevent new requests and new operations.
[/body/p[@paraId=3F130BBF]] · The policy for tasks already running when an account is disabled must be defined explicitly.
[/body/p[@paraId=5837F16B]] B. devices
[/body/p[@paraId=683DD81E]] Represents an individual Windows computer registered with NEXUS.
[/body/tbl[2]] [Table: 9 rows]
[/body/p[@paraId=5026BD3F]] 
[/body/p[@paraId=6583D297]] Design rules:
[/body/p[@paraId=575C8E7A]] · A device ID is an identifier, not an authentication secret.
[/body/p[@paraId=4AED59F0]] · The bridge must authenticate independently of merely knowing its device ID.
[/body/p[@paraId=18E0F80A]] · Revocation must be enforced at the backend and the execution boundary.
[/body/p[@paraId=7E731C58]] · Device ownership and task ownership must be checked together before dispatch.
[/body/p[@paraId=54328065]] · A device may appear online based on its latest heartbeat while still failing an operation; heartbeat status is not proof that every tool is available.
[/body/p[@paraId=431E90D2]] Open design question: can one device be explicitly shared with multiple users, or must every device have exactly one owning user? The initial proposal is one owner per registration. Shared-device access should be added only if a real use case requires it.
[/body/p[@paraId=799B03DD]] C. tasks
[/body/p[@paraId=4B9C33E2]] Represents one user-submitted request and its overall execution lifecycle.
[/body/tbl[3]] [Table: 13 rows]
[/body/p[@paraId=0BC9472C]] 
[/body/p[@paraId=0E243F05]] Recommended constraints:
[/body/p[@paraId=502858F6]] · owner_user_id must reference a valid user.
[/body/p[@paraId=2130B0FE]] · target_device_id must reference a registered device.
[/body/p[@paraId=53671F44]] · A unique constraint on (owner_user_id, client_request_id) prevents duplicate task creation for the same user.
[/body/p[@paraId=09AE2BF7]] · Timestamps must be consistent with the task lifecycle.
[/body/p[@paraId=7B729B43]] · Status changes must be validated by application code; an arbitrary update must not bypass the state machine.
[/body/p[@paraId=451F546F]] The request text may contain private information. Retention, access and deletion rules must be defined rather than assuming that all submitted text should be kept indefinitely.
[/body/p[@paraId=0854276C]] D. task_steps
[/body/p[@paraId=1291DABF]] Stores the individual operations that make up a task.
[/body/tbl[4]] [Table: 13 rows]
[/body/p[@paraId=1459B29F]] 
[/body/p[@paraId=5B4736C1]] Recommended constraints:
[/body/p[@paraId=41102344]] · Unique (task_id, step_number).
[/body/p[@paraId=3BD08743]] · Unique operation_id.
[/body/p[@paraId=73929A12]] · Every step belongs to exactly one task.
[/body/p[@paraId=1633E5BC]] · Tool arguments must be validated against the registered tool's schema before execution.
[/body/p[@paraId=2BA5789C]] · Result data should be bounded in size and should not automatically contain full document contents.
[/body/p[@paraId=7362FD9D]] Important design distinction: a step and an attempt are not necessarily the same thing. If one logical operation is attempted several times, overwriting the previous attempt's details destroys useful evidence. For that reason, I recommend adding a separate task_step_attempts table.
[/body/p[@paraId=3E1AE2CD]] E. task_step_attempts
[/body/p[@paraId=0EBD6887]] Records each dispatch or execution attempt for a logical step.
[/body/tbl[5]] [Table: 11 rows]
[/body/p[@paraId=088EA22E]] 
[/body/p[@paraId=6CD6A0DE]] Recommended uniqueness constraint: (task_step_id, attempt_number).
[/body/p[@paraId=3D39CF90]] This table helps answer questions such as:
[/body/p[@paraId=208F94E2]] · Did NEXUS attempt this operation?
[/body/p[@paraId=4214B8BF]] · Did it receive a response?
[/body/p[@paraId=5D81B47E]] · Was the response persisted?
[/body/p[@paraId=741C36D7]] · Is retrying safe?
[/body/p[@paraId=7E64D2AF]] · Is there evidence that the previous attempt may have completed?
[/body/p[@paraId=63615CD2]] It does not magically guarantee that the bridge's filesystem operation and PostgreSQL commit happen atomically. That limitation remains part of the execution design.
[/body/p[@paraId=76E16BD7]] F. approvals
[/body/p[@paraId=07D6B824]] Stores approval decisions for consequential operations.
[/body/tbl[6]] [Table: 10 rows]
[/body/p[@paraId=596D418B]] 
[/body/p[@paraId=73A7518F]] The fingerprint must cover the meaningful operation details, including the target device and relevant arguments. The exact canonicalization and hashing mechanism will be designed later.
[/body/p[@paraId=4D7DCB08]] A changed operation must not reuse an approval intended for the earlier version. The backend must revalidate the approval immediately before dispatch.
[/body/p[@paraId=22AC6E38]] G. memories
[/body/p[@paraId=55E37774]] Stores user-controlled information that can improve future requests.
[/body/tbl[7]] [Table: 9 rows]
[/body/p[@paraId=23173CE5]] 
[/body/p[@paraId=4932B56E]] Initial design recommendation:
[/body/p[@paraId=11B36E01]] · Keep memory private to the owning user by default.
[/body/p[@paraId=20AEE2F0]] · Separate durable user preferences from temporary task context.
[/body/p[@paraId=19527C50]] · Allow the user to inspect, update and delete memories.
[/body/p[@paraId=30542613]] · Retrieve only relevant memories for a request.
[/body/p[@paraId=03F0FD55]] · Do not automatically convert every conversation or file into permanent memory.
[/body/p[@paraId=559BEFCC]] · Treat model-generated inferences as uncertain unless explicitly confirmed.
[/body/p[@paraId=2B9C34FB]] · If semantic search is required, evaluate PostgreSQL full-text search first; add vector search only after choosing an embedding model and measuring its resource cost.
[/body/p[@paraId=733DCD1A]] Logical deletion alone is not enough to meet a permanent-deletion promise. The backup, retention and any derived-index policies must be addressed in the privacy design.
[/body/p[@paraId=4F0DEB2F]] H. audit_events
[/body/p[@paraId=08CE1D69]] Records security-relevant decisions and important actions.
[/body/tbl[8]] [Table: 10 rows]
[/body/p[@paraId=0CC751ED]] 
[/body/p[@paraId=309AFBEA]] Audit records should not be used as a dumping ground for complete prompts, passwords, authentication tokens or document contents.
[/body/p[@paraId=4A46A612]] Access to audit events must be restricted. Retention and deletion rules must be defined, especially when a user requests deletion of their task history or memory.
[/body/p[@paraId=45F1857E]] 03.10.4 — Supporting tables and authorization data
[/body/p[@paraId=2BA9C608]] 
[/body/p[@paraId=46DF6492]] The core tables are not sufficient by themselves to enforce every security and concurrency requirement.
[/body/p[@paraId=5597FBAD]] Additional tables to consider
[/body/p[@paraId=2082FD9C]] 
[/body/tbl[9]] [Table: 6 rows]
[/body/p[@paraId=4576C7C4]] 
[/body/p[@paraId=752BAACB]] Avoid creating a table simply because it sounds architecturally sophisticated. Each table should represent a real lifecycle, integrity rule or query requirement.
[/body/p[@paraId=29FEC104]] Ownership enforcement
[/body/p[@paraId=168DA894]] Application code should check that a task belongs to the authenticated user before returning its data or permitting an action. PostgreSQL foreign keys alone do not enforce this ownership relationship.
[/body/p[@paraId=52370ADA]] For example, a valid task_id is not sufficient authorization to retrieve a result. The query must constrain the task by both its identifier and the authenticated user's permitted scope.
[/body/p[@paraId=76FE3964]] For device execution, the authorization check must additionally establish that:
[/body/p[@paraId=6A48D29D]] · The target device is registered and active.
[/body/p[@paraId=7CA613C0]] · The requester is permitted to use that device.
[/body/p[@paraId=18AA001C]] · The task is still eligible to execute.
[/body/p[@paraId=350B62A2]] · The requested tool and its arguments are allowed.
[/body/p[@paraId=727EC1BF]] · Any required approval is valid and applies to the exact operation.
[/body/p[@paraId=3D9548F5]] The bridge should enforce its own local restrictions as well. Backend authorization and bridge validation serve different trust boundaries.
[/body/p[@paraId=4C285607]] 03.10.5 — Relationships and integrity constraints
[/body/p[@paraId=0D67DBF9]] The intended relationships are:
[/body/p[@paraId=28A085D3]] · One user can submit many tasks.
[/body/p[@paraId=5231B9EF]] · One user can register multiple devices, subject to the eventual device-sharing policy.
[/body/p[@paraId=153B3BDF]] · One task targets one device.
[/body/p[@paraId=6BFCA559]] · One task contains an ordered collection of steps.
[/body/p[@paraId=1D77B4C7]] · One logical step may have multiple execution attempts.
[/body/p[@paraId=34953A84]] · One step may require an approval record, depending on its risk and permission policy.
[/body/p[@paraId=08FFD742]] · One user can own multiple memories.
[/body/p[@paraId=5E56E0C4]] · Audit events can reference users, devices and tasks where applicable.
[/body/p[@paraId=7777E743]] The schema should use foreign keys for these relationships rather than relying on application conventions alone.
[/body/p[@paraId=438BCDD5]] Deletion policy
[/body/p[@paraId=2B6ADA3F]] Deletion behavior must be chosen deliberately:
[/body/p[@paraId=0D0528CB]] · Deleting a user should not accidentally cascade into deleting security evidence that is still subject to retention requirements.
[/body/p[@paraId=0A041D58]] · Removing a device should revoke access and preserve relevant task history.
[/body/p[@paraId=0F1EC610]] · Deleting a task must not automatically erase unrelated memories.
[/body/p[@paraId=079F3405]] · Deleting a memory must make it unavailable to future context retrieval.
[/body/p[@paraId=06E5D01C]] · Audit and backup retention may differ from normal application-data retention.
[/body/p[@paraId=32E07C67]] For the MVP, revocation or deactivation is generally safer than cascading deletion for users and devices. A dedicated data-retention policy will determine when physical deletion is appropriate.
[/body/p[@paraId=3A0E521C]] 03.10.6 — Transactions and concurrency
[/body/p[@paraId=2B20D447]] This is where the database model connects directly to NEXUS's execution engine.
[/body/p[@paraId=64B9BFEB]] Example A: duplicate task submissions
[/body/p[@paraId=0ECEEA82]] Two API requests arrive concurrently with the same (owner_user_id, client_request_id).
[/body/p[@paraId=3194BEB7]] A Python-level sequence such as “check whether it exists, then insert” is unsafe: both requests can observe that the row does not exist.
[/body/p[@paraId=15D84155]] The unique database constraint must arbitrate the race. The losing request should retrieve the existing task if its payload matches, or return a conflict if the payload differs.
[/body/p[@paraId=6E308994]] Example B: two workers claim the same task
[/body/p[@paraId=6AF4C122]] A worker must not simply read status = 'queued' and then update it later without coordination.
[/body/p[@paraId=0651F105]] The claim should be an atomic database operation that grants ownership to one worker. A transaction with row-level locking or a carefully designed atomic update is a possible implementation. The exact query and isolation behavior should be tested against the selected PostgreSQL version.
[/body/p[@paraId=31CC62BA]] Example C: task and step updates
[/body/p[@paraId=09940C7C]] When a worker records a step outcome, it may need to update both the step and the parent task.
[/body/p[@paraId=7BB4A987]] Those database changes should be committed in a single transaction when they form one logical database-state change. The transaction should remain short and must not include waiting for the bridge to finish a Windows operation.
[/body/p[@paraId=1AD8EBD1]] Example D: approval races
[/body/p[@paraId=4A1EB256]] Suppose a user approves a step just as another process cancels the task.
[/body/p[@paraId=11D56582]] NEXUS needs defined ordering and transition rules so that approval cannot accidentally revive a cancelled task. The approval endpoint and worker must re-read and validate the relevant state under appropriate transactional coordination.
[/body/p[@paraId=4254C733]] Database transactions protect NEXUS's records. They do not roll back external Windows operations. This distinction must remain explicit throughout implementation.

[/body/p[@paraId=5702DEA1]] Capture a baseline for:

[/body/p[@paraId=3AAB7DC1]] · Task status lookup latency.

[/body/p[@paraId=16147D50]] 03.10.8 — Schema migrations and development workflow
[/body/p[@paraId=71800C72]] Use a versioned migration tool such as Alembic with SQLAlchemy, subject to the team's final dependency decision.
[/body/p[@paraId=40BB844E]] The database workflow should be:
[/body/p[@paraId=62851DA7]] 1. Define the domain change and integrity requirements.
[/body/p[@paraId=0764B7E8]] 2. Write a migration with a reviewable upgrade path.
[/body/p[@paraId=733C11CB]] 3. Test the migration against a fresh database.
[/body/p[@paraId=438EE46F]] 4. Test it against a database containing representative existing data.
[/body/p[@paraId=147B4449]] 5. Verify constraints, indexes and application compatibility.
[/body/p[@paraId=2F0904F1]] 6. Document how to recover if the migration fails.
[/body/p[@paraId=67DA99B9]] 7. Commit migration files alongside the corresponding application change.
[/body/p[@paraId=06A5679C]] Do not let each developer independently modify the shared database schema through manual SQL and then try to reconstruct those changes later.
[/body/p[@paraId=34C05EAB]] A local Docker Compose environment can provide a repeatable PostgreSQL instance. The exact PostgreSQL version, database name, credentials management, connection-pool size and migration configuration remain deployment decisions.
[/body/p[@paraId=78033539]] Test database requirements
[/body/p[@paraId=54EB3885]] The test suite should include:
[/body/p[@paraId=5524FFF3]] · Fresh schema creation.
[/body/p[@paraId=703ADCFB]] · Migration upgrade tests.
[/body/p[@paraId=2ED97A0C]] · Foreign-key and uniqueness violations.
[/body/p[@paraId=349C9AD4]] · Concurrent duplicate submissions.
[/body/p[@paraId=1B412D02]] · Concurrent worker claims.
[/body/p[@paraId=7844D9AF]] · Approval versus cancellation races.
[/body/p[@paraId=7E7E233A]] · Task recovery after backend restart.
[/body/p[@paraId=43A4478B]] · Data-isolation tests between users.
[/body/p[@paraId=7B24398D]] · Memory deletion and retrieval tests.
[/body/p[@paraId=7196C692]] Unit tests may mock the persistence interface. However, tests for transactions, locking, uniqueness and isolation must run against PostgreSQL rather than relying entirely on mocks.
[/body/p[@paraId=1227DB31]] 03.10.9 — Data privacy and retention
[/body/p[@paraId=4CCE455E]] NEXUS can access private documents and maintain long-term context. The data model therefore needs a privacy policy before the team implements unrestricted logging or memory capture.
[/body/p[@paraId=3DE9BBC6]] Proposed defaults:
[/body/p[@paraId=246FDBAA]] · Store only the information needed to execute tasks, recover safely and provide useful history.
[/body/p[@paraId=07A6E13C]] · Do not store complete document contents in task records by default.
[/body/p[@paraId=767833AB]] · Avoid persisting model prompts and responses unless there is a defined product need.
[/body/p[@paraId=7195A800]] · Exclude secrets and authentication credentials from audit metadata.
[/body/p[@paraId=562D67A3]] · Keep user memories separate from task execution history.
[/body/p[@paraId=657A5785]] · Make memory inspection, editing and deletion available to the owner.
[/body/p[@paraId=0A797A72]] · Define retention periods for task history, execution attempts and audit records.
[/body/p[@paraId=6FE9B801]] · Document whether database backups retain deleted data and for how long.
[/body/p[@paraId=79255E39]] An additional unresolved decision is whether task history is retained indefinitely, for a fixed period, or according to a user-configurable setting. This should be decided before the application advertises specific deletion guarantees.
[/body/p[@paraId=370A9243]] 03.10.10 — Database acceptance criteria
[/body/p[@paraId=0D5D7886]] Use this checklist when reviewing the database implementation.
[/body/p[@paraId=0AF94F61]] Database review
[/body/p[@paraId=2CEABB56]] 0/13
[/body/p[@paraId=4A4B02D8]] All core tables have explicit primary keys, appropriate foreign keys and documented ownership.
[/body/p[@paraId=6467BB05]] Duplicate task submission is prevented by a database-enforced uniqueness constraint.
[/body/p[@paraId=3B0DF12A]] Task and step states cannot be changed through unvalidated application paths.
[/body/p[@paraId=08DDD8AF]] Worker coordination prevents two valid workers from simultaneously owning the same step.
[/body/p[@paraId=0B57F271]] Execution attempts preserve enough evidence for safe recovery.
[/body/p[@paraId=0AE7A412]] Approval records bind to the exact operation being authorized.
[/body/p[@paraId=3E42097F]] One user cannot retrieve another user's tasks, memories or unauthorized device records.
[/body/p[@paraId=431822EF]] Device revocation blocks new execution while preserving required history.
[/body/p[@paraId=67A3D035]] Memory deletion prevents future retrieval and follows the documented retention policy.
[/body/p[@paraId=5D6A25F3]] Migrations work on both a fresh database and a representative existing database.
[/body/p[@paraId=2E0F4129]] Concurrency and transaction tests run against PostgreSQL.
[/body/p[@paraId=58AB0157]] Indexes are justified by actual queries and measured access patterns.
[/body/p[@paraId=7E6C2811]] Logs and audit metadata do not expose credentials or unnecessary private content.

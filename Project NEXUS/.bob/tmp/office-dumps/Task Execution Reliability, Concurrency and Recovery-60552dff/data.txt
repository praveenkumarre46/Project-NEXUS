[/body/p[@paraId=0CF09223]] 03.15.1 Objectives
[/body/p[@paraId=380BC6EE]] NEXUS must:
[/body/p[@paraId=506646D5]] · Preserve accepted tasks and their execution history.
[/body/p[@paraId=6A205858]] · Prevent duplicate task submissions from unintentionally repeating work.
[/body/p[@paraId=65250832]] · Coordinate concurrent workers without claiming the same work unsafely.
[/body/p[@paraId=31C8917D]] · Keep user approvals attached to the exact operation they authorize.
[/body/p[@paraId=339B80CE]] · Handle cancellation without falsely claiming an operation stopped.
[/body/p[@paraId=39407876]] · Recover from backend, model-runtime and device failures.
[/body/p[@paraId=012A1717]] · Distinguish definite failure from an uncertain outcome.
[/body/p[@paraId=73D42E97]] · Report partial completion honestly.
[/body/p[@paraId=04C8CAEC]] · Avoid holding database transactions open while waiting for slow external operations.
[/body/p[@paraId=4814247E]] Fundamental constraint: PostgreSQL and a Windows computer cannot participate in one ordinary atomic transaction. NEXUS cannot guarantee that an external computer operation executes exactly once in every crash scenario. It must combine durable state, operation identifiers, safe retries and reconciliation.

[/body/p[@paraId=059F1B52]] 03.15.03 Task steps and operation states
[/body/p[@paraId=7E168E54]] A task is a sequence of logical steps. A step can represent searching files, reading a document, creating a file or launching an application.
[/body/p[@paraId=64D4853E]] The task state alone is insufficient to recover safely. NEXUS must track the state of each step and each attempt to perform that step.
[/body/p[@paraId=342F6B5D]] Proposed step states
[/body/tbl[2]] [Table: 11 rows]
[/body/p[@paraId=05C61D97]] The exact states may be simplified during implementation, but uncertainty must not be collapsed into ordinary failure.
[/body/p[@paraId=4FE39517]] Step execution protocol
[/body/p[@paraId=1CF701AD]] 1. Prepare: validate the proposed tool and its arguments.
[/body/p[@paraId=667B29BD]] 2. Authorize: check user, device, permissions and approval requirements.
[/body/p[@paraId=69D13D57]] 3. Persist intent: store the operation ID and a durable step state before dispatch.
[/body/p[@paraId=2C13FC47]] 4. Dispatch: send the request to the explicitly registered target device.
[/body/p[@paraId=13C6F5AC]] 5. Execute: the bridge validates the request again and invokes its registered tool.
[/body/p[@paraId=49EDF0EC]] 6. Record: persist the response, attempt information and outcome.
[/body/p[@paraId=5E3AFF08]] 7. Verify: apply the tool's verification contract to establish what actually happened.
[/body/p[@paraId=27D2EC60]] 8. Advance: release dependent steps only when their prerequisites are satisfied.
[/body/p[@paraId=538EA054]] The backend should use short database transactions for preparation, claims and result recording. It should not hold a database transaction open while waiting for a model response, user approval or a Windows operation.
[/body/p[@paraId=69780E3A]] 03.15.04 Duplicate requests and idempotency
[/body/p[@paraId=28A19863]] Network failures and impatient retries can cause the same task request to reach the backend more than once.
[/body/p[@paraId=78B45E8E]] NEXUS must support a client-generated client_request_id for task submission.
[/body/p[@paraId=4BC90A37]] Proposed behavior:
[/body/p[@paraId=7BAB5A91]] · The first valid request creates a task and stores its request identifier.
[/body/p[@paraId=51D49ED3]] · Repeating the same identifier for the same user and equivalent request returns the existing task.
[/body/p[@paraId=329D6141]] · Reusing that identifier for a different request returns a conflict.
[/body/p[@paraId=4E584A5A]] · The database enforces uniqueness; an application-level “check then insert” is not sufficient by itself under concurrent requests.
[/body/p[@paraId=2C77CEA1]] · The client can retrieve the existing task after a network timeout rather than blindly submitting a new one.
[/body/p[@paraId=5A136A70]] Task idempotency does not automatically make each computer operation idempotent. A task may contain several operations, and some operations—such as launching an application—may have different semantics when repeated.
[/body/p[@paraId=3B49C39A]] Each operation should have a stable operation_id across retries of that logical operation. The bridge should retain enough information to identify duplicate operations and return a known outcome when possible.

[/body/p[@paraId=1EE19926]] 03.15.05 Worker coordination and concurrency
[/body/p[@paraId=2B63B2E4]] The initial architecture is a modular backend with PostgreSQL-backed coordination. A separate message broker is not required unless measured workload or operational requirements justify it.
[/body/p[@paraId=11D1C448]] Multiple workers may try to claim work simultaneously. The database must arbitrate ownership rather than relying on in-memory flags.
[/body/p[@paraId=77D6FD9A]] Proposed worker-claim model
[/body/p[@paraId=5B1D457A]] Each active claim should identify:
[/body/p[@paraId=31C6FB3A]] · The task or step being claimed.
[/body/p[@paraId=6108CE17]] · The worker identifier.
[/body/p[@paraId=093CC8B3]] · A claim generation or fencing token.
[/body/p[@paraId=502DD470]] · The claim time and lease expiry.
[/body/p[@paraId=4B9CA625]] · The current execution state.
[/body/p[@paraId=03667431]] A worker must verify that it still owns the valid claim before committing a result. If a claim expires and another worker takes over, a stale worker must not overwrite the newer worker's task state.
[/body/p[@paraId=73C9BF76]] PostgreSQL row locking and atomic updates are candidate implementation mechanisms. The precise query strategy should be selected during the database design and validated with concurrent integration tests.
[/body/p[@paraId=51124543]] Concurrency boundaries
[/body/p[@paraId=7955C7B7]] NEXUS must manage concurrency at more than one level:
[/body/p[@paraId=46FAC6DD]] 1. Task-level: multiple tasks may be active at once.
[/body/p[@paraId=0524DF7D]] 2. Step-level: independent steps may be eligible to run concurrently only if their dependencies and side effects permit it.
[/body/p[@paraId=5783465F]] 3. Device-level: an individual computer may need a limit on simultaneous operations.
[/body/p[@paraId=25E9E0EE]] 4. Model-level: concurrent inference must respect available CPU, memory and GPU resources.
[/body/p[@paraId=19DBECD7]] 5. Resource-level: conflicting operations against the same file or application may require serialization.
[/body/p[@paraId=5A6385CC]] For the MVP, prefer a simple, configurable concurrency limit and conservative execution. Parallelize only when the task model and tool contracts establish that it is safe.
[/body/p[@paraId=141EA0AF]] A database lease is not proof that an external Windows operation stopped. If a worker loses its lease while a bridge operation is in progress, the system must reconcile that operation before another worker repeats it.
[/body/p[@paraId=2FB9B7C3]] 03.15.06 Cancellation semantics
[/body/p[@paraId=0651256D]] Cancellation is a request to stop further work, not evidence that the work has stopped.
[/body/p[@paraId=7551E27B]] The API should acknowledge the cancellation request separately from reporting the final task state.
[/body/p[@paraId=6B85DE31]] Proposed cancellation behavior
[/body/p[@paraId=7BAD6ACA]] · Queued task: prevent dispatch if execution has not started.
[/body/p[@paraId=11FBB24D]] · Running task before dispatch: stop future dispatches once the cancellation request is recorded and observed.
[/body/p[@paraId=06069BB6]] · Waiting for approval: invalidate or close the pending execution path so a late approval cannot restart the cancelled task.
[/body/p[@paraId=164E3C03]] · Bridge operation in progress: request cancellation only if the tool and bridge support it.
[/body/p[@paraId=6B0780F6]] · Operation with uncertain outcome: reconcile before deciding whether cancellation can safely be confirmed.
[/body/p[@paraId=1E21D9C6]] · Already completed operation: preserve the result. Do not imply that cancellation undid an action already performed.
[/body/p[@paraId=4636C566]] When cancellation is requested, the orchestrator should prevent new step dispatches and determine the status of any in-flight operations. A task becomes cancelled only after the system establishes that the remaining execution has stopped or will not proceed and that the required final-state conditions are satisfied.
[/body/p[@paraId=387ABBC0]] Some computer operations may not be safely reversible. NEXUS must not promise that cancelling a task restores the computer to its previous state.
[/body/p[@paraId=15C350D7]] 03.15.07 Recovery after a backend restart
[/body/p[@paraId=1F7DB665]] PostgreSQL is the durable record of accepted tasks, steps, approvals and recorded outcomes. In-memory worker state alone is insufficient.
[/body/p[@paraId=23E37552]] When the backend restarts, it should:
[/body/p[@paraId=5CFC32C0]] 1. Load tasks that were not in terminal states.
[/body/p[@paraId=5B014714]] 2. Identify claims that are expired or no longer owned by a live worker.
[/body/p[@paraId=17C80982]] 3. Inspect dispatched or running steps whose outcomes were not durably recorded.
[/body/p[@paraId=0E332C85]] 4. Query the target bridge for known operation status when the protocol supports it.
[/body/p[@paraId=29289661]] 5. Reconcile operation outcomes before deciding whether to retry.
[/body/p[@paraId=7C6998B6]] 6. Revalidate authorization and approval requirements before resuming work.
[/body/p[@paraId=55F84301]] 7. Mark unrecoverable ambiguity as interrupted or uncertain and report it honestly.

[/body/p[@paraId=22B76DA1]] 03.15.08 Recovery after a Windows device disconnects
[/body/p[@paraId=239C3661]] Each task has an explicit target device. An offline device must not cause NEXUS to silently execute the task on the designated inference host or another teammate's computer.
[/body/p[@paraId=20C22743]] When the target bridge disconnects:
[/body/p[@paraId=630328C0]] · Stop dispatching new operations to that device.
[/body/p[@paraId=0E419CA2]] · Preserve all recorded step outcomes.
[/body/p[@paraId=17240E4A]] · Detect whether an operation was in flight.
[/body/p[@paraId=37BC7900]] · Distinguish a known failure from a lost response.
[/body/p[@paraId=50325ABA]] · Resume only when the device reconnects and the operation is safe to continue.
[/body/p[@paraId=0C1C9AD7]] · Revalidate the device's registration and authorization.
[/body/p[@paraId=02FA23BD]] · Require recovery or user input if the external outcome cannot be established.
[/body/p[@paraId=3D69B367]] A heartbeat indicates recent communication, not proof that every tool is available or that the computer is in a state suitable for an operation.
[/body/p[@paraId=4B887EE8]] 03.15.09 Approval, expiry and cancellation races
[/body/p[@paraId=09CDB6FE]] Approval can race with cancellation, task recovery or a change in the requested operation.
[/body/p[@paraId=187E2BB4]] The backend must define one authoritative ordering for competing state changes. It must not let an approval request and a cancellation request independently authorize execution.
[/body/p[@paraId=07B8FF2C]] Required rules:
[/body/p[@paraId=01973A3C]] · Approval is bound to the specific task, step, user, device, tool, normalized arguments, risk decision and expiry.
[/body/p[@paraId=3BC1AB7B]] · If the operation or relevant parameters change, the previous approval no longer applies.
[/body/p[@paraId=68F0ADA5]] · Approval expiry must be checked when execution is about to proceed, not only when the approval is created.
[/body/p[@paraId=69BCE975]] · A late approval must not restart a terminal or cancelled task.
[/body/p[@paraId=400A6582]] · If cancellation wins the state transition, pending operations must not be dispatched.
[/body/p[@paraId=0700FC5D]] · Concurrent decisions must be serialized or resolved using a defined transactional rule.
[/body/p[@paraId=07407680]] · Authorization must be rechecked immediately before dispatch.
[/body/p[@paraId=46D7138D]] The approval expiry duration remains a configuration decision. It should be defined before implementation rather than embedded as an undocumented constant.
[/body/p[@paraId=26644FCF]] 03.15.10 Partial success and compensation
[/body/p[@paraId=696DB213]] Some tasks consist of several independent actions. If a task has five steps and the fourth fails, the first three may already have changed the user's computer.
[/body/p[@paraId=1A6260AA]] NEXUS must distinguish:
[/body/p[@paraId=11EA05C5]] · Complete success: all required steps succeeded and the requested outcome was verified.
[/body/p[@paraId=704957F7]] · Partial success: some steps succeeded, but the full requested outcome was not achieved.
[/body/p[@paraId=5EF3667E]] · Failure without known side effects: execution failed and no relevant external change is known to have occurred.
[/body/p[@paraId=31F2493E]] · Uncertain outcome: evidence is insufficient to establish what happened.
[/body/p[@paraId=2CA78987]] · Cancellation after partial execution: further execution stopped, but completed actions remain recorded.
[/body/p[@paraId=4410CFB2]] The task result should identify completed, failed, skipped and uncertain steps.
[/body/p[@paraId=27FD249E]] Compensation policy
[/body/p[@paraId=03BA95C0]] Compensation means performing a separate action intended to reverse or mitigate an earlier action. It is not the same as rolling back a database transaction.
[/body/p[@paraId=0B5CB75E]] For the MVP:
[/body/p[@paraId=697E10C3]] · Do not automatically compensate arbitrary computer operations.
[/body/p[@paraId=60E65305]] · A compensating operation must be explicitly defined, authorized and safe for that tool.
[/body/p[@paraId=2F07B24D]] · Do not delete or overwrite data as an assumed way to recover.
[/body/p[@paraId=266324D3]] · If a safe compensation is unavailable, report the partial outcome and offer a supported next step.
[/body/p[@paraId=704928F2]] · Preserve an audit trail of the original action and any compensation.
[/body/p[@paraId=194F589E]] 03.15.11 Timeouts and retry budgets
[/body/p[@paraId=188F58E3]] Every external operation should have a documented timeout policy. A timeout must not automatically be interpreted as proof that the operation failed.
[/body/p[@paraId=6744EECD]] Each registered tool should specify:
[/body/p[@paraId=11C89ADC]] · Execution timeout.
[/body/p[@paraId=35D0FD86]] · Whether cancellation is supported.
[/body/p[@paraId=5246D5EC]] · Whether retry is safe.
[/body/p[@paraId=71CD362C]] · Maximum retry count and any backoff policy.
[/body/p[@paraId=6E8A1F9A]] · Whether the operation supports status lookup or reconciliation.
[/body/p[@paraId=2C736666]] · What evidence is required to declare success.
[/body/p[@paraId=6FBDBB5A]] The task orchestrator should also have bounded limits for planning, approval waiting, task execution and recovery. Their actual values should be configurable and measured.
[/body/p[@paraId=509A5026]] Do not use one global timeout for every operation. Searching a directory, extracting a large document and launching an application have different performance characteristics.
[/body/p[@paraId=24FA4737]] 03.15.12 Observability and diagnostics
[/body/p[@paraId=110CB8CA]] A failure must be explainable without exposing private file contents or credentials.
[/body/p[@paraId=614C94A9]] For each task and step, capture relevant operational metadata:
[/body/p[@paraId=49453C72]] · Task ID, step ID and operation ID.
[/body/p[@paraId=768C39BD]] · User and target device identifiers.
[/body/p[@paraId=4667B5F3]] · Worker and attempt identifiers.
[/body/p[@paraId=70AF0A80]] · State transitions and timestamps.
[/body/p[@paraId=5D4D36D7]] · Duration and retry count.
[/body/p[@paraId=1FF66464]] · Machine-readable error code.
[/body/p[@paraId=5817D135]] · Whether the outcome is known, failed or uncertain.
[/body/p[@paraId=6C6E2557]] · Recovery decisions and approval events.
[/body/p[@paraId=78C16299]] Sensitive request content, document bodies, authentication tokens and secrets should not be included in ordinary logs by default.

[/body/p[@paraId=7DCD2B5C]] 03.15.14 Acceptance criteria
[/body/p[@paraId=2841E914]] Section 03.15 is ready for implementation when:
[/body/p[@paraId=2156A6E9]] · Task and step state transitions have explicit legal-transition rules.
[/body/p[@paraId=34FCA57B]] · Duplicate task submission is protected by database-enforced idempotency.
[/body/p[@paraId=0852E73B]] · Workers claim tasks or steps atomically.
[/body/p[@paraId=4C7BCDE1]] · Stale workers cannot overwrite newer state.
[/body/p[@paraId=1E52F1B4]] · Every external operation has an operation ID and a defined retry policy.
[/body/p[@paraId=7CDCFA5D]] · Uncertain outcomes remain distinguishable from definite failures.
[/body/p[@paraId=045DDFCD]] · Cancellation does not claim success before the outcome is established.
[/body/p[@paraId=75DD9C1A]] · Backend restart recovery is tested at key crash points.
[/body/p[@paraId=247A6AAB]] · Device disconnection never triggers silent execution on another computer.
[/body/p[@paraId=0C315DBB]] · Approval expiry and cancellation races have defined outcomes.
[/body/p[@paraId=0CCC5F49]] · Partial success is accurately reported.
[/body/p[@paraId=026D5505]] · Logs support diagnosis without unnecessarily storing private content.
[/body/p[@paraId=3C668B65]] · Failure-injection and concurrency tests pass.

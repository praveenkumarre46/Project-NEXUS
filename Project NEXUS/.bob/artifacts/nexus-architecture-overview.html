What is NEXUS?

NEXUS is a personal AI computer companion with two equally important capabilities:

🖥️ Computer automation — understand requests and safely execute multi-step tasks on a user's Windows 11 computer via explicitly permitted tools.

🧠 Context awareness — maintain persistent knowledge of projects, preferences, ongoing tasks, and prior interactions.

NEXUS goes beyond a chatbot: it plans, acts through explicitly permitted tools, observes outcomes, recovers from failures, and explains what happened.

Trust Boundaries

A
Client → Backend
Every request authenticated
Identity comes from validated credentials — never from a user ID in the request body.
B
Backend → Model
Model output is untrusted input
Model cannot authorize actions, touch the database, or bypass policy. It only proposes.
C
Backend → Bridge
Bridge validates independently
Bridge authenticates and validates every operation on that device — never trusts the backend blindly.
D
App → Database
Repository layer enforces ownership
Ownership checks on all user-owned records. Transactions keep task state consistent.
E
Device → Device
No cross-device file access
One teammate's bridge is never a route to another's files. Authorization checked per operation.

⚠ "Local network" does NOT mean "trusted."

Tiered Autonomy Policy

TierAction ClassBehavior
Tier 0 — ReadSearch permitted folders, read documents, inspect task historyExecute without per-action approval when the user has granted the relevant permission
Tier 1 — ReversibleCreate draft/file in a designated workspace, launch an approved applicationExecute automatically only within a clearly configured permission scope
Tier 2 — ConsequentialOverwrite files, move important data, change system settingsRequire explicit user confirmation before execution
Tier 3 — ProhibitedBypass access controls, access another user's files, execute unrestricted model-generated commandsReject unconditionally — even if requested by the model

8-Layer Policy Engine

Every proposed operation passes all 8 layers in strict order. A DENY at any layer cannot be overridden by a later layer.

L1
Hard prohibitions → DENY if prohibited or unsupported
L2
Tool capability registered and enabled → DENY if unknown or disabled
L3
Identity and ownership verified → DENY if user not owner or device not authorized
L4
Resource permissions (active grant for directory / app ID) → DENY if no grant
L5
Operation constraints (arguments valid, limits not exceeded) → DENY if violated
L6
Risk classification (Tier 0–3) → DENY or REQUIRE_APPROVAL by tier
L7
Approval validation (valid, unexpired, fingerprint matches) → REQUIRE_APPROVAL if missing
L8
Execution-time revalidation (all prior layers rechecked) → DENY if anything changed
✓ ALLOW → persist intent → dispatch to bridge

All decisions (ALLOW / DENY / REQUIRE_APPROVAL) are written to the audit log. Policy service unavailable = no dispatch.

Task State Machine

⚑ Initial: QUEUED
▶ RUNNING
⏸ WAITING_FOR_APPROVAL
⚡ INTERRUPTED
✓ SUCCEEDED
✗ FAILED
⊘ CANCELLED
Forbidden transitions: SUCCEEDED → RUNNING · CANCELLED → QUEUED · WAITING_FOR_APPROVAL → SUCCEEDED without execution · INTERRUPTED → SUCCEEDED without reconciliation · any state to SUCCEEDED on model/bridge claim alone · any state to CANCELLED while an external effect is unresolved.

A task is only marked SUCCEEDED after a correlated result is persisted and verified in the database. A timeout is not proof of failure — uncertain outcomes are surfaced to the user.

Key Design Rules (Non-negotiable)

  • The CLI never writes directly to PostgreSQL.
  • The planner proposes — application code authorizes. The planner cannot call arbitrary Windows functions.
  • API route handlers do not contain task state machine or authorization logic.
  • The bridge executes only registered local tools after its own independent validation.
  • A timeout is not proof of failure — uncertain outcomes are surfaced to the user, never assumed.
  • A task is only SUCCEEDED after a correlated result is persisted and verified.
  • "Local network" does not mean "trusted."
  • Model output is always untrusted input — it cannot authorize, touch the DB, or bypass policy.
  • Authorization filter runs before any content is exposed to the model.
  • Revoked devices remain revoked even after a database restore.
